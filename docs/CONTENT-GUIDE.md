## 1. Day 본문 형식

### 1.1 파일과 id

- 위치: `textbook/content/<프로젝트 id>/day-NN.md` (NN은 두 자리, `01`부터). 예: `textbook/content/p1/day-07.md`
- Day id는 `<프로젝트 id>-dNN`이다. 예: `p1-d07`. 링크·`--only` 옵션에 쓴다.
- Day 제목·예상 시간(`minutes`)·요약·키워드는 `curriculum.json`에 있다. 화면 맨 위 제목(`Day 7 · Git·GitHub 시작`)은 자동으로 붙으므로 본문에 `#` 제목(h1)을 쓰지 않는다(`E_H1`).
- `_`로 시작하는 파일(예: `_outline.md`)은 빌드가 무시한다. 개요·메모는 이렇게 둔다.
- 인코딩은 UTF-8. 줄바꿈은 LF·CRLF 모두 된다(빌드가 LF로 통일한다).

### 1.2 섹션 순서 (빌드가 강제한다)

본문의 `##`(h2) 제목은 **아래 문자열 그대로, 이 순서로만** 쓴다. 다른 h2는 오류(`E_SECTION_UNKNOWN`)다. 그 아래 구분은 `###`(h3)로 한다. 이모지 뒤의 변형 선택자(U+FE0F)는 비교할 때 무시되지만, 아래 문자열을 복사해 쓰는 것이 가장 안전하다.

| 순서 | 제목 (그대로 복사) | 필수 | 들어갈 내용 |
|---|---|---|---|
| 1 | `## 🎯 오늘의 목표` | 필수 | "오늘이 끝나면 이렇게 할 수 있어요." + 확인 가능한 목표 2~4개 + `**예상 시간: N분**`(curriculum의 `minutes`와 같은 값, 내역 포함) + 맨 끝에 `:::path 📂 시작 상태`(규칙 a) |
| 2 | `## 📖 개념 이해` | 필수 | 개념마다 `###`. **비유 → 정확한 정의 → 실무 맥락** 순서. 비유만 남기지 않는다. "왜"를 먼저, "어떻게"를 뒤에 |
| 3 | `## 🛠️ 따라하기` | 필수 | `### N단계 · 제목 (M분)`. 단계마다 **어디서 / 무엇을 / 결과(`:::success`)** (규칙 b) |
| 4 | `## ✍️ 과제` | 필수 | 1~3개. `### 과제 N · 제목 (쉬움 ⭐ / 보통 ⭐⭐ / 도전 ⭐⭐⭐, M분)`. 조건을 목록으로, 확인 방법과 힌트 포함 |
| 5 | `## ✅ 정답` | 필수 | 과제마다 `:::answer 과제 N 정답 · 제목` + 마지막에 `:::answer 오늘 끝 상태 전체 코드`(규칙 d). 각 정답에 "왜 이렇게 하나요?" 해설. `:::answer`가 하나도 없으면 오류(`E_ANSWER_MISSING`) |
| 6 | `## 🧯 자주 막히는 곳` | 필수 | 그날 가장 흔한 막힘 3~6개. `### 증상` / `**원인:**` / `**해결:**`. 첫 줄에 [문제 해결 모음](#/page/troubleshooting) 링크 |
| 7 | `## 📝 오늘의 체크리스트` | 필수 | `- [ ]` 항목 5~8개(3개 미만이면 `E_CHECKLIST_SHORT`). 화면으로 확인할 수 있는 문장. 과제도 한 줄 넣는다 |
| 8 | `## 📚 더 알아보기` | 선택 | 공식 문서 링크 2~4개 + 각 링크가 무엇을 보여 주는지 한 줄. 있으면 반드시 맨 끝 |

- Day의 **맨 마지막 줄**(체크리스트 또는 더 알아보기 섹션의 끝)에 다음 Day 예고를 한 줄 둔다(규칙 g).
- 체크리스트 원문의 `[x]`는 무시되고 항상 빈 칸으로 보인다(체크 상태는 학습자의 진도가 정한다). 항상 `- [ ]`로 쓴다.
- 프로젝트의 Day 1에는 시작 상태 바로 앞에 `:::tip 이 교재를 읽는 방법`을 둔다(견본 참고). 다른 Day에는 두지 않는다. 시작 상태(`:::path 📂 시작 상태`)는 언제나 `🎯 오늘의 목표`의 마지막 블록이다.

### 1.3 확장 블록 (`:::`)

| 블록 | 화면에 자동으로 붙는 표시 | 쓰는 곳 |
|---|---|---|
| `:::tip 제목` | 💡 꿀팁 | 알면 편한 것, 대안 경로 |
| `:::warn 제목` | ⚠️ 주의 | 데이터 손실, 보안, 되돌리기 어려운 일, 자주 하는 실수를 미리 막을 때 |
| `:::info 제목` | ℹ️ 알아두기 | 배경 지식. **실무 이야기는 `:::info 실무에서는`** 으로 쓴다 |
| `:::path 제목` | 📍 경로 | 경로·위치 강조. 시작 상태는 `:::path 📂 시작 상태` |
| `:::success` | ✅ 이렇게 보이면 성공 | 단계의 결과 확인. 표시가 자동으로 붙으므로 **제목을 쓰지 않는다** |
| `:::answer 제목` | 접힌 정답 (처음 펼칠 때 "먼저 직접 풀어 보세요" 확인) | `## ✅ 정답` 안에서만 |

엔진 규칙(어기면 빌드가 멈춘다):

- `:::종류`와 닫는 `:::`는 **줄 맨 앞(0번째 칸)** 에 쓴다. 들여 쓰면 `E_CONTAINER_INDENT`. 콜론은 **정확히 3개**(`::::`도 `E_CONTAINER_INDENT`).
- 블록 안에 블록을 넣지 않는다(`E_CONTAINER_NESTED`). 나란히 둔다.
- 종류는 위 6개뿐이다(`E_CONTAINER_TYPE`). 열었으면 반드시 `:::` 한 줄로 닫는다(`E_CONTAINER_UNCLOSED`, 짝 없는 닫기는 `E_CONTAINER_STRAY`).
- 제목(`:::tip` 뒤의 글자)은 **그냥 글자**로 나온다. `**굵게**`, `` `코드` ``, 링크를 쓰면 기호가 그대로 보인다. 제목은 짧은 평문으로 쓴다.
- 블록 안에는 문단·목록·표·코드 블록(📄 캡션 포함)을 자유롭게 쓸 수 있다.

**번호 단계 안에 성공 상자를 넣는 법.** 목록 항목 안에 `:::`를 들여 쓰면 오류다. 목록을 끝내고, 줄 맨 앞에 블록을 두고, 다음 번호부터 다시 쓴다. 다음 목록을 `3.`으로 시작하면 화면에서도 번호가 3부터 이어진다.

````md
1. 도구 모음에서 **보기**를 클릭해요.
2. **표시**에 마우스를 올려요.

:::success
목록이 옆으로 펼쳐져요.
:::

3. **파일 확장명**을 클릭해요.
````

틀린 예(빌드 오류):

````md
1. 도구 모음에서 **보기**를 클릭해요.
   :::success
   목록이 펼쳐져요.
   :::
````

더 좋은 방법은 견본처럼 **단계를 `###` 제목으로 나누는 것**이다. 단계 안의 클릭 순서만 번호 목록으로 쓰고, 성공 상자는 목록 뒤에 둔다. 그러면 들여쓰기 문제가 생기지 않는다.

### 1.4 문체

- **해요체**로 쓴다. 한 문장은 짧게(대략 40자 안팎, 절은 둘까지). 한 문장에 한 가지 일만 시킨다.
- **왜 → 어떻게.** 단계 앞에 그 단계를 하는 이유를 한두 문장으로 적는다(견본 5단계 "이름부터 저장하는 이유").
- **비유 → 정확한 정의 → 실무 맥락.** 비유 뒤에 반드시 정확한 정의를 둔다. 장난감 예제와 실무 방식이 다르면 `:::info 실무에서는`으로 구분한다.
- 번역투·전문 용어 남발 금지. 처음 나오는 용어는 4장 규칙대로 정의한다.
- 학습자를 탓하지 않는다("잘못했어요" 대신 "이런 경우예요").

표기 규칙:

| 대상 | 표기 | 예 |
|---|---|---|
| 메뉴 경로 | 화면 글자 그대로 굵게, 화살표 `→` | `**보기 → 표시 → 파일 확장명**` |
| 키 | 백틱, 키 이름은 영어, 조합은 공백 있는 `+` | `` `Ctrl + S` ``, `` `Win + E` ``, `` `Enter` ``, `` `한/영` `` |
| 화면 위치 | 창·영역 + 방향 + 모양 | "창 왼쪽 위 **파일** 메뉴", "도구 모음 맨 왼쪽의 **새로 만들기**(⊕ 모양)", "작업 표시줄 오른쪽 아래" |
| 경로 | Windows 전체 경로, 백틱 | `` `C:\dev\my-creator-site\css\style.css` `` |
| 입력할 값 | 백틱. 따옴표까지 입력해야 하면 "따옴표까지 그대로" | 파일 이름 칸에 따옴표까지 그대로 `"hello.html"` |
| 버전에 민감한 화면·메뉴 | 작성 기준일 + 다를 수 있다는 안내 | "Windows 11 기준이에요(작성 기준일 2026-11). 버전에 따라 이름이 조금 다를 수 있어요." |
| 도구 버전 | external-facts.md 0.3 고정표의 값 + `--version` 확인 + 예상 출력 | 3.2절 참고 |

- **Windows 화면 문구**는 한국어 UI 글자를 그대로 쓴다. 정확한 한국어 문구를 공식 출처로 확인하지 못했으면 **위치로 묘사**하고 "(버전에 따라 이름이 조금 다를 수 있어요)"를 붙인다. 확인하지 못한 문구를 확인한 것처럼 쓰지 않는다.
- 존재하지 않는 API·옵션·메뉴를 쓰지 않는다. 버전·명령·URL은 `docs/research/external-facts.md`에서 인용한다. 거기 없는 값이 필요하면 그 문서를 **먼저** 고치고(출처·확인일 포함) 인용한다.

### 1.5 Markdown 함정 (빌드는 통과하지만 화면이 깨지는 것)

**굵게 + 한글 조사.** 닫는 `**` 바로 앞이 문장부호(`)` `]` `` ` `` `!` `.` `"` `⋯` 등)이고 바로 뒤가 한글이면 굵게가 풀리지 않고 `**`가 글자로 보인다. 여는 `**` 바로 뒤가 문장부호이고 바로 앞이 한글이어도 같다. 이 엔진(marked, CommonMark 규칙)에서 실제로 확인한 결과다.

| 원문 | 결과 |
|---|---|
| `**확장자**는` | 굵게 됨 |
| `**보기 → 표시 → 파일 확장명**을` | 굵게 됨 |
| `**확장자(extension)**는` | **깨짐** (`)` 뒤에 한글) |
| `**[[브라우저]]**는` | **깨짐** (`]` 뒤에 한글) |
| `` **`C:\dev`**를 `` | **깨짐** (`` ` `` 뒤에 한글) |
| `**[[브라우저]]**(browser)는` | 굵게 됨 (닫는 `**` 뒤가 문장부호) |
| `**확장자**(extension)는` | 굵게 됨 |
| `**안녕하세요!** 와` | 굵게 됨 (닫는 `**` 뒤가 빈칸) |

고치는 법: 굵게를 **글자로 끝내거나**, 괄호·코드는 굵게 **밖으로** 빼거나, 닫는 `**` 뒤에 빈칸이나 문장부호를 둔다. 코드(`` ` ``)는 굵게 하지 않는다. 다 쓴 뒤에는 6.3절의 `check-bold.mjs`로 반드시 확인한다.

**본문 속 HTML은 항상 글자로 보인다.** 렌더러가 원본 HTML을 모두 escape한다. `<kbd>`, `<br>`, `<details>` 같은 태그는 동작하지 않고 꺾쇠까지 그대로 보인다. 본문에서 태그를 말할 때는 백틱으로 감싸고(`` `<h1>` ``), HTML 예제는 ` ```html ` 코드 블록에 넣는다.

**이미지는 쓸 수 없다**(`E_IMAGE_UNSUPPORTED`). 교재는 인터넷 없이 여는 파일 하나라서 외부 요청이 0건이어야 한다. 대신:

- 화면 위치는 글로 묘사한다("창 위쪽의 긴 칸(**주소 표시줄**)에서 글자 오른쪽의 빈 곳").
- 흐름·구조는 ` ```text ` 그림으로 그린다. **휴대폰(360px)에서 가로 스크롤 없이 보이도록 한 줄을 32칸 이하**로 맞춘다(한글 1자 = 2칸). 견본의 "주소 입력 → 서버 → 브라우저" 그림과 경로 분해 그림을 참고한다.
- 표는 3열 이하, 칸은 짧게. 코드가 긴 설명(`<html lang="ko">` ~ `</html>` 같은 것)은 표 대신 목록으로 쓴다(표는 좁은 화면에서 칸이 찌그러진다).

**링크.** 쓸 수 있는 대상은 다음뿐이다. 그 밖은 `E_LINK_UNSUPPORTED`, 없는 화면은 `E_LINK_UNKNOWN`.

| 대상 | 형식 | 예 |
|---|---|---|
| Day | `#/day/<day id>` | `[P1 Day 25](#/day/p1-d25)` (앞 Day 복습 링크로 쓴다) |
| 부록 페이지 | `#/page/<page id>` | `[용어 사전](#/page/glossary)`, `[문제 해결 모음](#/page/troubleshooting)` |

### 1.6 분량과 시간

- `curriculum.json`의 `validation.minDayChars`는 **4000자**다. 이보다 짧으면 `E_TOO_SHORT`. 이 값은 뼈대만 있는 미완성 Day를 막기 위한 하한이고, 실제 Day는 보통 12,000~30,000자다(견본 Day 1은 약 3만 자, 코드 포함).
- 예상 시간 = 개념 이해 + 따라하기 단계 시간의 합 + 과제 + 정리. `minutes`는 60~120 사이 정수이고, 본문의 `**예상 시간**`과 같아야 한다. 120분을 넘으면 내용을 다음 Day로 넘기거나 개요 담당에게 Day 분할을 요청한다.

## 2. 막힘 방지 규칙

### 2.1 필수 규칙 (a)~(g)

**(a) 시작 상태.** `🎯 오늘의 목표` 끝에 `:::path 📂 시작 상태`를 둔다. 어제 끝난 시점에 있어야 할 파일·폴더를 **전체 경로**로 적는다. 열려 있어야 할 프로그램(예: Live Preview 실행 중, 서버 실행 중)과 설치되어 있어야 할 도구(+ 확인 명령)도 적는다. 개요(`_outline.md`)의 "시작 상태"와 앞 Day의 "오늘 끝 상태 전체 코드"가 서로 같아야 한다. 프로젝트의 첫 Day는 "미리 있어야 할 것이 없다"고 명시한다(견본).

````md
:::path 📂 시작 상태
어제(Day 8)까지 만든 파일이 이렇게 있어야 해요. 없거나 다르면 [Day 8](#/day/p1-d08)의 "오늘 끝 상태 전체 코드"로 맞춰 주세요.

- `C:\dev\my-creator-site\index.html`
- `C:\dev\my-creator-site\about.html`
- VS Code에서 `C:\dev\my-creator-site` 폴더가 열려 있어요.
:::
````

**(b) 단계마다 어디서 / 무엇을 / 결과.** 따라하기의 **모든** 단계는 다음 세 가지를 갖는다.

- `**어디서:**` 앱 이름 + 메뉴·창 위치 + 전체 경로(터미널이면 현재 위치 `C:\...`).
- `**무엇을:**` 정확한 입력·클릭·명령. 여러 동작이면 번호 목록. 입력값은 백틱으로, 복사해 바로 쓸 수 있게.
- `:::success` 결과. 화면에서 **눈으로 확인할 수 있는 것**(글자, 아이콘, 주소, 출력)을 적는다. "잘 되면"처럼 확인할 수 없는 말은 쓰지 않는다.

성공 상자와 다를 때 갈 곳을 함께 적는다(예: "관리자 권한을 묻는 창이 떴다면 아래 🧯 자주 막히는 곳의 '…' 항목을 보세요"). 실패하기 쉬운 단계는 **실패를 일찍 발견하도록 순서를 설계**한다(견본 5단계: 내용을 쓰기 전에 빈 파일을 먼저 저장해 `.txt` 문제를 바로 찾는다).

**(c) 배우지 않은 것을 쓰지 않는다.** 앞 Day에서 배우지 않은 개념·문법·도구를 쓰지 않는다. 기준은 개요의 "이미 배운 것"이다. 꼭 미리 써야 하면(예: Day 1의 `<meta charset="utf-8">`) 한 줄로 뜻을 알려 주고 "Day N에서 자세히 배워요"라고 적는다. 그날 설치하지 않은 도구, 아직 가입하지 않은 서비스에 의존하는 단계를 두지 않는다.

**(d) 오늘 끝 상태 전체 코드.** `## ✅ 정답`의 마지막 블록은 `:::answer 오늘 끝 상태 전체 코드`다. 과제 정답과 별도로, 오늘 따라하기와 과제를 모두 끝낸 상태를 담는다.

- 맨 앞에 폴더 트리(` ```text `)를 둔다.
- 오늘 **바뀐 파일**은 200줄 이하면 **파일 전체**를 `📄 전체 경로` 캡션과 함께 싣는다.
- 200줄을 넘으면 바뀐 **함수·블록 전체**와 **정확한 삽입 위치**("`/* ---------- 5. 반응형 ---------- */` 주석 바로 위", "`</main>` 줄 바로 앞")를 싣는다. 블록 중간을 `...`로 줄이지 않는다.
- 목적: 막힌 학습자가 이 코드를 그대로 붙여 넣으면 다음 Day를 시작할 수 있어야 한다. 이 블록 첫 문장에 그 사용법을 적는다.

**(e) 오류 메시지는 원문 그대로.** 도구가 내는 오류(PowerShell, npm, tsc, dotnet, rustc, 브라우저 콘솔)는 **영어 원문을 그대로** ` ```text ` 블록에 싣고, 바로 아래에서 한국어로 풀이한다(무슨 뜻인지 → 왜 났는지 → 어떻게 고치는지). 실제로 실행해서 얻은 원문만 싣는다. 경로·줄 번호처럼 사람마다 다른 부분은 그렇다고 적는다. 한국어 Windows가 번역해서 보여 주는 대화 상자는 화면에 보이는 한국어 문구와 영어 원문을 함께 적고, 정확한 문구를 확인하지 못했으면 "(문구는 버전에 따라 조금 다를 수 있어요)"를 붙인다. 원문이 있어야 학습자가 검색할 수 있다.

**(f) 명령 바로 아래에 예상 출력.** 명령어 블록 바로 아래에 "예상 출력:"과 ` ```text ` 블록을 둔다. 버전·시간처럼 달라지는 값은 "(숫자는 달라도 돼요)"라고 적는다. 출력이 없는 명령이면 "아무것도 나오지 않고 다음 줄에 `PS C:\...>`가 다시 보이면 성공이에요"라고 적는다. 3.2절 참고.

**(g) 다음 Day 예고.** Day의 맨 마지막 줄에 한 줄 예고를 둔다. 형식:

```md
➡️ **다음 Day 예고:** [Day 2 · 개발 도구 설치](#/day/p1-d02)에서는 …을 해요.
```

프로젝트의 마지막 Day는 다음 프로젝트가 열린다는 사실과 그 프로젝트의 개요 링크(`#/project/<id>`)로 끝낸다.

### 2.2 추가 규칙

- **한 단계 = 한 앱·한 화면.** 단계 제목에 걸리는 시간을 적는다(`### 3단계 · C:\dev 폴더 만들기 (5분)`).
- **복사와 타이핑.** 직접 타이핑을 권하되 코드 블록 오른쪽 위 **복사** 버튼을 써도 된다고 알려 준다. 그래서 모든 코드 블록은 **복사해서 그대로 붙여 넣으면 동작**해야 한다(블록 안에 `...`, 설명 글, 프롬프트를 넣지 않는다).
- **Windows 함정은 처음 나올 때 안내한다.** 견본 Day 1이 다룬 것: 확장자 숨김, `hello.html.txt`, `한/영` 입력 상태, `₩` 키 = `\`, 노트북 `Fn` 키, OneDrive 폴더. 앞으로 다룰 것: PowerShell 실행 정책, Windows PowerShell 5.1의 문법 차이(3.4절), 방화벽 허용 창, 관리자 권한 창, 포트 충돌.
- **경로는 `C:\dev` 아래만.** 작업 폴더는 P1 `C:\dev\my-creator-site`, P2 `C:\dev\streamer-hub`, P3 `C:\dev\viewer-arena`, SP `C:\dev\image-donation`. 연습용 폴더도 `C:\dev` 안에 만든다(Day 1의 `C:\dev\hello`). 바탕 화면·문서·OneDrive·한글·공백이 들어간 경로를 쓰지 않는다.
- **이름은 레퍼런스와 같게.** 파일·폴더·클래스·id·변수·데이터 형식 이름은 레퍼런스(부록 D)와 같게 쓴다. 다르면 뒤 Day의 코드가 맞지 않는다.
- **외부 서비스 대기.** 가입·승인·메일 인증처럼 기다려야 하는 단계는 기다리는 동안 계속할 수 있는 길(테스트 모드, 로컬 실행)을 함께 둔다.
- **네트워크.** 인터넷이 필요한 단계(설치, 가입, 배포)는 그렇다고 적는다. 정답 확인은 네트워크 없이 되게 한다.
- **보안 습관.** 실행 정책을 `Unrestricted`/`Bypass`로 바꾸게 하지 않는다(공식 해결은 `RemoteSigned -Scope CurrentUser`). 방화벽·백신을 끄게 하지 않는다. 비밀 값(Client Secret, 비밀번호, 토큰)은 코드·커밋에 넣지 않는다. 7.2절 참고.

### 2.3 프로젝트별 고정 규칙

- **P1 시간 계산.** P1의 날짜·카운트다운 코드(Day 16 인사말, Day 26 카운트다운, Day 27 오버레이)는 **컴퓨터 시계가 한국 시간**이라고 가정한다. 본문에 "컴퓨터 시계 기준이에요. 한국에서 쓰는 컴퓨터면 한국 시간으로 계산돼요"를 적고, 시간대는 P2 Day 29(UTC vs 한국 시간)에서 제대로 배운다고 예고한다. P1에서 시간대 라이브러리나 `Intl` 시간대 옵션을 쓰지 않는다.
- **P1 영상 ID.** YouTube 영상 ID(`data/videos.json`의 `youtubeId`, `iframe` 주소)는 **예시 값**이다. 본문에 "내 YouTube 영상 주소 `watch?v=` 뒤의 11글자로 바꿔요"를 적는다. `file://`로 열면 YouTube 임베드가 재생되지 않을 수 있다고 함께 적는다.
- **P1 `fetch`와 `file://`.** `fetch`로 JSON을 읽는 Day(25 이후)는 파일 더블클릭(`file://`)으로는 동작하지 않으므로 VS Code **Live Preview**로 열게 한다(레퍼런스 README 기준). 그 전 Day는 더블클릭으로 열어도 동작해야 한다.
- **터미널.** 터미널(PowerShell)은 P2 Day 2에서 제대로 배운다. 그 전에 명령을 쳐야 하는 Day(예: P1의 Git Day)는 그 Day 안에서 필요한 최소한(창을 여는 위치, 현재 위치 확인법, 명령 붙여 넣기)을 단계로 안내한다. PowerShell 명령이 나오는 모든 Day는 3.4절 규칙을 따른다.
- **Docker를 쓰는 Day(P3·SP).** 모든 Docker Day에 **Docker 없는 경로**를 함께 둔다(PostgreSQL 직접 설치: `winget install PostgreSQL.PostgreSQL.18` 또는 EDB 설치 프로그램, 서버는 `dotnet run`/`cargo run`으로 직접 실행). Docker Desktop을 설치하는 Day는 **Windows 에디션·버전 확인으로 시작**한다: `Win + R` → `winver`로 버전·빌드(23H2, 빌드 22631 이상), **설정 → 시스템 → 정보**의 에디션(Home/Pro), 또는 PowerShell `(Get-CimInstance Win32_OperatingSystem).Caption`. Home이면 "Docker Desktop이 동작하지 않을 수 있으니 안 되면 Docker 없는 경로로 진행해요"를 `:::warn`으로 두되, **지원된다/안 된다고 단정하지 않는다**(external-facts.md 9절). 요구 사항(WSL 2, BIOS 가상화, RAM 8 GB)을 사전 점검 체크리스트에 넣는다. 이미지는 `postgres:18`, 볼륨은 `/var/lib/postgresql`에 마운트한다(`/var/lib/postgresql/data` 아님).
- **SP 돈 흐름.** SP는 결제를 다루지 않는다. 운영자(학습자)는 돈을 받지 않고, 치즈 후원은 치지직이 스트리머에게 직접 정산한다. 치지직 API 승인이 없어도 **테스트 모드**(가짜 후원 이벤트)로 전체 흐름을 실습할 수 있어야 한다. 실연동은 선택 단계로 둔다.

## 3. 코드 블록 규칙

### 3.1 언어와 캡션

- 모든 코드 블록(` ``` `)에는 언어를 적는다(`E_FENCE_LANG`). 들여쓰기로 만든 코드 블록은 금지다. 허용 언어(`textbook/lib/markdown.mjs`의 `LANG_MAP`, 이 밖은 `E_FENCE_LANG_UNKNOWN`):
  `html` `xml` `css` `js` `javascript` `jsx` `ts` `typescript` `tsx` `json` `powershell` `csharp` `cs` `sql` `rust` `toml` `dockerfile` `yaml` `yml` `http` `diff` `md` `markdown` `text` `plaintext` `bash`
- 고르는 법: 학습자가 Windows에서 치는 명령은 `powershell`. 예상 출력·오류 원문·폴더 트리·그림은 `text`. `.csproj`는 `xml`, `Cargo.toml`은 `toml`, `.http` 파일은 `http`, Compose 파일은 `yaml`. `bash`는 **리눅스 컨테이너 안에서 실행하는 명령**에만 쓴다(학습자 PC 명령에 쓰지 않는다).
- **파일 내용을 담은 블록**은 바로 윗줄에 캡션을 둔다. `📄` 다음에 빈칸 하나, 그리고 Windows 전체 경로. 캡션 줄과 코드 블록 사이에 빈 줄을 두지 않는다. 캡션은 코드 상자 머리에 표시된다.

  ````md
  📄 C:\dev\my-creator-site\css\style.css
  ```css
  body {
    margin: 0;
  }
  ```
  ````

- 파일의 일부만 실을 때는 캡션 끝에 `(일부)`를 붙이고, 블록 바로 위 문장에 **정확한 위치**를 적는다("`</main>` 줄 바로 앞에 붙여 넣어요").
- 번호 목록 안의 코드 블록은 캡션과 코드 블록을 같은 칸만큼 들여 쓴다(엔진이 지원한다). 다만 견본처럼 단계를 `###`으로 나누고 코드 블록은 줄 맨 앞에 두는 편이 안전하다.
- 들여쓰기: HTML·CSS·JS·TS·JSON은 스페이스 2칸, C#·Rust는 4칸(레퍼런스·포매터 기본값과 같게). 탭 문자는 쓰지 않는다.
- 한 줄은 80자 이하로 쓴다. 휴대폰에서는 코드 상자 안에서 가로로 스크롤된다(페이지 전체는 밀리지 않는다).
- 블록 안에 `...`, `(생략)`, "여기에 기존 코드" 같은 글을 넣지 않는다. 복사해서 붙여 넣으면 오류가 난다. 줄여야 하면 함수·블록 단위로 통째로 보여 준다.
- 변경점 강조에 `diff`를 쓸 수 있지만, 복사해서 쓸 수 없으므로 반드시 바뀐 뒤의 코드 블록을 함께 싣는다.

### 3.2 명령과 예상 출력

- 명령 블록에는 **명령만** 넣는다. `PS C:\dev>` 같은 프롬프트, 설명 글, 출력은 넣지 않는다(복사 버튼이 통째로 복사한다).
- 한 줄에 명령 하나. 블록 위 `**어디서:**`에 현재 위치를 적는다. 위치가 중요한 명령 묶음은 첫 줄을 전체 경로 `cd`로 시작한다.
- 바로 아래에 예상 출력(규칙 f). 버전 확인 예:

````md
**어디서:** PowerShell (위치는 어디든 괜찮아요)

```powershell
node --version
```

예상 출력(숫자는 달라도 돼요. 작성 기준일 2026-11의 LTS는 v26.13.0이에요):

```text
v26.13.0
```
````

### 3.3 Windows 줄바꿈 (CRLF)

- 교재 원본(`.md`)은 LF·CRLF 모두 괜찮다. 빌드가 통일한다.
- 학습자 PC의 메모장·VS Code는 Windows 줄바꿈(CRLF)으로 저장한다. HTML·CSS·JS·TS·JSON·C#·Rust·SQL에는 아무 문제가 없다. 이 차이로 학습자를 걱정시키지 않는다. VS Code 오른쪽 아래 상태 표시줄의 `CRLF` 글자를 설명할 때는 "Windows 방식 줄바꿈이라는 뜻이고 그대로 두면 돼요"라고 적는다.
- Git for Windows는 기본값(Checkout Windows-style, commit Unix-style)을 유지한다(external-facts.md 3절). 이 설정에서는 `git add` 때 `warning: in the working copy of '...', LF will be replaced by CRLF the next time Git touches it` 같은 경고가 나올 수 있다. 이 문장을 실제로 재현해 원문 그대로 싣고 "무시해도 되는 안내"라고 풀이한다.
- **리눅스에서 실행되는 셸 스크립트(`.sh`)는 LF여야 한다.** CRLF면 컨테이너 안에서 실행이 실패한다. 가능하면 교재에서 셸 스크립트를 쓰지 않는다. 꼭 필요하면 저장소에 `.gitattributes`(`*.sh text eol=lf`)를 두고, VS Code 상태 표시줄에서 `CRLF`를 눌러 `LF`로 바꾸는 단계를 넣고, CRLF일 때 나는 오류를 실제로 재현해 원문 그대로 "자주 막히는 곳"에 싣는다.

### 3.4 PowerShell 규칙

Windows 11의 기본 PowerShell은 **Windows PowerShell 5.1**(`powershell.exe`)이다. 교재의 명령은 5.1에서 동작해야 한다.

- `&&`, `||`를 쓰지 않는다. 5.1에서는 오류다(PowerShell 7부터 지원). 명령을 한 줄에 하나씩 쓴다.
- `curl`은 5.1에서 `Invoke-WebRequest`의 별칭이라 옵션이 다르다. HTTP 요청 예제는 `curl.exe`로 쓰거나 VS Code REST Client의 `.http` 파일을 쓴다.
- 환경 변수는 `$env:ASPNETCORE_ENVIRONMENT = "Development"` 형식(`export`, `set` 아님). 이 값은 그 창에서만 유지된다고 적는다.
- 파일 삭제는 `Remove-Item -Recurse -Force <경로>`(`rm -rf` 아님). 지우는 명령에는 `:::warn`을 붙이고 경로를 전체 경로로 쓴다.
- 줄 이어 쓰기(`` ` ``)를 쓰지 않는다. 긴 명령도 한 줄로 쓴다.
- 공백이 있는 경로의 프로그램은 `& "C:\Program Files\...\psql.exe"`처럼 `&`와 따옴표로 실행한다.
- **실행 정책.** Node를 설치한 Day에 `npm --version`을 실행해 보는 단계를 넣는다. `npm.ps1` … `UnauthorizedAccess` 오류가 나면 `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser` 한 줄을 안내한다(관리자 권한 불필요, 공식 예시). `npm.cmd`로 우회하는 방법은 "추정"으로 표시한 보조 안내로만 둔다(external-facts.md 1절).

## 4. 용어 규칙

### 4.1 본문에서

- 용어가 **처음 등장하는 Day**(개요가 배정한 Day)에서 한 번, 이렇게 쓴다: `**[[용어]]**(원어)` + 조사 + **한 줄 정의**를 같은 문장에.

  ```md
  **[[브라우저]]**(browser)는 웹페이지 파일을 받아 와서 사람이 볼 수 있는 화면으로 그려 주는 프로그램이에요.
  **[[HTML]]**(에이치티엠엘)은 웹페이지의 내용과 구조를 적는 언어예요.
  ```

  닫는 `**` 바로 뒤에 괄호(원어나 읽는 법)를 두는 이 형식은 1.5절의 "굵게 + 조사" 함정을 피한다. 영어 약어는 업계 표기 그대로 쓰고 괄호에 한국어 읽기를 적는다(`**[[URL]]**(유알엘)`).
- 같은 Day에서 두 번째부터는 평문으로 쓴다. 앞 Day에서 배운 용어를 다시 짚어 줄 때는 굵게 없이 `[[용어]]`로 사전 링크만 걸 수 있다.
- `[[용어]]`는 용어 사전 항목 제목(`### 용어`)과 **대소문자·띄어쓰기까지 똑같아야** 한다(`E_TERM_UNKNOWN`). 코드 안의 `[[...]]`는 용어로 처리되지 않는다.
- 정의하지 않은 용어가 본문에 나오지 않게 한다. 배정되지 않은 용어가 꼭 필요하면 쉬운 말로 풀어 쓰거나("링크(누르면 다른 페이지로 넘어가는 연결)"), 용어로 추가한다(4.3절).

### 4.2 용어 사전 항목 형식

```md
### 확장자
- 처음 등장: [P1 Day 1](#/day/p1-d01)

파일 이름에서 마지막 점(`.`) 뒤에 붙은 글자예요. (정의 2~4문장)
```

- 제목은 `### 용어`(화면에 보일 표기 그대로). 첫 줄은 `- 처음 등장: [P1 Day N](#/day/p1-dNN)`. 빈 줄 뒤에 **2~4문장** 정의(해요체).
- 정의는 그 자체로 이해되게 쓴다(비유만 쓰지 않는다). 예시 하나를 넣으면 좋다. 정의 안에서 다른 용어를 쓰면 그 용어도 사전에 있어야 한다.
- 파일의 첫 `###` 앞 글과 `#`·`##` 줄은 무시된다(파일 제목·묶음 구분으로 쓴다). 항목 순서는 빌드가 한글 사전순으로 정렬한다.
- 같은 용어가 두 번 정의되면 오류다(대소문자·공백 무시, `E_TERM_DUPLICATE`). **한 용어는 정확히 한 Day에 배정**한다.

### 4.3 파일

- 프로젝트 전체 용어: `textbook/content/glossary/<프로젝트 id>.md` (개요 담당 Task가 쓴다. P1은 `p1.md`).
- 개요에 없던 용어가 배치 작성 중에 필요하면 `textbook/content/glossary/<batch>-extra.md`에 추가하고 보고한다(예: `p1-days-11-20-extra.md`).

## 5. 문제 해결 항목 형식

문제 해결 모음 페이지(`#/page/troubleshooting`)는 `textbook/content/troubleshooting/*.md`를 합쳐 만든다. 파일 이름의 첫 `-` 앞(접두어)이 프로젝트 id여야 해당 프로젝트 제목 아래에 모인다(`p1.md`, `p1-days-02-10.md` → P1).

```md
### <증상: 오류 메시지 원문, 또는 학습자가 보는 현상 한 줄>
- 관련: [P1 Day 1](#/day/p1-d01)

**원인:** 왜 이런 일이 생기는지 2~4문장. 오류 원문이 있으면 영어 원문을 그대로 인용하고 한국어로 풀이해요.

**해결:**

1. 어디서 무엇을 하는지 (단계마다 위치와 정확한 입력)
2. …
3. 해결됐는지 확인하는 방법 (화면에 무엇이 보이면 되는지)
```

- `**원인:**` 뒤에 바로 문장을 이어 쓴다(`**원인**` 다음 줄에 쓰면 한 문단으로 붙어 보인다). `**해결:**` 다음에는 빈 줄을 두고 번호 목록을 쓴다.
- **제목 = 증상.** 오류 메시지가 있으면 핵심 부분을 **원문 그대로**(영어 원문 + 괄호 안 한국어 요지, 또는 한국어 UI 문구 + 괄호 안 영어 원문) 쓴다. 학습자는 화면의 글자로 검색한다. 오류가 없으면 학습자가 보는 현상을 학습자의 말로 쓴다("고쳤는데 브라우저 화면이 그대로예요").
- 원인이 여럿이면 ①, ②로 나누고, 해결 단계도 어느 원인용인지 적는다.
- 해결 단계는 Day 따라하기와 같은 수준으로 쓴다(어디서/무엇을/결과). 마지막 단계는 해결 확인이다.
- 한 Day의 `🧯 자주 막히는 곳`에는 그날 가장 흔한 3~6개를 **짧은 형식**(`### 증상` / `**원인:**` 한 문단 / `**해결:**` 단계)으로 다시 싣고, 첫 줄에 [문제 해결 모음](#/page/troubleshooting) 링크를 둔다. 긴 설명과 드문 경우는 문제 해결 파일에만 둔다.
- 파일: 배치마다 `textbook/content/troubleshooting/<batch>.md`.

## 6. 실행 검증과 기록

### 6.1 원칙

- 학습자가 입력하거나 복사하는 **모든 코드 블록**은 이 환경에서 **본문에 적힌 그대로** 실행해 확인한다. 레퍼런스가 아니라 Day 파일의 블록을 꺼내 검증해야 한다(학습자가 보는 것이 그것이다).
- "오늘 끝 상태 전체 코드"는 스크래치 폴더에 그대로 재구성해 실행한다.
- Windows에서만 할 수 있는 절차(설치 마법사 화면, 파일 탐색기·메모장 메뉴, 방화벽 창, 실행 정책)는 실행할 수 없으므로 **공식 문서 대조**로 기록하고 출처 URL을 남긴다. 확인하지 못한 문구는 본문에 "(버전에 따라 … 다를 수 있어요)"를 붙인다.
- 검증하지 못한 것은 검증하지 못했다고 적는다. 통과한 척하지 않는다.

### 6.2 배치 검증 순서

1. 스크래치 폴더를 만든다: `<스크래치>/<batch>/`(저장소 밖).
2. Day 파일에서 📄 캡션이 붙은 블록을 **원문 그대로** 꺼내 캡션 경로대로 저장한다(손으로 다시 치지 않는다). 아래 `extract-blocks.mjs`를 스크래치 폴더에 저장하고 저장소 루트에서 실행하면 블록마다 `<출력 폴더>/<줄 번호>/<C:\dev 아래 경로>`로 저장된다. 끝 상태는 "오늘 끝 상태 전체 코드" 블록들로 한 폴더를 만들어 확인하고, `(일부)` 블록은 적힌 위치에 직접 끼워 넣어 재구성한다.

   ```js
   // Day 파일에서 📄 캡션이 붙은 코드 블록을 원문 그대로 꺼내 <출력 폴더>/<줄 번호>/<C:\dev 아래 경로>에 저장한다.
   //   node <스크래치>/extract-blocks.mjs textbook/content/p1/day-02.md <스크래치>/p1-d02
   import { mkdirSync, readFileSync, writeFileSync } from 'node:fs';
   import path from 'node:path';
   const [dayFile, outDir] = process.argv.slice(2);
   const lines = readFileSync(dayFile, 'utf8').replace(/\r\n?/g, '\n').split('\n');
   for (let i = 0; i < lines.length - 1; i++) {
     const caption = /^\s*📄\s+(.+?)\s*$/.exec(lines[i]);
     const open = /^(\s*)(`{3,}|~{3,})\S/.exec(lines[i + 1]);
     if (!caption || !open) continue;
     const [, indent, fence] = open;
     const body = [];
     let j = i + 2;
     while (j < lines.length && lines[j].trim() !== fence) body.push(lines[j++].slice(indent.length));
     const rel = caption[1].replace(/\s*\(일부\)$/, '').replace(/^C:\\dev\\/i, '').split('\\');
     const file = path.join(outDir, String(i + 1), ...rel);
     mkdirSync(path.dirname(file), { recursive: true });
     writeFileSync(file, body.join('\n') + '\n');
     console.log(`줄 ${i + 1}: ${caption[1]} → ${file}`);
   }
   ```

3. 6.4절의 프로젝트별 방법으로 실행한다.
4. 결과를 `docs/verification/<batch>.md` 표에 적는다(6.5절).
5. 교재 검사: 저장소 루트에서

   ```bash
   cd textbook
   npm run check -- --only p1-d02,p1-d03
   ```

   → `검사 통과`가 나와야 한다(오류 0). 그리고 6.3절의 굵게 검사를 돌린다.

### 6.3 굵게 검사 스크립트 (모든 프로젝트)

빌드 검사는 1.5절의 "굵게 + 조사" 함정을 잡지 못한다. 아래 파일을 스크래치 폴더에 `check-bold.mjs`로 저장하고 **저장소 루트에서** 실행한다. `굵게가 풀리지 않은 곳 없음`이 나와야 한다.

```js
// 굵게(**)·기울임(__)이 풀리지 않고 글자로 남은 줄을 찾는다. 저장소 루트에서 실행한다.
//   node <스크래치>/check-bold.mjs textbook/content/p1/day-02.md textbook/content/glossary/p1.md
import { readFileSync } from 'node:fs';
import path from 'node:path';
import { pathToFileURL } from 'node:url';
const { renderMarkdown } = await import(pathToFileURL(path.resolve('textbook/lib/markdown.mjs')).href);
const anyTerm = { get: (t) => t }; // 용어·링크 검사는 npm run check 가 하므로 여기서는 모두 통과시킨다
const anyRoute = { has: () => true };
let found = 0;
for (const file of process.argv.slice(2)) {
  const { html } = renderMarkdown(readFileSync(file, 'utf8'), { idPrefix: 'x', terms: anyTerm, routes: anyRoute });
  const prose = html.replace(/<pre[\s\S]*?<\/pre>|<code>[\s\S]*?<\/code>/g, '');
  for (const line of prose.split('\n')) {
    if (/\*\*|(?<![\w*])__\S/.test(line)) {
      found++;
      console.log(`${file}: ${line.replace(/<[^>]+>/g, '').trim()}`);
    }
  }
}
console.log(found ? `굵게가 풀리지 않은 곳 ${found}개` : '굵게가 풀리지 않은 곳 없음');
process.exitCode = found ? 1 : 0;
```

P1 검증 스크립트(견본 Day 1 검증에 실제로 쓴 것). 스크래치 폴더에 `verify-p1.mjs`로 저장하고 **저장소 루트에서** 실행한다. 끝 상태 확인 항목이 더 있으면(버튼을 누른 뒤의 글자, 카드 개수 등) `page.evaluate` 안에 추가한다.

```js
// P1 끝 상태 코드 검증. 저장소 루트에서 실행한다.
//   node <스크래치>/verify-p1.mjs <사이트 폴더> <페이지...>          (정적 서버로 열기: Live Preview와 같은 http 방식)
//   node <스크래치>/verify-p1.mjs --file <사이트 폴더> <페이지...>   (더블클릭과 같은 file:// 방식)
import path from 'node:path';
import { pathToFileURL } from 'node:url';
const helper = (p) => import(pathToFileURL(path.resolve('tests/helpers', p)).href);
const { startStaticServer } = await helper('static-server.mjs');
const { launch, collectConsoleErrors } = await helper('browser.mjs');

const args = process.argv.slice(2);
const useFile = args[0] === '--file';
const [root, ...pages] = useFile ? args.slice(1) : args;
const server = useFile ? null : await startStaticServer(root);
const urlOf = (p) => (useFile ? pathToFileURL(path.resolve(root, p)).href : server.url + p);

const browser = await launch();
let failed = 0;
for (const width of [1280, 360]) {
  const page = await browser.newPage({ viewport: { width, height: 800 }, locale: 'ko-KR', timezoneId: 'Asia/Seoul' });
  const errors = collectConsoleErrors(page);
  for (const p of pages) {
    await page.goto(urlOf(p));
    const r = await page.evaluate(() => ({
      title: document.title,
      h1: document.querySelector('h1')?.textContent.trim() ?? null,
      horizontalScroll: document.documentElement.scrollWidth > document.documentElement.clientWidth,
    }));
    if (r.horizontalScroll) failed++;
    console.log(`${width}px ${p} ${JSON.stringify(r)}`);
  }
  if (errors.length) failed++;
  console.log(`${width}px 콘솔 오류 ${errors.length}개 ${errors.join(' | ')}`);
  await page.close();
}
await browser.close();
await server?.close();
console.log(failed ? `실패 ${failed}건` : '통과');
process.exitCode = failed ? 1 : 0;
```

## 부록 C. curriculum.json

`textbook/content/curriculum.json`이 프로젝트·Day 메타·해금 조건의 단일 원천이다.

- 최상위: `version: 1`, `title`, `writtenAt: "2026-11"`, `validation.minDayChars: 4000`, `projects`, `pages`.
- 프로젝트: `id`(`p1`, `p2`, `p3`, `sp`), `order`, `track`(`p1`·`p2`·`p3` = `main`, `sp` = `special`), `title`, `subtitle`, `folder`(작업 폴더 전체 경로), `stack`, `requires`(`p1` [], `p2` [`p1`], `p3` [`p2`], `sp` [`p2`]), `summary`, `outcome`, `days`.
- Day: `title`(설계서 3장 제목 그대로), `minutes`(60~120 정수), `summary`(한 문장), `keywords`(검색용 낱말 배열). Day 번호와 id는 배열 순서로 정해진다(첫 항목 = `day-01.md` = `<pid>-d01`). **Day를 중간에 끼워 넣거나 지우면 뒤 Day의 id와 파일 이름이 모두 바뀌므로** 개요 담당과 상의 없이 바꾸지 않는다.
- 페이지: 파일 페이지는 `{ "id", "title", "file": "start.md" }`(`content/pages/` 기준), 생성 페이지는 `{ "id": "glossary", "generated": "glossary" }`, `{ "id": "troubleshooting", "generated": "troubleshooting" }`. 잠금이 필요하면 `requires`(예: `roadmap`은 [`p3`]).
- `minDayChars`가 4000인 이유: 섹션 제목·블록만 채운 뼈대 Day(대략 1,000~2,000자)를 빌드에서 막고, 짧지만 완성된 Day(정리·회고 Day 등)는 통과시키는 하한이다. 바꾸려면 이 가이드와 함께 고친다.

## 부록 D. 레퍼런스(완성 코드) 사용법

`reference/<프로젝트>/`는 각 프로젝트의 **검증된 최종 완성본**이고, Day 정답 코드의 원천이다. P1은 `reference/p1-my-creator-site/`(테스트: `node --test tests/reference/p1.test.mjs`).

- **Day 코드는 레퍼런스로 가는 중간 단계다.** 개요(`_outline.md`)의 "오늘 만들/바꿀 파일 — 레퍼런스 대응 파일"을 보고, 레퍼런스 파일에서 오늘 배우는 부분까지를 잘라 쓴다. 마지막 Day의 끝 상태는 레퍼런스와 (글 내용·예시 데이터를 빼면) 같아야 한다.
- **이름을 바꾸지 않는다.** 파일·폴더 이름, 클래스·id, 변수·함수 이름, 데이터 형식(P1: `data/videos.json`의 `{ id, title, category, youtubeId, date }`, `data/schedule.json`의 `{ day, start, title }`, `localStorage` 키 `theme`, 오버레이 주소 값 `?title=…&start=HH:MM`)은 레퍼런스와 같게 쓴다.
- **앞 Day에서는 단순하게.** 레퍼런스의 완성 코드가 아직 배우지 않은 문법을 쓰면(예: `try/catch`는 Day 25), 그 Day에는 배운 문법만으로 같은 동작을 하는 단순한 버전을 쓰고, 그 코드도 6장대로 검증한다. 레퍼런스 주석의 `(Day N)` 표시가 그 기능을 배우는 Day다.
- **레퍼런스 README의 사실을 따른다.** P1: `fetch`가 있는 페이지는 Live Preview로 연다, YouTube ID는 예시다, 시간은 컴퓨터 시계(한국 시간) 기준이다, 외부 라이브러리·CDN·웹폰트를 쓰지 않는다, `og:image`는 배포 주소가 정해진 뒤(Day 28)에 넣는다.
- 레퍼런스에서 틀린 점이나 교재와 맞지 않는 점을 찾으면 Day 쪽에서 몰래 다르게 쓰지 말고, 보고서에 적어 레퍼런스 담당이 고치게 한다.
- P1 Day 1은 레퍼런스를 쓰지 않는다. 연습 폴더 `C:\dev\hello`에서 HTML 파일을 처음 만들어 보는 날이고, 프로젝트 폴더 `C:\dev\my-creator-site`는 개요가 정한 Day부터 쓴다.
