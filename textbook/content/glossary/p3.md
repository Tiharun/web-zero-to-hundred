# P3 용어

P3(시청자 참여 실시간 게임)에서 처음 가르치는 용어예요. 항목 순서는 빌드가 한글 사전순으로 정렬해요.

### Rust
- 처음 등장: [P3 Day 1](#/day/p3-d01)

C++처럼 빠르게 돌아가는 컴파일 언어인데, 메모리를 잘못 쓰는 실수를 컴파일할 때 막아 주는 언어예요. 가비지 컬렉터 없이도 안전하게 메모리를 관리해요. 이 교재에서는 게임 서버와 브라우저에서 돌 WebAssembly를 모두 Rust로 만들어요.

### rustup
- 처음 등장: [P3 Day 1](#/day/p3-d01)

Rust 컴파일러와 도구 묶음(툴체인)을 설치하고 업데이트하는 프로그램이에요. `rustup update`로 새 버전을 받고, `rustup target add`로 다른 컴파일 대상(예: `wasm32-unknown-unknown`)을 더해요. Windows에서는 `rustup-init.exe`로 처음 설치해요.

### Cargo
- 처음 등장: [P3 Day 1](#/day/p3-d01)

Rust의 빌드 도구이자 패키지 관리자예요. `cargo new`로 프로젝트를 만들고, `cargo build`로 컴파일하고, `cargo run`으로 실행하고, `cargo test`로 테스트를 돌려요. 필요한 라이브러리(크레이트)는 `Cargo.toml`에 적으면 Cargo가 내려받아요.

### 링커
- 처음 등장: [P3 Day 1](#/day/p3-d01)

컴파일러가 만든 조각 파일들과 운영체제 라이브러리를 이어 붙여 실행 파일(`.exe`) 하나로 만드는 프로그램이에요. Windows의 Rust는 Microsoft의 링커 `link.exe`를 써요. 링커가 없으면 ``linker `link.exe` not found`` 오류가 나요.

### MSVC 빌드 도구
- 처음 등장: [P3 Day 1](#/day/p3-d01)

Microsoft의 C/C++ 컴파일러·링커와 Windows SDK 묶음이에요. Windows용 Rust(`x86_64-pc-windows-msvc`)는 이 도구의 링커와 Windows 라이브러리를 빌려 실행 파일을 만들어요. `rustup-init.exe`가 "Rust Visual C++ prerequisites" 화면에서 Visual Studio 설치 프로그램으로 설치를 도와줘요.

### rust-analyzer
- 처음 등장: [P3 Day 1](#/day/p3-d01)

VS Code 같은 편집기에서 Rust 코드를 이해해 자동 완성, 오류 밑줄, 타입 보기, 실행·테스트 버튼을 보여 주는 확장이에요. 코드를 저장하기 전에도 문제를 알려 줘서 컴파일 오류를 일찍 찾게 해요. 폴더를 열 때 `Cargo.toml`이 있는 폴더를 열어야 제대로 동작해요.

### 매크로
- 처음 등장: [P3 Day 1](#/day/p3-d01)

코드를 만들어 내는 코드예요. Rust에서는 이름 뒤에 `!`가 붙어요(`println!`, `vec!`, `format!`). 보통 함수보다 유연해서 `println!("{name}")`처럼 개수가 정해지지 않은 값을 받을 수 있어요.

### 불변
- 처음 등장: [P3 Day 2](#/day/p3-d02)

한 번 정한 값을 바꿀 수 없다는 뜻이에요. Rust의 `let` 변수는 기본이 불변이고, 바꾸려면 `let mut`로 선언해요. 바뀌지 않는 값이 기본이라 "누가 언제 바꿨지?"를 걱정할 일이 줄어요.

### 섀도잉
- 처음 등장: [P3 Day 2](#/day/p3-d02)

같은 이름으로 `let`을 다시 써서 새 변수를 만드는 것이에요. 예를 들어 `let level = 3;` 다음에 `let level = level as f32 * 1.5;`라고 쓰면 앞의 `level`은 가려지고 새 값이 쓰여요. 값을 바꾸는 `mut`와 달리 타입까지 바꿀 수 있어요.

### 표현식
- 처음 등장: [P3 Day 2](#/day/p3-d02)

계산해서 값을 만들어 내는 코드 조각이에요. Rust에서는 `if`, 블록 `{ }`, `match`도 값을 돌려주는 표현식이에요. 함수의 마지막 줄을 세미콜론 없이 쓰면 그 표현식의 값이 반환값이 되고, 세미콜론을 붙이면 값이 없는 문(statement)이 돼요.

### 소유권
- 처음 등장: [P3 Day 4](#/day/p3-d04)

Rust에서 모든 값에는 그 값을 책임지는 주인(변수)이 정확히 하나 있다는 규칙이에요. 주인이 범위를 벗어나면 값이 자동으로 정리돼요. 이 규칙 덕분에 가비지 컬렉터 없이도 메모리를 두 번 지우거나 지운 메모리를 쓰는 실수가 생기지 않아요.

### 스택
- 처음 등장: [P3 Day 4](#/day/p3-d04)

함수가 실행될 때 크기가 정해진 값(정수, 실수, 고정 크기 구조체)을 차곡차곡 쌓아 두는 메모리 영역이에요. 넣고 빼기가 매우 빠르고 함수가 끝나면 자동으로 비워져요. 크기가 실행 중에 바뀌는 값은 힙에 두고 스택에는 그 위치만 둬요.

### 힙
- 처음 등장: [P3 Day 4](#/day/p3-d04)

실행 중에 크기가 정해지거나 바뀌는 값(예: `String`, `Vec`)을 두는 메모리 영역이에요. 필요할 때 자리를 빌려 오고 다 쓰면 돌려줘야 해요. Rust는 소유권 규칙으로 언제 돌려줄지 자동으로 정해요.

### 소유권 이동
- 처음 등장: [P3 Day 4](#/day/p3-d04)

값의 주인이 다른 변수나 함수로 넘어가는 것이에요(영어로 move). `let b = a;`나 `greet(a)` 뒤에는 `a`를 더 쓸 수 없어요. `String`처럼 힙을 가진 값은 이동하고, `i32`처럼 `Copy`인 값은 이동 대신 복사돼요.

### 가비지 컬렉션
- 처음 등장: [P3 Day 4](#/day/p3-d04)

프로그램이 더 쓰지 않는 메모리를 런타임이 주기적으로 찾아서 치워 주는 방식이에요. C#·JavaScript가 이 방식을 써요. 편리하지만 치우는 순간 프로그램이 잠깐 멈출 수 있어서, 게임에서는 프레임이 끊기는 원인이 되기도 해요.

### RAII
- 처음 등장: [P3 Day 4](#/day/p3-d04)

자원을 얻는 순간 그 자원을 관리할 객체를 만들고, 객체가 사라질 때 자원도 자동으로 돌려주는 방식이에요(Resource Acquisition Is Initialization). C++에서 생긴 이름이고, Rust의 소유권과 `Drop`이 같은 생각이에요. 파일 닫기, 잠금 풀기, 목록에서 지우기를 잊지 않게 해 줘요.

### 빌림
- 처음 등장: [P3 Day 5](#/day/p3-d05)

소유권을 넘기지 않고 값을 잠시 써도 되는 권한을 얻는 것이에요. `&x`로 읽기만 빌리거나 `&mut x`로 고치려고 빌려요. 빌린 쪽이 다 쓰면 주인은 그대로 값을 계속 써요.

### 참조
- 처음 등장: [P3 Day 5](#/day/p3-d05)

값이 있는 자리를 가리키는 값이에요. Rust에서는 `&x`가 `x`의 참조이고, 참조로는 값을 읽을 수 있지만 소유하지는 않아요. 컴파일러가 참조가 가리키는 값이 살아 있는 동안만 쓰이도록 검사해요.

### 가변 참조
- 처음 등장: [P3 Day 5](#/day/p3-d05)

빌린 값을 고칠 수 있는 참조예요(`&mut x`). 한 번에 하나만 있을 수 있고, 그동안에는 읽기 참조도 만들 수 없어요. 이 규칙 덕분에 두 곳에서 동시에 같은 값을 고쳐 꼬이는 일이 없어요.

### 빌림 검사기
- 처음 등장: [P3 Day 5](#/day/p3-d05)

Rust 컴파일러에서 참조 규칙(읽기 여러 개 또는 쓰기 하나, 주인보다 오래 살지 않기)을 검사하는 부분이에요. 규칙을 어기면 E0502, E0499 같은 오류로 컴파일을 멈춰요. 실행하기 전에 메모리 실수를 잡아 주는 Rust의 핵심 장치예요.

### 슬라이스
- 처음 등장: [P3 Day 5](#/day/p3-d05)

배열이나 `Vec`의 일부(또는 전체)를 빌려 보는 참조예요. `&[u32]`는 "u32 여러 개가 이어진 구간"이라는 뜻이고, `&scores[1..3]`처럼 범위로 잘라 만들어요. 길이를 함께 알고 있어서 범위 밖을 읽지 않게 검사해요.

### 문자열 슬라이스
- 처음 등장: [P3 Day 5](#/day/p3-d05)

어딘가에 있는 UTF-8 글자들을 빌려 보는 참조로, 타입은 `&str`이에요. 따옴표로 쓴 글자 `"철수"`도 `&str`이에요. 크기를 바꿀 수 있는 내 문자열이 필요하면 `String`을 쓰고, 읽기만 하는 함수 매개변수는 보통 `&str`로 받아요.

### 구조체
- 처음 등장: [P3 Day 6](#/day/p3-d06)

관련 있는 값 여러 개를 이름 붙은 필드로 묶은 사용자 정의 타입이에요. 예를 들어 `struct Vec2 { x: f32, y: f32 }`는 x와 y를 한 덩어리로 다뤄요. C#의 클래스·TypeScript의 interface와 비슷하게 데이터의 모양을 정해요.

### impl 블록
- 처음 등장: [P3 Day 6](#/day/p3-d06)

타입에 함수와 메서드를 붙이는 `impl 타입 { … }` 블록이에요. 안에 쓴 `fn length(self)`처럼 `self`를 받는 함수는 메서드가 되고, `self`가 없는 함수는 연관 함수가 돼요. 한 타입에 `impl` 블록을 여러 개 둘 수도 있어요.

### 연관 함수
- 처음 등장: [P3 Day 6](#/day/p3-d06)

타입에 속하지만 `self`를 받지 않는 함수예요. `Vec2::new(3.0, 4.0)`처럼 `타입::이름`으로 불러요. 새 값을 만드는 생성 함수를 보통 `new`라는 연관 함수로 만들어요.

### 2차원 벡터
- 처음 등장: [P3 Day 6](#/day/p3-d06)

평면 위의 방향과 크기를 (x, y) 두 숫자로 나타낸 값이에요. 게임에서는 위치, 속도, 입력 방향을 모두 2차원 벡터로 다뤄요. 이 교재의 `Vec2`가 2차원 벡터이고, Rust 표준 라이브러리의 목록 타입 `Vec`과는 다른 것이에요.

### Option
- 처음 등장: [P3 Day 7](#/day/p3-d07)

"값이 있을 수도, 없을 수도 있음"을 나타내는 Rust 표준 열거형이에요. 값이 있으면 `Some(값)`, 없으면 `None`이에요. null 대신 쓰기 때문에 "없는 경우"를 빠뜨리면 컴파일러가 알려 줘요.

### Result
- 처음 등장: [P3 Day 8](#/day/p3-d08)

"성공했거나 실패했음"을 나타내는 Rust 표준 열거형이에요. 성공하면 `Ok(값)`, 실패하면 `Err(오류)`를 담아요. 예외를 던지는 대신 함수가 `Result`를 돌려주므로, 실패할 수 있는 곳이 타입에 드러나요.

### ? 연산자
- 처음 등장: [P3 Day 8](#/day/p3-d08)

`Result`나 `Option` 뒤에 붙여 "성공이면 값을 꺼내고, 실패면 지금 함수에서 그 오류를 바로 돌려줘"라는 뜻의 연산자예요. `let n = text.parse::<u32>()?;`처럼 써요. 오류를 하나하나 `match`하지 않아도 되어 코드가 짧아져요.

### panic
- 처음 등장: [P3 Day 8](#/day/p3-d08)

프로그램이 더 진행할 수 없는 버그를 만났을 때 즉시 멈추는 것이에요. 범위 밖 인덱스, `None`에 `unwrap()`, 디버그 빌드의 정수 넘침에서 일어나요. 사용자의 잘못된 입력처럼 예상할 수 있는 실패는 panic 대신 `Result`로 다뤄요.

### Vec
- 처음 등장: [P3 Day 9](#/day/p3-d09)

Rust 표준 라이브러리의 크기가 늘었다 줄었다 하는 목록 타입이에요(`Vec<T>`). `push`로 넣고, `iter()`로 돌고, `retain`으로 조건에 맞는 것만 남겨요. 값들은 힙에 이어서 저장돼요.

### HashMap
- 처음 등장: [P3 Day 9](#/day/p3-d09)

키로 값을 찾는 Rust 표준 라이브러리의 사전 타입이에요(`HashMap<K, V>`). 예를 들어 닉네임 → 최고 점수를 저장해요. 순서가 정해져 있지 않아서 출력할 때마다 순서가 다를 수 있어요.

### 반복자
- 처음 등장: [P3 Day 9](#/day/p3-d09)

값을 하나씩 차례로 꺼내 주는 것이에요(iterator). Rust에서는 `iter()`로 얻은 반복자에 `map`, `filter`, `sum`, `collect` 같은 메서드를 이어 붙여 목록을 가공해요. 실제 계산은 `collect`나 `sum`처럼 결과를 요구할 때 일어나요.

### 클로저
- 처음 등장: [P3 Day 9](#/day/p3-d09)

이름 없이 그 자리에서 만드는 작은 함수로, 바깥의 변수를 붙잡아 쓸 수 있어요. Rust에서는 `|p| p.score > min`처럼 세로 막대 사이에 매개변수를 써요. JavaScript의 화살표 함수, C#의 람다와 같은 역할이에요.

### 트레이트
- 처음 등장: [P3 Day 10](#/day/p3-d10)

여러 타입이 공통으로 가져야 할 메서드의 목록을 정한 것이에요. `impl 트레이트 for 타입`으로 각 타입이 그 메서드를 구현해요. C#의 인터페이스와 비슷하고, `+` 연산자도 `Add`라는 트레이트로 정해져 있어요.

### derive
- 처음 등장: [P3 Day 10](#/day/p3-d10)

`#[derive(Debug, Clone, Copy, PartialEq)]`처럼 표준 트레이트 구현을 컴파일러가 자동으로 써 주게 하는 속성이에요. 손으로 쓰면 길고 뻔한 코드를 한 줄로 줄여요. 필드가 모두 그 트레이트를 가져야 쓸 수 있어요.

### 연산자 오버로딩
- 처음 등장: [P3 Day 10](#/day/p3-d10)

`+`, `-`, `*` 같은 연산자가 내가 만든 타입에서도 동작하게 정의하는 것이에요. Rust에서는 `std::ops`의 `Add`, `Sub`, `Mul` 같은 트레이트를 구현해요. 그러면 `a + b * 2.0`처럼 벡터 계산을 수식 그대로 쓸 수 있어요.

### 트레이트 경계
- 처음 등장: [P3 Day 10](#/day/p3-d10)

제네릭 타입이 반드시 가져야 할 트레이트를 적은 조건이에요. `fn best<T: Scored>(items: &[T])`는 "`Scored`를 구현한 타입이면 무엇이든"이라는 뜻이에요. 조건 덕분에 함수 안에서 그 트레이트의 메서드를 안심하고 부를 수 있어요.

### 크레이트
- 처음 등장: [P3 Day 11](#/day/p3-d11)

Rust에서 한 번에 컴파일되는 코드 묶음이에요. 실행 파일을 만드는 바이너리 크레이트와 다른 코드가 가져다 쓰는 라이브러리 크레이트가 있어요. 이 교재의 `game-core`, `server`, `game-wasm`이 각각 크레이트이고, crates.io에서 받는 serde 같은 라이브러리도 크레이트예요.

### 워크스페이스
- 처음 등장: [P3 Day 11](#/day/p3-d11)

크레이트 여러 개를 한 폴더에서 함께 빌드·테스트하는 Cargo의 묶음이에요. 루트 `Cargo.toml`의 `[workspace]`에 멤버를 적고, 의존성 버전과 `Cargo.lock`, `target` 폴더를 함께 써요. `cargo test --workspace`나 `cargo run -p server`처럼 멤버를 골라 실행해요.

### pub
- 처음 등장: [P3 Day 11](#/day/p3-d11)

Rust에서 모듈·함수·구조체·필드를 바깥에서도 쓸 수 있게 공개하는 키워드예요. 아무것도 안 쓰면 기본은 비공개라서 같은 모듈 안에서만 보여요. 공개할 것만 골라서 열어 두면 나중에 안쪽 구현을 바꾸기 쉬워요.

### serde
- 처음 등장: [P3 Day 11](#/day/p3-d11)

Rust 값을 JSON 같은 형식으로 바꾸고 되돌리는 표준적인 라이브러리예요. 구조체·열거형에 `#[derive(Serialize, Deserialize)]`를 붙이고 `#[serde(…)]` 속성으로 이름 규칙을 정해요. 실제 JSON 글자 처리는 짝 라이브러리 `serde_json`이 해요.

### 역직렬화
- 처음 등장: [P3 Day 11](#/day/p3-d11)

[[직렬화]]의 반대로, 글자·바이트로 온 데이터를 다시 프로그램의 값으로 바꾸는 것이에요. 받은 JSON이 약속한 모양과 다르면 실패하므로, 잘못된 메시지를 걸러 내는 첫 관문이 돼요. Rust에서는 `serde_json::from_str`가 이 일을 해요.

### 수명
- 처음 등장: [P3 Day 12](#/day/p3-d12)

참조가 얼마 동안 유효한지를 나타내는 Rust의 표시예요(lifetime). `'a`처럼 작은따옴표로 시작하고, "돌려주는 참조는 입력 참조만큼만 살아 있다" 같은 관계를 컴파일러에게 알려 줘요. `'static`은 프로그램이 끝날 때까지 살아 있는 값(예: 코드에 박힌 글자)이라는 뜻이에요.

### 스마트 포인터
- 처음 등장: [P3 Day 12](#/day/p3-d12)

값을 가리키면서 추가 기능(힙에 두기, 주인 수 세기 등)을 가진 타입이에요. `Box<T>`는 값을 힙에 하나 두고, `Rc<T>`는 한 스레드에서 여러 주인이 같은 값을 나눠 가지게 해요. 마지막 주인이 사라지면 값도 자동으로 정리돼요.

### Arc
- 처음 등장: [P3 Day 12](#/day/p3-d12)

여러 스레드가 같은 값을 함께 소유하게 해 주는 스마트 포인터예요(Atomically Reference Counted). `Arc::clone`으로 주인을 늘려도 값은 하나이고, 주인 수는 스레드끼리 안전하게 세요. 고쳐야 하면 보통 `Arc<Mutex<T>>`처럼 잠금과 함께 써요.

### Mutex
- 처음 등장: [P3 Day 12](#/day/p3-d12)

한 번에 한 스레드만 안의 값을 쓸 수 있게 하는 잠금이에요(mutual exclusion). `lock()`으로 잠그고 값을 쓰면, 잠금이 범위를 벗어날 때 자동으로 풀려요. 잠근 채 오래 기다리면 다른 스레드가 모두 멈추므로 잠그는 시간을 짧게 해요.

### 스레드
- 처음 등장: [P3 Day 12](#/day/p3-d12)

한 프로그램 안에서 동시에 실행되는 작업의 흐름이에요. Rust에서는 `std::thread::spawn`으로 새 스레드를 만들고 `join`으로 끝나기를 기다려요. 여러 스레드가 같은 데이터를 쓰려면 `Arc`, `Mutex` 같은 안전 장치가 필요해요.

### 동시성
- 처음 등장: [P3 Day 12](#/day/p3-d12)

여러 일이 시간상 겹쳐서 진행되도록 프로그램을 짜는 것이에요. 게임 서버는 수십 명의 연결을 동시에 처리해야 해서 동시성이 꼭 필요해요. 스레드나 비동기 작업(Tokio)으로 구현해요.

### 데이터 경쟁
- 처음 등장: [P3 Day 12](#/day/p3-d12)

두 스레드가 같은 메모리를 동시에 접근하고 그중 하나 이상이 쓰기일 때 결과가 실행마다 달라지는 버그예요. 재현이 어려워 찾기 힘든 버그로 유명해요. Rust는 빌림 규칙과 `Send`·`Sync` 검사로 이런 코드를 컴파일 단계에서 막아요.

### 게임 루프
- 처음 등장: [P3 Day 13](#/day/p3-d13)

게임이 켜져 있는 동안 "입력 읽기 → 상태 갱신(update) → 그리기(render)"를 끝없이 반복하는 구조예요. 거의 모든 게임과 게임 엔진이 이 구조로 돌아가요. 유니티의 `Update()`는 엔진의 게임 루프가 프레임마다 불러 주는 함수예요.

### 프레임
- 처음 등장: [P3 Day 13](#/day/p3-d13)

게임이나 영상에서 화면 한 장을 그리는 한 번의 단위예요. 1초에 그리는 장수를 FPS(frames per second)라고 하고, 보통 모니터 주사율(60Hz, 144Hz)에 맞춰요. 게임 루프 한 바퀴가 보통 한 프레임이에요.

### 델타 타임
- 처음 등장: [P3 Day 13](#/day/p3-d13)

지난 프레임에서 이번 프레임까지 흐른 시간(초)이에요. 이동량을 "속도 × 델타 타임"으로 계산하면 60Hz든 144Hz든 1초에 같은 거리를 움직여요. 유니티에서는 `Time.deltaTime`이라는 이름으로 써요.

### requestAnimationFrame
- 처음 등장: [P3 Day 13](#/day/p3-d13)

브라우저에게 "다음 화면을 그리기 직전에 이 함수를 불러 줘"라고 부탁하는 API예요. 화면 주사율에 맞춰 불리고, 탭이 보이지 않으면 쉬어서 전력을 아껴요. 불린 함수 안에서 다시 부탁하면 게임 루프가 돼요.

### Canvas
- 처음 등장: [P3 Day 14](#/day/p3-d14)

HTML의 `<canvas>` 요소로, JavaScript로 도형·글자·그림을 픽셀 단위로 직접 그리는 그림판이에요. 요소를 수십 개 만들지 않고 한 장에 그려서 많은 물체가 움직이는 게임에 알맞아요. 그리기는 렌더링 컨텍스트를 통해 해요.

### 렌더링 컨텍스트
- 처음 등장: [P3 Day 14](#/day/p3-d14)

Canvas에 실제로 그리는 도구 모음 객체예요. `canvas.getContext('2d')`로 얻은 2D 컨텍스트에 `arc`, `fill`, `fillText`, `translate`, `scale` 같은 메서드가 있어요. 색·선 굵기·변환 같은 현재 그리기 상태도 이 객체가 기억해요.

### 월드 좌표
- 처음 등장: [P3 Day 14](#/day/p3-d14)

화면 크기와 상관없이 게임 세계 안에서 정한 좌표예요. 이 게임은 아레나 중심이 (0, 0)이고 반지름이 600인 월드 좌표를 써요. 그릴 때만 화면 크기에 맞춰 확대·축소해서, 서버와 모든 기기가 같은 숫자로 말할 수 있어요.

### 기기 픽셀 비율
- 처음 등장: [P3 Day 14](#/day/p3-d14)

화면의 CSS 픽셀 하나가 실제 물리 픽셀 몇 개로 그려지는지를 나타내는 값이에요(device pixel ratio, DPR). 휴대폰은 보통 2~3이라서 캔버스를 CSS 크기 그대로 만들면 흐릿해 보여요. 캔버스 해상도를 CSS 크기 × DPR로 맞추면 선명해져요.

### 포인터 이벤트
- 처음 등장: [P3 Day 15](#/day/p3-d15)

마우스·터치·펜 입력을 한 가지 방식으로 받는 브라우저 이벤트예요(`pointerdown`, `pointermove`, `pointerup`, `pointercancel`). 각 손가락은 `pointerId`로 구분돼요. `setPointerCapture`를 쓰면 손가락이 요소 밖으로 나가도 계속 이벤트를 받아요.

### 가상 조이스틱
- 처음 등장: [P3 Day 15](#/day/p3-d15)

휴대폰 화면에 그린 원형 받침을 손가락으로 끌어서 방향과 세기를 입력하는 조작 장치예요. 받침 중심에서 손가락까지의 벡터를 반지름으로 나눠 길이 0~1의 방향으로 만들어요. 실제 게임패드 스틱처럼 아날로그 입력을 흉내 내요.

### 속도
- 처음 등장: [P3 Day 16](#/day/p3-d16)

물체의 위치가 1초에 얼마나, 어느 방향으로 바뀌는지를 나타내는 벡터예요. 매 틱 "위치 += 속도 × 시간"으로 위치를 옮겨요. 크기만 따로 말할 때는 속력이라고 해요.

### 가속도
- 처음 등장: [P3 Day 16](#/day/p3-d16)

속도가 1초에 얼마나 바뀌는지를 나타내는 값이에요. 조이스틱 방향으로 가속도를 주면 물체가 서서히 빨라져요. 이 게임에서는 `PLAYER_ACCEL = 1800`이에요.

### 마찰
- 처음 등장: [P3 Day 16](#/day/p3-d16)

움직이는 물체의 속도를 조금씩 줄이는 힘이에요. 이 게임은 매 틱 속도에 `1 / (1 + 마찰 × 시간)`을 곱해서 손을 떼면 미끄러지다 멈추게 해요. 가속과 마찰이 균형을 이루는 곳이 사실상의 최고 속력이에요.

### 정규화
- 처음 등장: [P3 Day 16](#/day/p3-d16)

벡터의 방향은 그대로 두고 길이만 1로 만드는 것이에요. 각 성분을 길이로 나눠서 구해요. 길이가 0인 벡터는 방향이 없으므로 0으로 나누지 않게 따로 처리해야 해요.

### 충돌 판정
- 처음 등장: [P3 Day 17](#/day/p3-d17)

두 물체가 겹쳤는지 계산으로 알아내는 것이에요. 원 두 개는 중심 사이 거리가 반지름의 합보다 작으면 겹쳐요. 제곱근을 피하려고 거리의 제곱과 반지름 합의 제곱을 비교하기도 해요.

### 밀어내기
- 처음 등장: [P3 Day 17](#/day/p3-d17)

겹친 두 물체를 겹친 만큼 서로 반대 방향으로 옮겨 떼어 놓는 충돌 처리예요. 이 게임은 겹친 길이를 반씩 나눠 두 원을 밀어요. 벽(아레나 경계)과 부딪힌 경우에는 경계 안쪽으로 되돌려요.

### 내적
- 처음 등장: [P3 Day 17](#/day/p3-d17)

두 벡터의 같은 성분끼리 곱해 더한 값이에요(`a.x*b.x + a.y*b.y`). 방향이 같으면 양수, 반대면 음수, 직각이면 0이에요. 이 게임에서는 속도 중 "벽 바깥쪽으로 향하는 부분"만 골라 없애는 데 써요.

### 상태 머신
- 처음 등장: [P3 Day 18](#/day/p3-d18)

시스템이 몇 가지 정해진 상태 중 하나에 있고, 조건이 맞을 때만 다른 상태로 넘어가게 설계하는 방법이에요. 이 게임의 라운드는 대기 → 게임 → 결과 → 대기를 도는 상태 머신이에요. 상태마다 할 일과 넘어가는 조건이 분명해서 버그가 줄어요.

### 이식
- 처음 등장: [P3 Day 19](#/day/p3-d19)

이미 동작하는 프로그램을 다른 언어나 환경으로 옮겨 다시 만드는 것이에요(porting). 이 교재는 TypeScript로 먼저 만든 게임 규칙을 Rust `game-core`로 옮겨요. 이름과 순서를 원본과 똑같이 맞추면 옮긴 결과를 비교하기 쉬워요.

### 고정 틱
- 처음 등장: [P3 Day 19](#/day/p3-d19)

실제 프레임 속도와 상관없이 항상 같은 시간 간격(예: 0.05초)으로 게임을 계산하는 방식이에요. 이 게임 서버는 1초에 20번, 매번 `TICK_DT = 0.05`로 한 걸음씩 진행해요. 간격이 늘 같아서 결과가 예측 가능하고 테스트하기 쉬워요.

### 결정성
- 처음 등장: [P3 Day 19](#/day/p3-d19)

같은 시작 상태와 같은 입력을 주면 언제 어디서 실행해도 결과가 똑같이 나오는 성질이에요. 이 게임은 시드 난수와 사칙연산·제곱근만 써서 결정성을 지켜요. 덕분에 테스트로 결과를 확인하고, 브라우저 예측이 서버와 같은 답을 낼 수 있어요.

### 시드
- 처음 등장: [P3 Day 19](#/day/p3-d19)

난수 생성기가 수열을 만들기 시작하는 출발 값이에요. 같은 시드로 만든 난수 생성기는 언제나 같은 순서의 "무작위" 수를 내요. 이 게임의 `World::new(seed)`는 시드로 아이템 위치를 정해서 같은 시드면 같은 판이 돼요.

### WebAssembly
- 처음 등장: [P3 Day 20](#/day/p3-d20)

브라우저에서 JavaScript 옆에서 빠르게 실행되는 작은 바이너리 형식이에요(줄여서 wasm). Rust·C++ 같은 언어를 이 형식으로 컴파일하면 웹페이지에서 그 코드를 그대로 돌릴 수 있어요. 이 게임은 서버의 이동 계산 코드를 wasm으로 만들어 휴대폰에서도 써요.

### 컴파일 타깃
- 처음 등장: [P3 Day 20](#/day/p3-d20)

컴파일러가 결과물을 어떤 기계·운영체제용으로 만들지 정하는 이름이에요. Windows PC용은 `x86_64-pc-windows-msvc`, 브라우저용 WebAssembly는 `wasm32-unknown-unknown`이에요. 기본 설치에는 내 PC용만 있어서 다른 타깃은 `rustup target add`로 더해야 해요.

### wasm-bindgen
- 처음 등장: [P3 Day 20](#/day/p3-d20)

Rust로 만든 WebAssembly와 JavaScript가 서로 함수를 부르고 문자열 같은 값을 주고받게 이어 주는 도구예요. Rust 쪽에서는 `#[wasm_bindgen]` 속성을 붙이고, 명령행 도구 `wasm-bindgen`이 브라우저용 `.js`·`.d.ts` 파일을 만들어요. 크레이트 버전과 명령행 도구 버전이 정확히 같아야 해요.

### 바인딩
- 처음 등장: [P3 Day 20](#/day/p3-d20)

한 언어로 만든 기능을 다른 언어에서 부를 수 있게 이어 주는 연결 코드예요. `npm run wasm`이 만드는 `game_wasm.js`는 Rust의 `predict` 함수를 TypeScript에서 부를 수 있게 해 주는 바인딩이에요. 바인딩은 빌드할 때 다시 만들 수 있어서 커밋하지 않아요.

### 권위 서버
- 처음 등장: [P3 Day 21](#/day/p3-d21)

게임의 진짜 상태를 오직 서버만 계산하고, 클라이언트는 입력만 보내고 결과를 받아 보여 주는 구조예요(authoritative server). 클라이언트가 위치나 점수를 마음대로 바꿔도 서버가 받아들이지 않아서 치팅을 막기 쉬워요. 이 게임의 Rust 서버가 권위 서버예요.

### 지연 시간
- 처음 등장: [P3 Day 21](#/day/p3-d21)

데이터를 보낸 뒤 상대에게 도착할 때까지 걸리는 시간이에요(latency). 거리, 네트워크 상태, 공유기 등에 따라 수 ms에서 수백 ms까지 달라져요. 지연 때문에 서버의 소식은 항상 조금 과거의 것이에요.

### 틱 레이트
- 처음 등장: [P3 Day 21](#/day/p3-d21)

서버가 1초에 게임 상태를 몇 번 계산하는지를 나타내는 값이에요(Hz). 이 게임 서버는 20Hz로 계산하고, 그중 절반인 10Hz로 스냅샷을 보내요. 높을수록 정확하지만 계산량과 전송량이 늘어요.

### RTT
- 처음 등장: [P3 Day 21](#/day/p3-d21)

메시지를 보내고 그 답이 돌아올 때까지 걸린 왕복 시간이에요(Round-Trip Time). 이 게임은 2초마다 `ping`에 보낸 시각을 담고, 돌아온 `pong`의 시각을 빼서 RTT를 재요. 한쪽 방향 지연은 보통 RTT의 절반으로 어림해요.

### 넷코드
- 처음 등장: [P3 Day 21](#/day/p3-d21)

온라인 게임에서 상태를 맞추고, 지연을 숨기고, 입력을 주고받는 네트워크 처리 코드 전체를 부르는 말이에요. 권위 서버, 스냅샷, 보간, 클라이언트 예측이 모두 넷코드의 부품이에요. 유니티의 Netcode for GameObjects, 언리얼의 리플리케이션이 엔진이 제공하는 넷코드예요.

### 데디케이티드 서버
- 처음 등장: [P3 Day 21](#/day/p3-d21)

플레이어 중 누군가의 PC가 아니라 게임 진행만 맡는 별도 서버 프로그램이에요. 화면을 그리지 않고 규칙 계산과 상태 전송만 해요. 언리얼 엔진은 이런 서버 빌드를 공식 지원하고, 이 교재의 Rust 서버도 같은 역할이에요.

### Tokio
- 처음 등장: [P3 Day 22](#/day/p3-d22)

Rust의 대표적인 비동기 런타임이에요. `async` 함수가 만든 Future들을 적은 수의 스레드 위에서 번갈아 실행해서, 연결 수천 개를 동시에 기다릴 수 있게 해요. `#[tokio::main]`을 붙이면 `main`이 Tokio 위에서 돌아요.

### Future
- 처음 등장: [P3 Day 22](#/day/p3-d22)

"지금은 아니지만 나중에 끝날 일"을 나타내는 Rust의 값이에요. `async fn`을 부르면 바로 실행되지 않고 Future가 만들어지며, `.await`하거나 런타임에 넘겨야 실제로 진행돼요. JavaScript의 Promise, C#의 Task와 비슷한 개념이에요.

### Axum
- 처음 등장: [P3 Day 22](#/day/p3-d22)

Tokio 위에서 동작하는 Rust 웹 프레임워크예요. `Router`에 주소와 핸들러 함수를 연결하고, 추출기로 요청의 경로·쿼리·상태를 받아요. 이 교재의 HTTP API와 WebSocket 업그레이드를 모두 Axum으로 만들어요.

### 추출기
- 처음 등장: [P3 Day 22](#/day/p3-d22)

Axum 핸들러의 매개변수로 써서 요청에서 필요한 부분을 꺼내 주는 타입이에요(extractor). `State(state)`는 공유 상태, `Path(code)`는 경로의 값, `Query(params)`는 쿼리 문자열을 꺼내요. 꺼내지 못하면 Axum이 핸들러를 부르지 않고 400 같은 오류 응답을 보내요.

### WebSocket
- 처음 등장: [P3 Day 23](#/day/p3-d23)

브라우저와 서버가 연결 하나를 열어 둔 채 양쪽에서 언제든 메시지를 보낼 수 있게 하는 프로토콜이에요. 주소는 `ws://`(암호화하면 `wss://`)로 시작해요. 요청할 때만 답하는 HTTP와 달리 서버가 먼저 보낼 수 있어서 실시간 게임에 알맞아요.

### 프로토콜 업그레이드
- 처음 등장: [P3 Day 23](#/day/p3-d23)

처음에는 평범한 HTTP 요청으로 시작해서, 서버가 `101 Switching Protocols`로 답하면 같은 연결을 다른 프로토콜(WebSocket)로 바꾸는 과정이에요. 그래서 WebSocket은 HTTP와 같은 포트와 주소 체계를 쓸 수 있어요. Axum에서는 `WebSocketUpgrade`의 `on_upgrade`가 이 일을 해요.

### 에코 서버
- 처음 등장: [P3 Day 23](#/day/p3-d23)

받은 메시지를 그대로 돌려보내기만 하는 가장 단순한 서버예요. 연결·보내기·받기가 제대로 되는지 확인하는 첫 실험으로 많이 만들어요. 동작을 확인한 뒤에는 진짜 처리 코드로 바꿔요.

### 메시지 프로토콜
- 처음 등장: [P3 Day 24](#/day/p3-d24)

두 프로그램이 주고받을 메시지의 종류와 모양을 미리 정한 약속이에요. 이 게임은 JSON에 `t` 필드로 종류를 적고(`join`, `input`, `snapshot` …) 종류마다 필드를 정해요. 양쪽(Rust와 TypeScript)의 타입이 이 약속과 똑같아야 해요.

### 프로토콜 버전
- 처음 등장: [P3 Day 24](#/day/p3-d24)

메시지 약속의 판 번호예요. 이 게임은 `PROTOCOL_VERSION = 1`을 `welcome` 메시지에 실어 보내요. 메시지 모양을 호환되지 않게 바꿀 때 번호를 올리면, 옛 화면과 새 서버가 서로 다른 말을 하는 것을 알아챌 수 있어요.

### 구별된 유니온
- 처음 등장: [P3 Day 24](#/day/p3-d24)

여러 타입 중 하나인데, 공통 필드 하나(예: `t`)의 글자 값으로 어느 타입인지 구별할 수 있게 만든 TypeScript 유니온 타입이에요. `switch (msg.t)`로 나누면 각 가지 안에서 TypeScript가 정확한 타입을 알아요. Rust의 데이터 있는 열거형과 짝이 돼요.

### 액터 패턴
- 처음 등장: [P3 Day 25](#/day/p3-d25)

데이터를 가진 작업 하나(액터)가 그 데이터를 혼자 다루고, 다른 쪽은 메시지로 부탁만 하는 설계예요. 잠금 없이도 여러 연결이 안전하게 같은 게임 세계를 쓸 수 있어요. 이 게임은 방 하나가 액터 하나예요.

### 채널
- 처음 등장: [P3 Day 25](#/day/p3-d25)

작업(스레드나 비동기 작업) 사이에 값을 보내는 통로예요. 보내는 쪽(Sender)과 받는 쪽(Receiver)이 짝으로 만들어져요. Tokio에는 용도에 따라 mpsc, oneshot, broadcast 같은 채널이 있어요.

### mpsc
- 처음 등장: [P3 Day 25](#/day/p3-d25)

보내는 쪽은 여럿, 받는 쪽은 하나인 채널이에요(multi-producer, single-consumer). 이 게임에서는 여러 연결이 방 액터에게 참가·퇴장·입력 명령을 보낼 때 써요. 버퍼가 가득 차면 `send`는 기다리고 `try_send`는 실패를 돌려줘요.

### oneshot 채널
- 처음 등장: [P3 Day 25](#/day/p3-d25)

값을 딱 한 번만 보낼 수 있는 일회용 채널이에요. 명령과 함께 "답장 봉투"로 보내면, 받은 쪽이 결과를 넣어 돌려줘요. 이 게임은 참가 결과(플레이어 번호)와 방 정보를 이 채널로 돌려받아요.

### broadcast 채널
- 처음 등장: [P3 Day 25](#/day/p3-d25)

한 번 보낸 값을 구독한 모든 수신기가 받는 채널이에요. 이 게임의 방 액터는 스냅샷 JSON을 한 번 만들어 broadcast로 보내고, 각 연결이 자기 수신기로 받아요. 느린 수신기는 오래된 값을 놓치고(`Lagged`) 최신 값부터 다시 받아요.

### select!
- 처음 등장: [P3 Day 25](#/day/p3-d25)

Tokio의 매크로로, 여러 비동기 작업을 동시에 기다리다가 먼저 끝난 하나의 가지를 실행해요. 이 게임은 "명령이 왔다 / 틱 시간이 됐다", "스냅샷이 왔다 / 기한이 지났다 / 소켓에서 메시지가 왔다"를 `tokio::select!`로 기다려요. 한 가지의 본문이 실행되는 동안에는 다른 가지를 살피지 않아요.

### 유휴 타임아웃
- 처음 등장: [P3 Day 26](#/day/p3-d26)

연결에서 정해진 시간 동안 아무 소식이 없으면 끊긴 것으로 보고 정리하는 규칙이에요. 화면이 꺼지거나 Wi-Fi가 끊긴 휴대폰은 "닫기"를 보내지 못하므로 시간으로 알아채야 해요. 이 게임은 10초(`IDLE_TIMEOUT`)를 기준으로 해요.

### 하트비트
- 처음 등장: [P3 Day 26](#/day/p3-d26)

살아 있다는 것을 알리려고 주기적으로 보내는 작은 메시지예요. 이 게임의 브라우저는 2초마다 `ping`을 보내고, 서버는 무언가 받을 때마다 유휴 기한을 늘려요. 하트비트가 끊기면 유휴 타임아웃으로 정리돼요.

### 스냅샷
- 처음 등장: [P3 Day 27](#/day/p3-d27)

어느 한 순간의 게임 상태 전체(틱 번호, 단계, 남은 시간, 플레이어들, 아이템들)를 담은 메시지예요. 이 게임 서버는 1초에 10번 스냅샷을 모든 연결에 보내요. 클라이언트는 받은 스냅샷들로 화면을 그려요.

### 상태 동기화
- 처음 등장: [P3 Day 27](#/day/p3-d27)

서버의 게임 상태를 여러 클라이언트가 같은 모습으로 보게 맞추는 일이에요. 전체 상태를 주기적으로 보내는 스냅샷 방식과 바뀐 것만 보내는 방식이 있어요. 이 게임은 단순하고 튼튼한 전체 스냅샷 방식을 써요.

### 보간
- 처음 등장: [P3 Day 27](#/day/p3-d27)

알고 있는 두 값 사이의 중간값을 계산해 채우는 것이에요(interpolation). 이 게임의 화면은 조금 과거 시각을 그리면서, 그 시각을 사이에 둔 두 스냅샷의 위치를 비율대로 섞어(lerp) 부드럽게 움직여요. 그래서 스냅샷이 1초에 10번만 와도 끊김 없이 보여요.

### 클라이언트 예측
- 처음 등장: [P3 Day 28](#/day/p3-d28)

서버의 답을 기다리지 않고, 내 입력의 결과를 내 기기에서 먼저 계산해 바로 보여 주는 기법이에요. 이 게임은 서버와 같은 Rust 이동 코드(WebAssembly)로 내 플레이어만 매 프레임 미리 움직여요. 지연이 있어도 조작이 즉시 반응하는 것처럼 느껴져요.

### 서버 보정
- 처음 등장: [P3 Day 28](#/day/p3-d28)

클라이언트가 예측한 상태를 서버가 보낸 진짜 상태 쪽으로 고치는 것이에요(reconciliation). 정석은 서버가 처리한 입력 번호를 알려 주면 그 뒤 입력을 다시 적용하는 방식이에요. 이 게임은 입력 확인 번호가 없어서, 서버 위치를 지연만큼 앞으로 계산한 뒤 크게 다르면 바로 맞추고 작으면 조금씩 다가가요.

### 시퀀스 번호
- 처음 등장: [P3 Day 28](#/day/p3-d28)

메시지에 1, 2, 3 …처럼 차례로 붙이는 번호예요. 네트워크에서는 메시지가 늦게 도착할 수 있으므로, 받은 쪽은 번호를 보고 이미 받은 것보다 오래된 메시지를 버려요. 이 게임의 `input` 메시지의 `seq`가 시퀀스 번호예요.

### 방 코드
- 처음 등장: [P3 Day 29](#/day/p3-d29)

여러 방 중 하나를 찾아 들어가는 짧은 이름이에요. 이 게임은 영문 대문자 4자(예: `QWER`)를 무작위로 만들고, 소문자로 입력해도 찾아 줘요. 참가 주소 `play.html?room=QWER`와 QR 코드에 방 코드가 들어가요.

### Drop
- 처음 등장: [P3 Day 29](#/day/p3-d29)

값이 사라질 때 Rust가 자동으로 부르는 정리 함수를 정하는 트레이트예요. `impl Drop for 타입`에 `fn drop(&mut self)`를 쓰면, 정상 종료든 panic으로 풀리든 그 값이 사라지는 순간 실행돼요. 이 게임의 `RemoveOnDrop`은 이 성질로 끝난 방을 목록에서 반드시 지워요.

### 관전 화면
- 처음 등장: [P3 Day 30](#/day/p3-d30)

게임에 참가하지 않고 진행 상황만 보여 주는 화면이에요. 이 게임의 `host.html`은 OBS 브라우저 소스로 방송 화면 위에 투명하게 겹치고, 아레나·참가자 수·결과·참가 QR을 보여 줘요. 서버에는 `role=host`로 접속해 스냅샷을 받기만 해요.

### QR 코드
- 처음 등장: [P3 Day 30](#/day/p3-d30)

흑백 사각형 칸 무늬에 글자(보통 주소)를 담은 2차원 바코드예요. 휴대폰 카메라로 찍으면 담긴 주소가 바로 열려요. 이 게임은 관전 화면에 참가 주소 QR을 그려 시청자가 찍고 들어오게 해요.

### 멀티 페이지 앱
- 처음 등장: [P3 Day 30](#/day/p3-d30)

HTML 페이지 여러 개가 각자 따로 열리는 웹 앱 구조예요(MPA). 이 게임은 `index.html`(방 만들기), `host.html`(관전), `play.html`(컨트롤러) 세 페이지로 되어 있어요. Vite에서는 빌드할 시작점 HTML들을 설정에 모두 적어야 해요.

### LAN
- 처음 등장: [P3 Day 31](#/day/p3-d31)

집이나 사무실처럼 가까운 곳의 기기들을 공유기 하나로 묶은 근거리 네트워크예요(Local Area Network). 같은 Wi-Fi에 연결된 PC와 휴대폰은 같은 LAN에 있어서 인터넷을 거치지 않고 직접 통신할 수 있어요. 이 게임은 방송 PC의 서버에 같은 LAN의 휴대폰이 접속해요.

### 사설 IP 주소
- 처음 등장: [P3 Day 31](#/day/p3-d31)

공유기 안쪽(LAN)에서만 쓰는 IP 주소예요. 보통 `192.168.x.x`, `10.x.x.x` 꼴이고, 바깥 인터넷에서는 이 주소로 찾아올 수 없어요. PowerShell `ipconfig`의 IPv4 주소에서 내 PC의 사설 IP를 볼 수 있어요.

### Windows 방화벽
- 처음 등장: [P3 Day 31](#/day/p3-d31)

Windows에 들어 있는, 네트워크 연결을 허용하거나 막는 보안 기능이에요(Windows Defender 방화벽). 프로그램이 처음으로 바깥 연결을 받으려 하면 허용할지 묻는 창을 띄워요. 같은 Wi-Fi의 휴대폰이 서버에 들어오려면 개인 네트워크에서 허용해야 해요.

### 네트워크 프로필
- 처음 등장: [P3 Day 31](#/day/p3-d31)

Windows가 연결된 네트워크를 개인(집처럼 믿을 수 있는 곳)과 공용(카페처럼 낯선 곳) 중 무엇으로 보는지 정한 설정이에요. 공용이면 다른 기기가 내 PC에 접속하는 것을 더 강하게 막아요. 집 Wi-Fi가 공용으로 잡혀 있으면 휴대폰이 서버에 못 들어올 수 있어요.

### 치팅
- 처음 등장: [P3 Day 32](#/day/p3-d32)

게임 규칙을 어겨 부당하게 이득을 보거나 다른 사람을 방해하는 행위예요. 웹게임에서는 메시지를 조작해 속도를 높이거나, 메시지를 폭탄처럼 보내거나, 이상한 닉네임으로 방송 화면을 어지럽히는 식이에요. 권위 서버와 서버 검증이 기본 방어예요.

### 거부 목록
- 처음 등장: [P3 Day 32](#/day/p3-d32)

"이것만은 안 된다"고 금지할 것을 적어 두고 나머지는 모두 허용하는 검사 방식이에요(deny list). 한글·이모지 닉네임을 넓게 허용할 수 있지만, 새로운 꼼수가 나오면 목록을 늘려야 해요. 이 게임의 닉네임 검사는 보이지 않는 문자와 금지어를 막는 거부 목록 방식이에요.

### 허용 목록
- 처음 등장: [P3 Day 32](#/day/p3-d32)

"이것만 된다"고 허용할 것을 정해 두고 나머지는 모두 막는 검사 방식이에요(allow list). 예상하지 못한 입력까지 막아서 안전하지만, 정상적인 입력(다양한 언어·이모지)도 막힐 수 있어요. 보안이 중요한 곳일수록 허용 목록을 먼저 검토해요.

### 보이지 않는 문자
- 처음 등장: [P3 Day 32](#/day/p3-d32)

화면에 보이지 않거나 빈칸처럼 보이는 유니코드 글자예요. 폭 없는 공백(U+200B), 글자 방향을 바꾸는 제어 문자, 한글 채움 문자(U+3164) 등이 있어요. 금지어 검사를 피하거나 빈 닉네임을 만드는 데 악용될 수 있어 닉네임에서 거절해요.

### 쓰기 마감 시간
- 처음 등장: [P3 Day 32](#/day/p3-d32)

소켓에 데이터를 보내는 작업을 정해진 시각까지만 기다리는 규칙이에요(deadline). 상대가 읽지 않으면 운영체제의 보내기 버퍼가 차서 보내기가 끝나지 않고 멈출 수 있어요. 마감 시간을 넘기면 실패로 보고 연결을 정리해서 끊긴 휴대폰이 자리를 오래 차지하지 않게 해요.

### Docker
- 처음 등장: [P3 Day 33](#/day/p3-d33)

프로그램과 그 실행 환경을 컨테이너로 묶어 어느 컴퓨터에서나 같게 실행하는 도구예요. 이미지를 만들고(build), 받아 오고(pull), 컨테이너로 실행(run)해요. 이 교재에서는 PostgreSQL을 띄우고 게임 서버를 한 이미지로 묶을 때 써요.

### 컨테이너
- 처음 등장: [P3 Day 33](#/day/p3-d33)

이미지를 바탕으로 실행된, 다른 프로그램과 격리된 프로세스예요. 자기만의 파일 시스템·네트워크를 가진 것처럼 동작하지만 가상 머신보다 훨씬 가벼워요. 지워도 이미지는 남아서 언제든 같은 상태로 다시 만들 수 있어요.

### 컨테이너 이미지
- 처음 등장: [P3 Day 33](#/day/p3-d33)

프로그램과 실행에 필요한 파일·설정을 층(레이어)으로 쌓아 굳힌 읽기 전용 틀이에요. `postgres:18`처럼 이름과 태그로 부르고, 이 틀로 컨테이너를 몇 개든 만들어요. Dockerfile로 직접 만들 수도 있어요.

### Docker Hub
- 처음 등장: [P3 Day 33](#/day/p3-d33)

Docker 이미지를 올리고 받는 공개 저장소(레지스트리)예요. `docker run hello-world`나 `image: postgres:18`처럼 쓰면 기본으로 여기서 이미지를 받아요. 로그인하지 않은 다운로드에는 횟수 제한이 있어요.

### Docker Desktop
- 처음 등장: [P3 Day 33](#/day/p3-d33)

Windows와 macOS에서 Docker를 쓰게 해 주는 프로그램이에요. Windows에서는 WSL 2 위의 가벼운 Linux에서 Linux 컨테이너를 실행하고, 작업 표시줄의 고래 아이콘으로 상태를 보여 줘요. 개인 학습과 작은 사업체는 무료로 쓸 수 있어요(조건은 작성 기준일 2026-11 기준).

### WSL 2
- 처음 등장: [P3 Day 33](#/day/p3-d33)

Windows 안에서 진짜 Linux 커널을 가벼운 가상 머신으로 돌리는 기능이에요(Windows Subsystem for Linux 2). `wsl --install`로 켜고 `wsl --update`로 업데이트해요. Docker Desktop이 Linux 컨테이너를 실행하는 바탕으로 써요.

### 하드웨어 가상화
- 처음 등장: [P3 Day 33](#/day/p3-d33)

CPU가 가상 머신을 빠르고 안전하게 돌리도록 돕는 기능이에요(Intel VT-x, AMD-V). PC의 BIOS/UEFI 설정에서 꺼져 있으면 WSL 2와 Docker Desktop이 동작하지 않아요. 작업 관리자 → 성능 → CPU의 "가상화" 항목에서 켜져 있는지 볼 수 있어요.

### PostgreSQL
- 처음 등장: [P3 Day 34](#/day/p3-d34)

많은 서비스가 쓰는 오픈 소스 관계형 데이터베이스 서버예요. 파일 하나인 SQLite와 달리 따로 실행되는 서버 프로그램이고 여러 연결을 동시에 받아요. 이 교재는 PostgreSQL 18을 Docker 이미지나 Windows 설치 프로그램으로 써요.

### psql
- 처음 등장: [P3 Day 34](#/day/p3-d34)

PostgreSQL에 접속해 SQL을 직접 입력하는 명령행 프로그램이에요. `\dt`(표 목록), `\d 표`(구조), `\q`(끝내기) 같은 역슬래시 명령도 있어요. SQL 문장은 세미콜론(`;`)으로 끝내야 실행돼요.

### Docker Compose
- 처음 등장: [P3 Day 34](#/day/p3-d34)

컨테이너 여러 개의 이미지·환경 변수·포트·볼륨을 YAML 파일(`docker-compose.yml`) 하나에 적어 한 번에 띄우고 끄는 도구예요. `docker compose up -d`, `docker compose down` 같은 명령을 써요. 서버와 DB처럼 함께 도는 서비스를 묶기에 좋아요.

### 볼륨
- 처음 등장: [P3 Day 34](#/day/p3-d34)

컨테이너가 지워져도 남도록 Docker가 따로 관리하는 데이터 저장 공간이에요. PostgreSQL 컨테이너의 데이터 폴더를 볼륨에 연결하면 `docker compose down` 뒤에도 기록이 남아요. `docker compose down -v`는 볼륨까지 지워서 데이터가 사라져요.

### 포트 매핑
- 처음 등장: [P3 Day 34](#/day/p3-d34)

내 PC의 포트를 컨테이너 안의 포트에 연결하는 설정이에요. `127.0.0.1:5432:5432`는 "이 PC의 5432번으로 온 연결을 컨테이너의 5432번으로 보내되, 이 PC 안에서만"이라는 뜻이에요. 포트가 이미 쓰이고 있으면 컨테이너가 시작하지 못해요.

### SQLx
- 처음 등장: [P3 Day 35](#/day/p3-d35)

Rust에서 PostgreSQL 같은 데이터베이스를 비동기로 쓰게 해 주는 라이브러리예요. SQL을 문자열로 쓰고 값은 `$1`, `$2` 자리에 `.bind()`로 넣어서 SQL 인젝션을 막아요. 연결 풀과 마이그레이션 기능도 들어 있어요.

### 연결 풀
- 처음 등장: [P3 Day 35](#/day/p3-d35)

데이터베이스 연결 몇 개를 미리 열어 두고 요청마다 빌려 쓰고 돌려주는 방식이에요(connection pool). 요청마다 새로 연결하는 것보다 빠르고, 동시에 열리는 연결 수를 제한할 수 있어요. SQLx에서는 `PgPool`이 연결 풀이에요.

### 트랜잭션
- 처음 등장: [P3 Day 35](#/day/p3-d35)

여러 개의 데이터베이스 작업을 "전부 성공하거나 전부 취소"되는 한 덩어리로 묶는 것이에요. 시작(`begin`) 후 작업들을 하고 `commit`해야 반영되고, 중간에 실패하면 아무것도 저장되지 않아요. 경기 한 판과 그 점수들을 함께 저장할 때 써요.

### 데이터베이스 인덱스
- 처음 등장: [P3 Day 35](#/day/p3-d35)

표에서 원하는 행을 빨리 찾도록 데이터베이스가 따로 만들어 두는 정렬된 찾아보기 구조예요. 책 뒤의 색인처럼 모든 행을 처음부터 읽지 않아도 돼요. 대신 저장할 때마다 인덱스도 고쳐야 해서 꼭 필요한 열에만 만들어요.

### 리더보드
- 처음 등장: [P3 Day 36](#/day/p3-d36)

플레이어들의 점수를 높은 순으로 보여 주는 순위표예요. 이 게임은 닉네임별 최고 점수를 최근 24시간과 전체 기간으로 보여 줘요. 데이터베이스에 저장한 경기 결과를 SQL로 모아서 만들어요.

### 집계 함수
- 처음 등장: [P3 Day 36](#/day/p3-d36)

여러 행을 하나의 값으로 모아 계산하는 SQL 함수예요. `MAX`(가장 큰 값), `COUNT`(개수), `SUM`(합계), `AVG`(평균) 등이 있어요. `GROUP BY`와 함께 쓰면 "닉네임별 최고 점수"처럼 묶음마다 계산해요.

### tracing
- 처음 등장: [P3 Day 37](#/day/p3-d37)

Rust에서 로그와 실행 흐름을 기록하는 라이브러리예요. `tracing::info!`, `warn!`, `error!`처럼 수준을 정해 기록하고, `room = %code` 같은 필드를 붙일 수 있어요. `RUST_LOG` 환경 변수로 얼마나 자세히 볼지 정해요.

### .env 파일
- 처음 등장: [P3 Day 37](#/day/p3-d37)

환경 변수 값을 `이름=값` 줄로 적어 둔 개인 설정 파일이에요. 이 게임 서버는 시작할 때 `dotenvy` 크레이트로 이 파일을 읽어요. 비밀번호가 들어갈 수 있으므로 저장소에는 예시 파일(`.env.example`)만 올리고 `.env`는 `.gitignore`에 넣어요.

### 우아한 종료
- 처음 등장: [P3 Day 37](#/day/p3-d37)

서버를 끌 때 새 연결은 받지 않되, 처리 중인 요청은 마저 끝내고 정리한 뒤 종료하는 방식이에요(graceful shutdown). 갑자기 끊는 것보다 데이터 손실과 오류가 적어요. Axum에서는 `with_graceful_shutdown`에 종료 신호를 기다리는 Future를 넘겨요.

### 종료 신호
- 처음 등장: [P3 Day 37](#/day/p3-d37)

운영체제가 프로그램에게 "이제 끝내 달라"고 알리는 신호예요. 터미널의 `Ctrl + C`, Linux의 SIGTERM(`docker stop`이 보냄) 등이 있어요. 서버는 이 신호를 받으면 우아한 종료를 시작해요.

### Clippy
- 처음 등장: [P3 Day 38](#/day/p3-d38)

Rust 코드에서 흔한 실수나 더 좋은 쓰는 법을 찾아 주는 공식 린터예요. `cargo clippy`로 실행하고, `-D warnings`를 붙이면 경고 하나도 실패로 처리해요. 경고마다 이름(예: `needless_return`)과 고치는 법을 알려 줘요.

### rustfmt
- 처음 등장: [P3 Day 38](#/day/p3-d38)

Rust 코드의 들여쓰기·줄바꿈·띄어쓰기를 정해진 규칙으로 자동 정리하는 공식 포매터예요. `cargo fmt`로 고치고 `cargo fmt --check`로 정리가 필요한지만 검사해요. 모두가 같은 모양으로 쓰게 되어 코드 리뷰가 쉬워져요.

### 린터
- 처음 등장: [P3 Day 38](#/day/p3-d38)

코드를 실행하지 않고 읽어서 버그가 될 만한 곳이나 나쁜 습관을 찾아 알려 주는 도구예요. 포매터가 모양을 다듬는다면 린터는 내용을 검사해요. Rust의 Clippy가 대표적인 린터예요.

### 릴리스 빌드
- 처음 등장: [P3 Day 39](#/day/p3-d39)

최적화를 켜고 만든 실행 파일이에요(`cargo build --release`). 디버그 빌드보다 만들기는 오래 걸리지만 훨씬 빠르게 실행되고, 정수 넘침 검사 같은 디버그용 검사가 빠져요. 결과는 `target\release` 폴더에 생기고, 실제 방송이나 배포에는 릴리스 빌드를 써요.

### 부하 테스트
- 처음 등장: [P3 Day 39](#/day/p3-d39)

많은 사용자가 동시에 쓰는 상황을 일부러 만들어 서버가 버티는지 확인하는 테스트예요. 응답 시간, CPU·메모리 사용량, 오류 수를 재요. 이 교재에서는 봇 수십 명을 한 방에 넣어 시험해요.

### 봇
- 처음 등장: [P3 Day 39](#/day/p3-d39)

사람 대신 정해진 동작을 자동으로 하는 프로그램이에요. 이 교재의 부하 테스트 봇은 방에 참가해 무작위 방향을 보내고, 통합 테스트의 봇은 정해진 메시지를 보내고 답을 검사해요. 진짜 사용자를 모으지 않고도 여러 명이 접속한 상황을 만들 수 있어요.

### 대역폭
- 처음 등장: [P3 Day 39](#/day/p3-d39)

네트워크로 1초에 보내거나 받을 수 있는 데이터의 양이에요(예: KB/s, Mbps). 게임 서버가 보내는 양은 대략 "스냅샷 크기 × 초당 횟수 × 연결 수"예요. 대역폭을 아끼려고 스냅샷 빈도를 틱 레이트보다 낮게 정해요.

### Dockerfile
- 처음 등장: [P3 Day 40](#/day/p3-d40)

컨테이너 이미지를 만드는 순서를 적은 글자 파일이에요. `FROM`(바탕 이미지), `COPY`(파일 복사), `RUN`(명령 실행), `ENV`(환경 변수), `CMD`(시작 명령) 같은 줄을 위에서부터 실행해요. 줄 하나하나가 이미지의 층(레이어)이 돼요.

### 멀티스테이지 빌드
- 처음 등장: [P3 Day 40](#/day/p3-d40)

Dockerfile 안에서 `FROM … AS 이름`으로 단계를 여러 개 나누고, 앞 단계의 결과물만 마지막 이미지로 복사하는 방식이에요. Rust·Node 같은 무거운 빌드 도구는 최종 이미지에 들어가지 않아 이미지가 작고 안전해져요. 이 게임은 wasm → 클라이언트 → 서버 → 실행 이미지의 4단계예요.

### 레이어 캐시
- 처음 등장: [P3 Day 40](#/day/p3-d40)

Docker가 Dockerfile의 각 단계 결과를 저장해 두었다가, 그 단계의 입력이 바뀌지 않았으면 다시 실행하지 않고 재사용하는 기능이에요. 그래서 자주 바뀌지 않는 것(의존성 설치)을 위에, 자주 바뀌는 것(소스 복사)을 아래에 둬요. 입력이 하나라도 바뀌면 그 단계부터 아래는 다시 실행돼요.

### .dockerignore
- 처음 등장: [P3 Day 40](#/day/p3-d40)

`docker build`가 빌드 재료(빌드 컨텍스트)로 보내지 않을 파일·폴더 목록이에요. `target`, `node_modules`처럼 크고 다시 만들 수 있는 것과 `.env`처럼 비밀이 든 것을 적어요. 빌드가 빨라지고 비밀이 이미지에 들어가지 않아요.

### 도메인 이름
- 처음 등장: [P3 Day 41](#/day/p3-d41)

`example.com`처럼 사람이 기억하기 쉬운 인터넷 주소 이름이에요. 실제 통신은 IP 주소로 하므로, 도메인 이름은 DNS를 통해 IP 주소로 바뀌어요. 도메인 등록 업체에서 사거나, 호스팅 서비스가 주는 하위 주소를 무료로 쓸 수 있어요.

### DNS
- 처음 등장: [P3 Day 41](#/day/p3-d41)

도메인 이름을 IP 주소로 바꿔 주는 인터넷의 전화번호부 같은 시스템이에요(Domain Name System). 브라우저가 주소를 열면 먼저 DNS에 IP를 물어보고 그 IP로 접속해요. 설정을 바꾸면 전 세계에 반영되기까지 시간이 걸릴 수 있어요.

### TLS
- 처음 등장: [P3 Day 41](#/day/p3-d41)

인터넷 통신을 암호화하고 상대가 진짜 그 서버인지 인증서로 확인하는 보안 프로토콜이에요(Transport Layer Security). HTTPS와 WSS가 TLS 위에서 동작해요. 클라우드 데이터베이스도 연결에 TLS를 요구하는 경우가 많아요.

### WSS
- 처음 등장: [P3 Day 41](#/day/p3-d41)

TLS로 암호화한 WebSocket이에요(HTTPS의 WebSocket판)(`wss://`). HTTPS로 연 페이지는 암호화되지 않은 `ws://`에 연결할 수 없어서(혼합 콘텐츠) 배포한 게임은 WSS를 써야 해요. 이 게임은 페이지 주소가 `https:`면 자동으로 `wss:`를 골라요.

### 관리형 데이터베이스
- 처음 등장: [P3 Day 42](#/day/p3-d42)

설치·백업·업데이트를 클라우드 업체가 대신 맡아 주는 데이터베이스 서비스예요. 직접 서버를 관리하지 않아도 되지만, 무료 요금제는 기간·용량 제한이 있고 TLS 연결을 요구하는 경우가 많아요. 이 교재의 배포 실습은 랭킹 없이(데이터베이스 없이) 진행해요.

### 콜드 스타트
- 처음 등장: [P3 Day 42](#/day/p3-d42)

잠들어 있던(꺼져 있던) 서버가 첫 요청을 받고 다시 켜지느라 첫 응답이 늦는 현상이에요. 무료 호스팅은 일정 시간 요청이 없으면 서버를 재우기 때문에 자주 생겨요. 방송 전에 미리 한 번 접속해 깨워 두면 좋아요.

### 방송 리허설
- 처음 등장: [P3 Day 43](#/day/p3-d43)

실제 방송과 같은 장비·순서로 미리 한 번 끝까지 진행해 보는 연습이에요. OBS 화면 구성, 시청자 참가, 서버가 꺼졌을 때의 복구까지 확인해요. 리허설에서 찾은 문제를 체크리스트로 남겨 본방송에서 반복하지 않게 해요.

### 채팅 명령어
- 처음 등장: [P3 Day 44](#/day/p3-d44)

방송 채팅에 `!join`처럼 약속된 글자를 입력해 기능을 실행하는 방식이에요. 채팅 이벤트를 받는 봇이나 서버가 글자를 해석해서 동작해요. 휴대폰을 따로 열지 않아도 채팅만으로 참여할 수 있게 해 줘요.

### 수평 확장
- 처음 등장: [P3 Day 44](#/day/p3-d44)

서버 한 대를 더 좋게 바꾸는 대신(수직 확장) 같은 서버를 여러 대로 늘려 일을 나누는 방법이에요. 더 많은 사용자를 받을 수 있지만, 상태(이 게임의 방)가 서버마다 따로 있으면 사용자를 같은 서버로 보내는 규칙이나 공유 저장소가 필요해요. 이 교재의 서버는 방이 메모리에 있어서 지금은 한 대로만 운영해요.
