# P2 용어

P2(스트리머 허브)에서 처음 가르치는 용어예요. P1에서 배운 용어는 P1 사전 항목을 보세요. 항목은 빌드가 가나다순으로 정렬해요.

## Day 1 · 풀스택 큰 그림

### 프론트엔드
- 처음 등장: [P2 Day 1](#/day/p2-d01)

사용자가 직접 보고 누르는 화면 쪽 프로그램이에요. 브라우저 안에서 HTML·CSS·JavaScript(TypeScript)로 만들어요. 스트리머 허브에서는 `client` 폴더가 프론트엔드예요.

### 백엔드
- 처음 등장: [P2 Day 1](#/day/p2-d01)

화면 뒤에서 데이터를 저장하고, 규칙을 검사하고, 요청에 답하는 서버 쪽 프로그램이에요. 사용자 눈에는 보이지 않아요. 스트리머 허브에서는 C#으로 만든 `server` 폴더가 백엔드예요.

### 풀스택
- 처음 등장: [P2 Day 1](#/day/p2-d01)

프론트엔드와 백엔드, 데이터베이스까지 한 서비스의 모든 층을 함께 다루는 것을 말해요. 이렇게 일하는 개발자를 풀스택 개발자라고 불러요. P2에서는 화면·서버·DB를 모두 직접 만들어요.

### 클라이언트
- 처음 등장: [P2 Day 1](#/day/p2-d01)

서버에 무언가를 요청하는 쪽 프로그램이에요. 웹에서는 보통 브라우저와 그 안에서 도는 화면 코드가 클라이언트예요. 서버가 "주는 쪽"이라면 클라이언트는 "받아서 보여 주는 쪽"이에요.

### 데이터베이스
- 처음 등장: [P2 Day 1](#/day/p2-d01)

데이터를 정해진 모양으로 오래 보관하고, 빠르게 찾고 고칠 수 있게 해 주는 저장소예요. 프로그램을 껐다 켜도 데이터가 남아요. 줄여서 DB라고 하고, P2에서는 SQLite를 써요.

### API
- 처음 등장: [P2 Day 1](#/day/p2-d01)

프로그램끼리 정해진 방법으로 기능이나 데이터를 주고받게 해 주는 약속이에요. 웹에서는 보통 "이 주소로 이렇게 요청하면 이런 JSON을 돌려준다"는 규칙 모음을 말해요. 스트리머 허브의 `/api/streamers` 같은 주소가 API예요.

### 요청
- 처음 등장: [P2 Day 1](#/day/p2-d01)

클라이언트가 서버에게 "이것을 주세요" 또는 "이것을 해 주세요"라고 보내는 메시지예요. 주소, 방법(메서드), 필요하면 보낼 데이터가 들어 있어요. 영어로는 request예요.

### 응답
- 처음 등장: [P2 Day 1](#/day/p2-d01)

서버가 요청을 받고 돌려보내는 메시지예요. 결과를 나타내는 상태 코드와 내용(예: HTML 파일, JSON 데이터)이 들어 있어요. 영어로는 response예요.

## Day 2 · 터미널 기초

### Windows Terminal
- 처음 등장: [P2 Day 2](#/day/p2-d02)

PowerShell 같은 셸을 탭으로 여러 개 열어 쓰게 해 주는 Windows 11의 터미널 앱이에요. 시작 메뉴에서 "터미널"을 검색해 열어요. 창 안에서 실제로 명령을 처리하는 것은 PowerShell이에요.

### 프롬프트
- 처음 등장: [P2 Day 2](#/day/p2-d02)

터미널이 "명령을 입력하세요"라고 기다리며 보여 주는 앞부분 글자예요. PowerShell에서는 `PS C:\dev\streamer-hub>`처럼 현재 위치가 함께 보여요. 프롬프트가 다시 보이면 앞 명령이 끝났다는 뜻이에요.

### 현재 위치
- 처음 등장: [P2 Day 2](#/day/p2-d02)

터미널이 지금 "들어가 있는" 폴더예요. 상대 경로와 많은 명령이 이 폴더를 기준으로 동작해요. PowerShell에서는 프롬프트에 보이고, `Get-Location`으로도 확인할 수 있어요.

### 탭 완성
- 처음 등장: [P2 Day 2](#/day/p2-d02)

명령이나 경로를 몇 글자만 치고 `Tab` 키를 누르면 터미널이 나머지를 채워 주는 기능이에요. 오타를 줄이고 긴 경로를 빨리 입력할 수 있어요. 여러 후보가 있으면 `Tab`을 누를 때마다 다음 후보로 바뀌어요.

## Day 3 · Node.js와 npm

### Node.js
- 처음 등장: [P2 Day 3](#/day/p2-d03)

브라우저 밖에서 JavaScript를 실행하게 해 주는 프로그램이에요. 개발 도구(TypeScript 컴파일러, Vite 등)가 Node.js 위에서 돌아가요. 터미널에서 `node --version`으로 설치를 확인해요.

### npm
- 처음 등장: [P2 Day 3](#/day/p2-d03)

Node.js와 함께 설치되는 패키지 관리자예요. 다른 사람이 만든 코드 묶음(패키지)을 내려받고, 버전을 기록하고, 정해 둔 명령(`npm run dev` 등)을 실행해 줘요. 이름은 Node Package Manager에서 왔어요.

### 패키지
- 처음 등장: [P2 Day 3](#/day/p2-d03)

다른 프로젝트에서 가져다 쓸 수 있게 묶어서 공개한 코드 묶음이에요. npm 패키지는 npm 레지스트리에서, C# 패키지는 NuGet에서 내려받아요. 예: `typescript`, `vite`.

### 의존성
- 처음 등장: [P2 Day 3](#/day/p2-d03)

내 프로젝트가 동작하려면 꼭 있어야 하는 다른 패키지예요. `package.json`에 이름과 버전 범위를 적어 두면 npm이 알아서 설치해요. 개발할 때만 필요한 것은 `devDependencies`에 따로 적어요.

### package.json
- 처음 등장: [P2 Day 3](#/day/p2-d03)

Node.js 프로젝트의 이름, 실행 명령(`scripts`), 의존성 목록을 적어 두는 JSON 파일이에요. 프로젝트 폴더 맨 위에 있어요. `npm init -y`로 처음 만들 수 있어요.

### node_modules
- 처음 등장: [P2 Day 3](#/day/p2-d03)

npm이 내려받은 패키지가 실제로 들어 있는 폴더예요. 파일이 아주 많고 언제든 `npm install`로 다시 만들 수 있어서 직접 고치거나 Git에 올리지 않아요. 보통 `.gitignore`에 넣어요.

### package-lock.json
- 처음 등장: [P2 Day 3](#/day/p2-d03)

npm이 실제로 설치한 모든 패키지의 정확한 버전을 기록한 파일이에요. 이 파일이 있으면 다른 컴퓨터에서도 `npm ci`로 똑같은 버전을 설치할 수 있어요. 직접 고치지 않고 Git에는 함께 올려요.

### npx
- 처음 등장: [P2 Day 3](#/day/p2-d03)

패키지에 들어 있는 명령을 바로 실행해 주는 도구예요. 프로젝트에 설치된 패키지면 그것을, 없으면 잠깐 내려받아 실행해요. 예: `npx tsc --version`.

### LTS
- 처음 등장: [P2 Day 3](#/day/p2-d03)

Long Term Support의 줄임말로, 오랫동안 보안·버그 수정을 해 주기로 약속한 안정 버전이에요. 처음 배우는 사람은 LTS를 설치하는 것이 안전해요. Node.js와 .NET 모두 LTS 버전이 있어요.

### 환경 변수
- 처음 등장: [P2 Day 3](#/day/p2-d03)

운영 체제가 프로그램에게 알려 주는 이름=값 설정이에요. 프로그램 코드를 고치지 않고도 동작을 바꿀 수 있어요. PowerShell에서는 `$env:이름 = "값"`으로 그 창에서만 정할 수 있어요.

### PATH
- 처음 등장: [P2 Day 3](#/day/p2-d03)

명령 이름만 쳐도 실행 파일을 찾을 수 있도록 Windows가 뒤져 보는 폴더 목록을 담은 환경 변수예요. 프로그램을 설치하면 이 목록에 폴더가 추가되는데, 이미 열려 있던 터미널은 예전 목록을 기억해요. 그래서 설치한 뒤에는 터미널을 새로 열어야 해요.

### 실행 정책
- 처음 등장: [P2 Day 3](#/day/p2-d03)

PowerShell이 스크립트 파일(`.ps1`)을 실행해도 되는지 정하는 안전장치예요. Windows 기본값에서는 `npm.ps1` 같은 스크립트가 막힐 수 있어요. 이 교재는 공식 권장대로 `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser`로 내 계정만 바꿔요.

## Day 4 · TypeScript 시작

### TypeScript
- 처음 등장: [P2 Day 4](#/day/p2-d04)

JavaScript에 "타입"을 더한 언어예요. 코드를 실행하기 전에 잘못된 값이나 오타를 찾아 줘요. 브라우저는 TypeScript를 바로 읽지 못해서 JavaScript로 바꾼 뒤 실행해요.

### 정적 타입
- 처음 등장: [P2 Day 4](#/day/p2-d04)

변수나 매개변수에 들어갈 값의 종류(타입)를 코드를 실행하기 전에 정하고 검사하는 방식이에요. 숫자 칸에 글자를 넣으면 실행하기 전에 오류가 나요. TypeScript와 C#이 정적 타입 언어이고, JavaScript는 실행 중에 타입이 정해지는 언어예요.

### 타입 표기
- 처음 등장: [P2 Day 4](#/day/p2-d04)

변수나 매개변수 이름 뒤에 `: number`처럼 타입을 직접 적는 것이에요. 예: `let viewers: number = 0;`. 영어로는 type annotation이에요.

### 타입 추론
- 처음 등장: [P2 Day 4](#/day/p2-d04)

타입을 적지 않아도 넣은 값을 보고 컴파일러가 타입을 알아서 정하는 기능이에요. `const title = '저녁 방송';`이라고 쓰면 `title`은 `string`이 돼요. C#의 `var`도 같은 생각이에요.

### 컴파일
- 처음 등장: [P2 Day 4](#/day/p2-d04)

사람이 쓴 코드를 검사하고 컴퓨터(또는 다른 프로그램)가 실행할 수 있는 형태로 바꾸는 일이에요. TypeScript는 JavaScript로, C#은 .NET이 실행하는 파일(`.dll`)로 컴파일돼요. 이 일을 하는 프로그램을 컴파일러라고 해요.

### tsc
- 처음 등장: [P2 Day 4](#/day/p2-d04)

TypeScript 컴파일러의 명령 이름이에요. 타입 오류를 찾아 알려 주고, TypeScript 파일을 JavaScript 파일로 바꿔요. 프로젝트에서는 `npx tsc`로 실행하고, `npx tsc --noEmit`은 검사만 해요.

### tsconfig.json
- 처음 등장: [P2 Day 4](#/day/p2-d04)

TypeScript 컴파일러가 어떤 파일을 어떤 규칙으로 컴파일할지 적어 두는 설정 파일이에요. 원본 폴더, 결과 폴더, 얼마나 엄격하게 검사할지 등을 정해요. `npx tsc --init`으로 처음 만들 수 있어요.

### strict 모드
- 처음 등장: [P2 Day 4](#/day/p2-d04)

TypeScript의 엄격한 검사 묶음을 한꺼번에 켜는 설정(`"strict": true`)이에요. 예를 들어 `null`일 수도 있는 값을 확인 없이 쓰면 오류로 알려 줘요. 처음에는 귀찮아도 실수를 일찍 찾게 해 줘서 이 교재는 항상 켜 둬요.

## Day 5 · 타입 설계

### 인터페이스
- 처음 등장: [P2 Day 5](#/day/p2-d05)

데이터나 클래스가 갖춰야 할 모양(어떤 칸·메서드가 있는지)을 이름 붙여 정해 둔 약속이에요. TypeScript에서는 `interface Streamer { name: string; }`처럼 객체의 모양을 정하고, C#에서는 클래스가 `: INotifier`처럼 구현을 선언해야 하는 약속이 돼요. 이름이 같아도 두 언어에서 쓰는 방식이 조금 달라요.

### 타입 별칭
- 처음 등장: [P2 Day 5](#/day/p2-d05)

`type` 키워드로 타입에 새 이름을 붙이는 것이에요. 예: `type Platform = 'chzzk' | 'youtube' | 'soop' | 'other';`. 객체 모양은 `interface`로, 유니온처럼 여러 타입을 묶을 때는 `type`으로 쓰는 경우가 많아요.

### 유니온 타입
- 처음 등장: [P2 Day 5](#/day/p2-d05)

`A | B`처럼 "이것 또는 저것"을 뜻하는 타입이에요. `string | null`은 글자이거나 비어 있음(`null`)이라는 뜻이에요. 쓰기 전에 어느 쪽인지 확인(좁히기)해야 해요.

### 리터럴 타입
- 처음 등장: [P2 Day 5](#/day/p2-d05)

`'chzzk'`처럼 특정한 값 하나만 허용하는 타입이에요. 유니온과 함께 쓰면 정해진 몇 개의 글자만 들어가게 할 수 있어요. 오타(`'Chzzk'`)를 컴파일 단계에서 잡아 줘요.

### 선택적 프로퍼티
- 처음 등장: [P2 Day 5](#/day/p2-d05)

TypeScript 객체 타입에서 이름 뒤에 `?`를 붙여 "없어도 되는 칸"으로 만든 것이에요. 예: `nickname?: string`. 이 교재의 서버 데이터는 칸이 항상 오고 값만 비어 있을 수 있어서 `string | null`을 더 많이 써요.

### 타입 좁히기
- 처음 등장: [P2 Day 5](#/day/p2-d05)

`if`나 `typeof` 같은 검사로 유니온 타입의 값이 지금 어떤 타입인지 확실하게 만드는 것이에요. `if (avatarUrl !== null)` 블록 안에서는 `avatarUrl`이 `string`으로 다뤄져요. TypeScript가 검사 결과를 기억해 주기 때문에 가능해요.

### null 병합 연산자
- 처음 등장: [P2 Day 5](#/day/p2-d05)

왼쪽 값이 `null`이나 `undefined`이면 오른쪽 값을 쓰는 연산자 `??`예요. 예: `streamer.avatarUrl ?? '사진 없음'`. JavaScript·TypeScript와 C#에서 같은 기호로 써요.

### 옵셔널 체이닝
- 처음 등장: [P2 Day 5](#/day/p2-d05)

`a?.b`처럼 `a`가 `null`이나 `undefined`이면 오류를 내지 않고 바로 `undefined`(C#은 `null`)를 돌려주는 문법이에요. 비어 있을 수 있는 객체의 칸을 안전하게 읽을 때 써요. `??`와 함께 `streamer?.name ?? ''`처럼 자주 써요.

## Day 6 · 함수·제네릭·모듈

### 함수 타입
- 처음 등장: [P2 Day 6](#/day/p2-d06)

함수가 어떤 매개변수를 받고 무엇을 돌려주는지 나타낸 타입이에요. 예: `(s: Streamer) => boolean`은 스트리머 하나를 받아 참·거짓을 돌려주는 함수예요. 함수를 다른 함수에 넘길 때 그 모양을 정해 줘요.

### 제네릭
- 처음 등장: [P2 Day 6](#/day/p2-d06)

타입을 나중에 정할 수 있게 비워 두고, 쓰는 쪽이 채워 넣게 하는 문법이에요. `function first<T>(items: T[]): T | undefined`는 어떤 배열이든 받아서 같은 타입의 값을 돌려줘요. TypeScript의 `Paged<T>`와 C#의 `List<T>`, `PagedResult<T>`가 제네릭이에요.

### 타입 매개변수
- 처음 등장: [P2 Day 6](#/day/p2-d06)

제네릭에서 `<T>`처럼 꺾쇠 안에 쓰는 "타입 자리"의 이름이에요. 쓰는 쪽이 `getJson<Streamer[]>(…)`처럼 실제 타입을 넣으면 `T`가 그 타입으로 바뀌어요. 관례로 `T`, `TKey`, `TValue` 같은 이름을 써요.

### 모듈
- 처음 등장: [P2 Day 6](#/day/p2-d06)

## Day 7 · Vite 프로젝트

### Vite
- 처음 등장: [P2 Day 7](#/day/p2-d07)

프론트엔드 프로젝트를 만들고, 개발 서버로 띄우고, 배포용으로 빌드해 주는 도구예요. 이름은 프랑스어로 "빠르다"는 뜻이에요(발음 "비트"). 이 교재는 `vanilla-ts` 템플릿으로 프레임워크 없이 TypeScript만 써요.

### 개발 서버
- 처음 등장: [P2 Day 7](#/day/p2-d07)

개발하는 동안 내 컴퓨터에서 웹페이지를 보여 주는 작은 서버예요. 파일을 저장하면 바로 화면에 반영해 줘요. Vite 개발 서버는 기본으로 `http://localhost:5173`에서 열려요.

### localhost
- 처음 등장: [P2 Day 7](#/day/p2-d07)

"바로 이 컴퓨터"를 가리키는 특별한 주소 이름이에요. `http://localhost:5173`은 내 컴퓨터에서 5173번 포트로 기다리는 프로그램에 연결하라는 뜻이에요. 다른 컴퓨터에서는 이 주소로 내 컴퓨터에 들어올 수 없어요.

### 포트
- 처음 등장: [P2 Day 7](#/day/p2-d07)

한 컴퓨터 안에서 여러 서버 프로그램을 구별하는 번호예요. 주소 끝의 `:5173`, `:5250`이 포트 번호예요. 한 포트는 한 프로그램만 쓸 수 있어서, 이미 쓰는 포트로 또 켜면 "사용 중" 오류가 나요.

### HMR
- 처음 등장: [P2 Day 7](#/day/p2-d07)

Hot Module Replacement의 줄임말로, 파일을 저장하면 페이지 전체를 새로 고치지 않고 바뀐 부분만 바로 바꿔 끼우는 기능이에요. Vite 개발 서버가 제공해요. 고치고 확인하는 시간이 크게 줄어요.

### 빌드
- 처음 등장: [P2 Day 7](#/day/p2-d07)

개발용 원본 코드를 배포할 수 있는 결과물로 만드는 일이에요. Vite의 `npm run build`는 TypeScript를 검사·변환하고 파일을 묶어 `dist` 폴더에 넣어요. C#에서는 `dotnet build`가 프로젝트를 컴파일해요.

### 타입 단언
- 처음 등장: [P2 Day 7](#/day/p2-d07)

"이 값의 타입은 내가 알아요"라고 TypeScript에게 알려 주는 문법이에요. 값 뒤의 `!`는 "null이 아니에요", `as Platform`은 "이 타입으로 봐 주세요"라는 뜻이에요. 실행 중에 검사하지는 않으니 확실할 때만 써요.

### innerHTML
- 처음 등장: [P2 Day 7](#/day/p2-d07)

요소 안에 넣을 내용을 HTML 글자로 정하는 DOM 속성이에요. 글자 속의 태그가 실제 요소로 바뀌어 화면 틀을 한 번에 만들기 편해요. 사용자가 쓴 글을 넣으면 그 안의 스크립트가 실행될 수 있어서, 이 교재는 우리가 직접 쓴 고정 글자만 넣고 사용자 데이터는 `textContent`로 넣어요.

## Day 8 · 비동기 깊게

### Promise
- 처음 등장: [P2 Day 8](#/day/p2-d08)

지금은 없지만 나중에 도착할 값(또는 오류)을 나타내는 JavaScript 객체예요. 기다리는 중(대기), 성공(이행), 실패(거부) 세 상태가 있어요. `await`는 Promise가 끝날 때까지 기다렸다가 값을 꺼내고, `Promise.all`은 여러 Promise를 동시에 기다려요.

### 구조 분해 할당
- 처음 등장: [P2 Day 8](#/day/p2-d08)

배열이나 객체의 값을 한 번에 여러 변수로 나눠 담는 문법이에요. 예: `const [streamers, schedules] = await Promise.all([...]);`. 객체는 `const { path, query } = readHash();`처럼 칸 이름으로 꺼내요.

### 전개 구문
- 처음 등장: [P2 Day 8](#/day/p2-d08)

`...`을 배열 앞에 붙여 안의 값들을 낱개로 펼치는 문법이에요. `list.append(...items)`는 배열의 요소를 하나씩 인수로 넘긴 것과 같아요. 영어로는 spread syntax예요.

### unknown
- 처음 등장: [P2 Day 8](#/day/p2-d08)

"어떤 값인지 아직 모른다"는 뜻의 TypeScript 타입이에요. `any`와 달리 검사(좁히기) 없이는 아무것도 할 수 없어서 안전해요. `catch (error)`의 `error`가 `unknown`이라 `instanceof` 등으로 확인한 뒤 써요.

## Day 11 · 메서드와 컬렉션

### 컬렉션
- 처음 등장: [P2 Day 11](#/day/p2-d11)

값 여러 개를 한데 모아 다루는 자료 구조를 통틀어 부르는 말이에요. C#에는 배열, `List`, `Dictionary` 등이 있어요. LINQ로 거르고 정렬할 수 있어요.

### List
- 처음 등장: [P2 Day 11](#/day/p2-d11)

크기가 자유롭게 늘고 주는 C#의 순서 있는 목록 `List<T>`예요. `Add`로 넣고 `Remove`로 빼고 `Count`로 개수를 세요. JavaScript 배열과 가장 비슷해요.

### Dictionary
- 처음 등장: [P2 Day 11](#/day/p2-d11)

키로 값을 찾는 C#의 표 `Dictionary<TKey, TValue>`예요. 예: 플랫폼 이름(키)으로 스트리머 수(값)를 찾아요. 없는 키를 `dictionary[key]`로 읽으면 예외가 나서 `TryGetValue`로 먼저 확인해요.

### nullable
- 처음 등장: [P2 Day 11](#/day/p2-d11)

`null`(값 없음)이 들어갈 수 있다고 표시한 타입이에요. C#에서는 타입 뒤에 `?`를 붙여 `string?`, `int?`처럼 써요. 이 표시가 없는 칸에 null이 들어갈 수 있으면 컴파일러가 경고해 줘요.

### out 매개변수
- 처음 등장: [P2 Day 11](#/day/p2-d11)

메서드가 반환값 말고 추가로 결과를 돌려주는 C# 매개변수예요. `int.TryParse(text, out var number)`는 성공 여부를 돌려주면서 바꾼 숫자를 `number`에 담아 줘요. `out var`로 그 자리에서 변수를 만들 수 있어요.

## Day 12 · 클래스와 객체

### C# 클래스
- 처음 등장: [P2 Day 12](#/day/p2-d12)

객체를 만들기 위한 설계도예요. 어떤 데이터(프로퍼티)와 동작(메서드)을 가질지 정해 두고, `new`로 실제 객체를 찍어 내요. C#의 `class Streamer`가 예이고, TypeScript의 `class ApiError`도 같은 문법 개념이에요(HTML·CSS의 `class` 이름표와는 다른 뜻이에요).

### 인스턴스
- 처음 등장: [P2 Day 12](#/day/p2-d12)

클래스(설계도)로 실제로 만든 객체 하나예요. `new Streamer()`를 세 번 하면 인스턴스가 세 개 생기고 각자 다른 값을 가져요. 같은 클래스의 인스턴스는 모양이 같아요.

### 프로퍼티
- 처음 등장: [P2 Day 12](#/day/p2-d12)

C# 클래스가 가진 값을 읽고 쓰는 칸이에요. `public string Name { get; set; } = "";`처럼 쓰고, `get`은 읽기, `set`은 쓰기, `init`은 처음 만들 때만 쓰기를 뜻해요. HTML의 속성(attribute)과 헷갈리지 않게 이 교재는 프로퍼티라고 불러요.

### 생성자
- 처음 등장: [P2 Day 12](#/day/p2-d12)

`new`로 인스턴스를 만들 때 자동으로 한 번 실행되는 특별한 메서드예요. 클래스 이름과 같은 이름으로 쓰고, 꼭 필요한 값을 받아 객체를 준비해요. 예: `public PostService(AppDbContext db) { _db = db; }`.

### 접근 제한자
- 처음 등장: [P2 Day 12](#/day/p2-d12)

클래스나 멤버를 어디에서 쓸 수 있는지 정하는 키워드예요. `public`은 어디서나, `private`는 그 클래스 안에서만, `internal`은 같은 프로젝트 안에서만 쓸 수 있어요. 바깥에서 함부로 바꾸면 안 되는 값을 지켜 줘요.

### static
- 처음 등장: [P2 Day 12](#/day/p2-d12)

인스턴스를 만들지 않고 클래스 이름으로 바로 쓰는 멤버를 표시하는 C# 키워드예요. `static class SeedData`처럼 클래스 전체를 static으로 만들면 인스턴스를 만들 수 없고 static 멤버만 가져요. 공통 도우미 메서드를 모아 둘 때 써요.

### record
- 처음 등장: [P2 Day 12](#/day/p2-d12)

데이터를 담는 용도로 만든 C#의 특별한 클래스예요. 담긴 값이 모두 같으면 같은 것으로 비교되고, `with`로 일부만 바꾼 복사본을 쉽게 만들어요. `record StreamerResponse(int Id, string Name)`처럼 한 줄로 쓸 수 있어 DTO에 잘 맞아요.

### 네임스페이스
- 처음 등장: [P2 Day 12](#/day/p2-d12)

클래스 이름이 겹치지 않게 묶어 주는 C#의 이름 공간이에요. 파일 위에 `namespace StreamerHub.Api.Entities;`라고 쓰면 그 파일의 클래스가 그 묶음에 들어가요. 다른 묶음의 클래스를 쓰려면 `using`으로 가져와요.

## Day 13 · 상속과 인터페이스

### 상속
- 처음 등장: [P2 Day 13](#/day/p2-d13)

이미 있는 클래스의 기능을 물려받아 새 클래스를 만드는 것이에요. C#에서는 `class AppUser : IdentityUser`처럼 콜론 뒤에 물려줄 클래스(기본 클래스)를 써요. 물려받은 것 위에 새 칸이나 동작을 더할 수 있어요.

### virtual
- 처음 등장: [P2 Day 13](#/day/p2-d13)

"물려받은 클래스가 이 메서드를 바꿔도 된다"고 기본 클래스에서 표시하는 C# 키워드예요. `virtual`이 붙은 메서드만 자식 클래스에서 `override`할 수 있어요. 표시가 없으면 바꿀 수 없다는 오류가 나요.

### override
- 처음 등장: [P2 Day 13](#/day/p2-d13)

기본 클래스의 `virtual`(또는 추상) 메서드를 자식 클래스에서 새로 정의한다고 표시하는 C# 키워드예요. 예: `public override bool IsValid(object? value)`. 같은 이름의 메서드를 불러도 실제 객체의 클래스에 따라 다른 코드가 실행돼요.

### 다형성
- 처음 등장: [P2 Day 13](#/day/p2-d13)

같은 방식으로 불러도 객체의 실제 종류에 따라 다르게 동작하는 성질이에요. `List<User>`에 팬과 관리자를 섞어 담고 모두 `Describe()`를 부르면 각자 다른 문장이 나와요. 상속과 인터페이스가 이것을 가능하게 해요.

### 패턴 매칭
- 처음 등장: [P2 Day 13](#/day/p2-d13)

값이 어떤 모양·타입인지 검사하면서 동시에 꺼내 쓰는 C# 문법이에요. `if (value is string text)`는 `value`가 문자열이면 `text`라는 이름으로 쓰게 해 줘요. `is null`, `is not null`도 패턴 매칭이에요.

## Day 16 · HTTP와 REST

### HTTP
- 처음 등장: [P2 Day 16](#/day/p2-d16)

브라우저와 서버가 요청과 응답을 주고받는 규칙(프로토콜)이에요. 요청에는 메서드·주소·헤더·본문이, 응답에는 상태 코드·헤더·본문이 들어 있어요. 웹 주소의 `http://`가 이 규칙을 쓴다는 뜻이에요.

### HTTPS
- 처음 등장: [P2 Day 16](#/day/p2-d16)

HTTP에 암호화를 더한 것이에요. 오가는 내용을 중간에서 엿보거나 바꾸지 못하게 해 줘요. 주소가 `https://`로 시작하고, 서버에는 인증서가 필요해요.

### HTTP 메서드
- 처음 등장: [P2 Day 16](#/day/p2-d16)

요청이 무엇을 하려는지 나타내는 동사예요. `GET`은 읽기, `POST`는 새로 만들기, `PUT`은 고치기, `DELETE`는 지우기에 써요. 같은 주소라도 메서드에 따라 하는 일이 달라요.

### 상태 코드
- 처음 등장: [P2 Day 16](#/day/p2-d16)

응답의 결과를 세 자리 숫자로 알려 주는 값이에요. 2xx는 성공(200 OK, 201 Created, 204 No Content), 4xx는 요청 쪽 문제(400 잘못된 요청, 401 로그인 필요, 403 권한 없음, 404 없음, 429 너무 많음), 5xx는 서버 쪽 문제예요. 화면은 이 숫자를 보고 사용자에게 보여 줄 문장을 골라요.

### HTTP 헤더
- 처음 등장: [P2 Day 16](#/day/p2-d16)

요청과 응답에 붙는 부가 정보 줄이에요. `이름: 값` 모양이고, 예를 들어 `Content-Type`은 본문의 형식, `Location`은 새로 만든 자원의 주소, `Set-Cookie`는 쿠키를 알려 줘요. 본문보다 먼저 보내져요.

### HTTP 본문
- 처음 등장: [P2 Day 16](#/day/p2-d16)

요청이나 응답에서 헤더 뒤, 빈 줄 다음에 오는 실제 내용이에요. API에서는 주로 JSON 글자가 들어 있어요. `GET` 요청이나 `204` 응답처럼 본문이 없는 경우도 있어요.

### Content-Type
- 처음 등장: [P2 Day 16](#/day/p2-d16)

본문이 어떤 형식인지 알려 주는 HTTP 헤더예요. JSON이면 `application/json`, 오류 응답(ProblemDetails)이면 `application/problem+json`이에요. JSON을 보내면서 이 헤더를 빼면 서버가 본문을 읽지 않아요.

### REST
- 처음 등장: [P2 Day 16](#/day/p2-d16)

웹 API를 설계하는 널리 쓰이는 방식이에요. 다루는 대상(자원)을 `/api/streamers/3` 같은 명사 주소로 나타내고, 할 일은 HTTP 메서드로 나타내요. 규칙이 일정해서 주소만 봐도 무슨 일을 하는지 짐작할 수 있어요.

### 엔드포인트
- 처음 등장: [P2 Day 16](#/day/p2-d16)

API에서 "이 메서드 + 이 주소"로 요청을 받는 입구 하나예요. 예: `GET /api/streamers`, `POST /api/posts`. 서버 코드에서는 엔드포인트마다 요청을 처리할 함수를 연결해요.

### .http 파일
- 처음 등장: [P2 Day 16](#/day/p2-d16)

HTTP 요청을 글자로 적어 두고 편집기에서 바로 보낼 수 있게 한 파일이에요. VS Code의 REST Client 확장이 요청 위의 Send Request를 눌러 보내고 응답을 보여 줘요. 요청 사이는 `###` 줄로 나눠요.

## Day 17 · 첫 웹 API

### ASP.NET Core
- 처음 등장: [P2 Day 17](#/day/p2-d17)

.NET으로 웹 서버와 웹 API를 만드는 Microsoft의 프레임워크예요. 요청 받기, 주소 연결, 로그인, 오류 처리 같은 기능이 들어 있어요. `dotnet new web`으로 프로젝트를 만들어요.

### Minimal API
- 처음 등장: [P2 Day 17](#/day/p2-d17)

`app.MapGet("/api/streamers", …)`처럼 주소와 처리 함수를 몇 줄로 바로 연결하는 ASP.NET Core의 API 작성 방식이에요. 컨트롤러 클래스 없이도 엔드포인트를 만들 수 있어 배우기 쉬워요. 이 교재의 서버는 모두 이 방식이에요.

### 라우트
- 처음 등장: [P2 Day 17](#/day/p2-d17)

요청 주소와 그 주소를 처리할 코드를 짝지은 규칙이에요. 서버에서는 `/api/streamers/{id}` 같은 주소 모양을, 화면의 해시 라우터에서는 `#/streamers/:id` 같은 모양을 등록해요. 들어온 주소에 맞는 라우트의 코드가 실행돼요.

### 솔루션
- 처음 등장: [P2 Day 17](#/day/p2-d17)

여러 C# 프로젝트를 한 묶음으로 관리하는 파일이에요. .NET 10에서는 `.slnx` 형식이 기본이고, 스트리머 허브는 `StreamerHub.slnx`에 API 프로젝트와 테스트 프로젝트를 담아요. 솔루션 폴더에서 `dotnet test`를 하면 묶인 프로젝트를 모두 빌드해요.

### launchSettings.json
- 처음 등장: [P2 Day 17](#/day/p2-d17)

`dotnet run`과 `dotnet watch`가 서버를 켤 때 쓰는 설정 파일이에요. `Properties` 폴더 안에 있고, 주소와 포트(`applicationUrl`), 실행 환경(`ASPNETCORE_ENVIRONMENT`) 등을 정해요. 이 교재는 `http://localhost:5250` 하나만 남겨요.

### dotnet watch
- 처음 등장: [P2 Day 17](#/day/p2-d17)

파일을 저장할 때마다 자동으로 다시 빌드하고 적용해 주는 실행 명령이에요. 바꾼 내용을 바로 반영할 수 없으면 서버를 다시 시작해요. 개발하는 동안 서버는 `dotnet watch`로 켜 둬요.

### 직렬화
- 처음 등장: [P2 Day 17](#/day/p2-d17)

프로그램 안의 객체를 JSON 같은 글자로 바꾸는 일이에요. 반대로 JSON을 객체로 바꾸는 일은 역직렬화라고 해요. ASP.NET Core는 C#의 `Name` 프로퍼티를 JSON의 `name`처럼 첫 글자를 소문자로 바꿔 직렬화해요.

## Day 18 · 메모리 CRUD API

### CRUD
- 처음 등장: [P2 Day 18](#/day/p2-d18)

데이터를 다루는 네 가지 기본 일, Create(만들기)·Read(읽기)·Update(고치기)·Delete(지우기)의 머리글자예요. REST API에서는 각각 POST·GET·PUT·DELETE에 대응해요. 게시판, 회원 관리 등 대부분의 기능이 CRUD로 이뤄져요.

### 라우트 매개변수
- 처음 등장: [P2 Day 18](#/day/p2-d18)

주소의 일부를 값으로 받는 자리예요. `/api/streamers/{id}`에 `/api/streamers/3`이 오면 `id`에 3이 들어가요. 처리 함수의 같은 이름 매개변수로 받아요.

### 라우트 제약
- 처음 등장: [P2 Day 18](#/day/p2-d18)

라우트 매개변수에 들어올 수 있는 값을 제한하는 표시예요. `{id:int}`는 정수만 받아서 `/api/streamers/abc`는 이 라우트와 맞지 않아요. 잘못된 주소가 처리 함수까지 오지 않게 해 줘요.

### TypedResults
- 처음 등장: [P2 Day 18](#/day/p2-d18)

Minimal API에서 상태 코드와 본문이 정해진 응답을 만드는 도우미 모음이에요. `TypedResults.Ok(값)`은 200, `Created(주소, 값)`은 201, `NoContent()`는 204, `NotFound()`는 404예요. 여러 결과를 돌려줄 때는 반환 타입을 `Results<Ok<T>, NotFound>`처럼 적어요.

### 모델 바인딩
- 처음 등장: [P2 Day 18](#/day/p2-d18)

요청의 주소·쿼리 문자열·JSON 본문에서 값을 꺼내 처리 함수의 매개변수에 알맞은 타입으로 채워 주는 ASP.NET Core의 기능이에요. JSON 본문은 C# 객체로, `{id}`는 `int`로 바뀌어 들어와요. 바꿀 수 없는 값이면 처리 함수가 실행되지 않아요.

## Day 19 · DB와 SQL 기초

### SQL
- 처음 등장: [P2 Day 19](#/day/p2-d19)

관계형 데이터베이스에 데이터를 만들고 찾고 고치고 지우라고 명령하는 언어예요. `SELECT`, `INSERT`, `UPDATE`, `DELETE`가 기본 명령이에요. 대부분의 DB가 거의 같은 SQL을 써요.

### SQLite
- 처음 등장: [P2 Day 19](#/day/p2-d19)

DB 전체가 파일 하나에 들어 있는 가벼운 관계형 데이터베이스예요. 따로 DB 서버를 설치하고 켤 필요가 없어서 배우기와 작은 앱에 좋아요. 스트리머 허브의 데이터는 `streamerhub.db` 파일에 저장돼요.

### 테이블
- 처음 등장: [P2 Day 19](#/day/p2-d19)

관계형 DB에서 같은 종류의 데이터를 행과 열로 모아 둔 표예요. 예: `Streamers` 테이블에는 스트리머 한 명이 한 줄씩 들어 있어요. EF Core에서는 엔티티 클래스 하나가 테이블 하나가 돼요.

### 행
- 처음 등장: [P2 Day 19](#/day/p2-d19)

테이블의 가로 한 줄로, 데이터 하나(예: 스트리머 한 명)를 나타내요. 영어로는 row예요. `INSERT`가 행을 더하고 `DELETE`가 행을 지워요.

### 열
- 처음 등장: [P2 Day 19](#/day/p2-d19)

테이블의 세로 한 칸으로, 모든 행이 갖는 항목(예: 이름, 플랫폼)이에요. 열마다 정해진 자료형(`INTEGER`, `TEXT`)이 있어요. 영어로는 column이에요.

### 기본 키
- 처음 등장: [P2 Day 19](#/day/p2-d19)

테이블에서 각 행을 하나로 딱 구별해 주는 열이에요. 보통 `Id`라는 정수 열을 쓰고, 값이 겹치거나 비면 안 돼요. EF Core는 이름이 `Id`인 프로퍼티를 알아서 기본 키로 써요.

### 쿼리
- 처음 등장: [P2 Day 19](#/day/p2-d19)

DB에 보내는 질문이나 명령 한 개예요. `SELECT * FROM Streamers WHERE Platform = 'chzzk';`가 쿼리예요. EF Core에서는 LINQ로 쓴 코드가 쿼리로 바뀌어요.

## Day 20 · EF Core 연결

### ORM
- 처음 등장: [P2 Day 20](#/day/p2-d20)

프로그램의 객체와 DB 테이블을 서로 바꿔 주는 도구예요(Object-Relational Mapping). SQL을 직접 쓰지 않고 C# 객체와 LINQ로 데이터를 다룰 수 있어요. EF Core가 .NET의 대표 ORM이에요.

### EF Core
- 처음 등장: [P2 Day 20](#/day/p2-d20)

Entity Framework Core의 줄임말로, .NET에서 쓰는 Microsoft의 ORM이에요. 엔티티 클래스로 테이블을 정하고, 마이그레이션으로 DB를 만들고, LINQ로 데이터를 읽고 써요. SQLite, PostgreSQL 등 여러 DB를 지원해요.

### NuGet
- 처음 등장: [P2 Day 20](#/day/p2-d20)

.NET의 패키지 저장소이자 관리 방식이에요. `dotnet add package 이름 --version 버전`으로 프로젝트에 패키지를 추가하면 `.csproj`에 기록돼요. npm의 .NET 판이라고 생각하면 돼요.

### 엔티티
- 처음 등장: [P2 Day 20](#/day/p2-d20)

DB 테이블의 한 행에 대응하는 C# 클래스예요. 스트리머 허브의 `Streamer`, `Schedule`, `Post`, `Notice`가 엔티티이고 `Entities` 폴더에 있어요. EF Core가 엔티티의 프로퍼티를 테이블의 열로 바꿔요.

### DbContext
- 처음 등장: [P2 Day 20](#/day/p2-d20)

EF Core에서 DB와 C# 코드를 이어 주는 통로 클래스예요. 어떤 테이블이 있는지 알고, 바뀐 내용을 모았다가 `SaveChangesAsync()`로 한꺼번에 저장해요. 스트리머 허브에서는 `AppDbContext`예요.

### DbSet
- 처음 등장: [P2 Day 20](#/day/p2-d20)

DbContext 안에서 테이블 하나를 나타내는 프로퍼티예요. `db.Streamers`처럼 쓰고, 여기에 LINQ를 붙여 조회하거나 `Add`·`Remove`로 행을 바꿔요. 타입은 `DbSet<Streamer>`처럼 엔티티 타입을 담아요.

### 연결 문자열
- 처음 등장: [P2 Day 20](#/day/p2-d20)

프로그램이 어느 DB에 어떻게 연결할지 적은 글자예요. SQLite는 `Data Source=streamerhub.db`처럼 파일 이름만 쓰고, 상대 경로는 서버를 실행한 폴더 기준이에요. `appsettings.json`의 `ConnectionStrings` 아래에 둬요.

### 마이그레이션
- 처음 등장: [P2 Day 20](#/day/p2-d20)

엔티티가 바뀐 만큼 DB 구조(테이블·열)를 바꾸는 단계를 코드 파일로 기록한 것이에요. `dotnet ef migrations add 이름`으로 만들고, `dotnet ef database update`나 `MigrateAsync()`로 DB에 적용해요. 파일이 쌓여서 DB가 어떻게 변해 왔는지 알 수 있어요.

### dotnet-ef
- 처음 등장: [P2 Day 20](#/day/p2-d20)

EF Core의 마이그레이션을 만들고 적용하는 명령줄 도구예요. `dotnet tool install --global dotnet-ef --version 10.0.14`로 한 번 설치하면 `dotnet ef …` 명령을 쓸 수 있어요. 프로젝트에는 `Microsoft.EntityFrameworkCore.Design` 패키지가 있어야 해요.

## Day 21 · DB CRUD

### 시드 데이터
- 처음 등장: [P2 Day 21](#/day/p2-d21)

앱을 처음 켤 때 DB에 미리 넣어 두는 기본 데이터예요. 스트리머 허브는 예시 스트리머 3명과 일정, 관리자 계정을 넣어요. 이미 데이터가 있으면 다시 넣지 않게 확인해요.

### IQueryable
- 처음 등장: [P2 Day 21](#/day/p2-d21)

아직 실행하지 않은 "질문"을 나타내는 LINQ의 타입이에요. `Where`·`OrderBy`를 이어 붙여도 바로 실행되지 않고, `ToListAsync()` 같은 메서드를 부를 때 한 번에 SQL로 바뀌어 DB에서 실행돼요. 그래서 조건에 따라 질문을 조립하기 좋아요.

### 변경 추적
- 처음 등장: [P2 Day 21](#/day/p2-d21)

DbContext가 DB에서 읽은 엔티티를 기억해 두었다가 바뀐 칸을 알아내는 기능이에요. 찾은 객체의 값을 바꾸고 `SaveChangesAsync()`만 부르면 EF Core가 알맞은 `UPDATE` SQL을 만들어요. 읽기만 할 때는 `AsNoTracking()`으로 꺼서 가볍게 할 수 있어요.

## Day 22 · 관계 설계

### 1:N 관계
- 처음 등장: [P2 Day 22](#/day/p2-d22)

한 쪽의 행 하나에 다른 쪽의 행 여러 개가 연결되는 관계예요(일대다). 스트리머 한 명에게 방송 일정이 여러 개 있는 것이 예예요. "여러 개" 쪽 테이블에 "하나" 쪽을 가리키는 외래 키를 둬요.

### 외래 키
- 처음 등장: [P2 Day 22](#/day/p2-d22)

다른 테이블의 기본 키를 가리키는 열이에요. `Schedules` 테이블의 `StreamerId`는 이 일정이 어느 스트리머의 것인지 알려 줘요. DB는 없는 스트리머를 가리키는 값을 막아 줘요.

### 탐색 속성
- 처음 등장: [P2 Day 22](#/day/p2-d22)

관계로 이어진 다른 엔티티를 바로 따라갈 수 있게 해 주는 엔티티의 프로퍼티예요. `schedule.Streamer`는 그 일정의 스트리머, `streamer.Schedules`는 그 스트리머의 일정 목록이에요. 함께 불러오려면 `Include`를 써요.

### Include
- 처음 등장: [P2 Day 22](#/day/p2-d22)

EF Core에서 엔티티를 읽을 때 관계로 이어진 엔티티도 함께 불러오라고 지정하는 메서드예요. `db.Streamers.Include(s => s.Schedules)`처럼 써요. 쓰지 않으면 탐색 속성이 비어 있어요.

### 계단식 삭제
- 처음 등장: [P2 Day 22](#/day/p2-d22)

"하나" 쪽 행을 지우면 그것을 가리키는 "여러 개" 쪽 행도 자동으로 지워지는 규칙이에요(Cascade). 스트리머를 지우면 그 스트리머의 일정도 함께 사라져요. 마이그레이션의 `onDelete: ReferentialAction.Cascade`가 이 규칙이에요.

### 순환 참조
- 처음 등장: [P2 Day 22](#/day/p2-d22)

객체 A가 B를 가리키고 B가 다시 A를 가리켜 끝없이 이어지는 연결이에요. 스트리머 → 일정 → 스트리머 → …를 그대로 JSON으로 바꾸면 끝나지 않아서 직렬화 오류가 나요. 필요한 칸만 담은 DTO로 끊어요.

### DTO
- 처음 등장: [P2 Day 22](#/day/p2-d22)

Data Transfer Object의 줄임말로, API로 주고받을 데이터의 모양만 담은 객체예요. 엔티티를 그대로 내보내지 않고 필요한 칸만 골라 보내서 순환 참조와 비밀 정보 노출을 막아요. 스트리머 허브의 `Dtos` 폴더에 요청 DTO와 응답 DTO가 있어요.

## Day 23 · 구조화

### 특성
- 처음 등장: [P2 Day 23](#/day/p2-d23)

C# 코드의 클래스·프로퍼티·매개변수 위에 `[Required]`처럼 대괄호로 붙이는 꼬리표예요. 그 자체로 실행되지는 않고, 프레임워크가 읽어서 검증이나 DB 설정에 써요. 영어로는 attribute이고, 직접 만들 수도 있어요(`[HttpUrl]`).

### 검증
- 처음 등장: [P2 Day 23](#/day/p2-d23)

들어온 데이터가 규칙(필수, 길이, 범위, 형식)에 맞는지 확인하는 일이에요. 화면에서도 하지만, 화면은 우회할 수 있어서 서버가 반드시 한 번 더 해요. 스트리머 허브는 DTO의 특성과 `AddValidation()`으로 검증하고, 틀리면 400을 돌려줘요.

### 확장 메서드
- 처음 등장: [P2 Day 23](#/day/p2-d23)

이미 있는 타입에 메서드를 새로 붙인 것처럼 쓰게 해 주는 C# 문법이에요. static 클래스 안의 static 메서드 첫 매개변수에 `this`를 붙여 만들어요. `app.MapStreamerEndpoints()`가 우리가 `WebApplication`에 붙인 확장 메서드예요.

### MapGroup
- 처음 등장: [P2 Day 23](#/day/p2-d23)

앞부분이 같은 주소들을 한 묶음으로 만드는 Minimal API 메서드예요. `var group = app.MapGroup("/api/streamers");` 뒤에 `group.MapGet("/{id:int}", …)`처럼 나머지만 써요. 묶음 전체에 권한이나 요청 제한을 한 번에 걸 수도 있어요.

### 의존성 주입
- 처음 등장: [P2 Day 23](#/day/p2-d23)

객체가 필요로 하는 다른 객체를 스스로 만들지 않고 바깥(프레임워크)에서 넣어 주는 방식이에요. `Program.cs`에 서비스를 등록해 두면 ASP.NET Core가 처리 함수의 매개변수나 생성자에 알맞은 객체를 넣어 줘요. 영어로는 Dependency Injection(DI)이에요.

### 서비스 수명
- 처음 등장: [P2 Day 23](#/day/p2-d23)

의존성 주입으로 넣어 줄 객체를 얼마나 오래 쓸지 정한 규칙이에요. Scoped는 요청마다 새로(DbContext, PostService), Singleton은 앱 전체에 하나만(NoticeBroadcaster), Transient는 필요할 때마다 새로 만들어요. `AddScoped`, `AddSingleton`, `AddTransient`로 등록해요.

### 서비스 계층
- 처음 등장: [P2 Day 23](#/day/p2-d23)

"누가 무엇을 할 수 있나" 같은 규칙을 엔드포인트에서 떼어 따로 모아 둔 코드 층이에요. 엔드포인트는 HTTP 요청·응답만 다루고 규칙은 서비스가 맡아요. 그래서 HTTP 없이도 규칙만 단위 테스트할 수 있어요.

## Day 24 · 오류·설정·로깅

### 미들웨어
- 처음 등장: [P2 Day 24](#/day/p2-d24)

요청이 처리 함수에 닿기 전과 응답이 나가기 전에 차례로 지나가는 처리 단계예요. 오류 처리, 정적 파일, 인증, 권한, 요청 제한이 모두 미들웨어예요. `app.Use…()`를 쓴 순서대로 지나가서 순서가 중요해요.

### ProblemDetails
- 처음 등장: [P2 Day 24](#/day/p2-d24)

HTTP API의 오류 응답을 같은 모양의 JSON으로 알려 주는 표준 형식이에요. `type`, `title`, `status`, 필요하면 `detail`과 `errors` 칸이 있고 `Content-Type`은 `application/problem+json`이에요. 화면은 이 모양만 알면 모든 오류를 같은 방식으로 읽을 수 있어요.

### 구성
- 처음 등장: [P2 Day 24](#/day/p2-d24)

코드를 고치지 않고 바꿀 수 있게 바깥에 둔 설정 값들이에요(configuration). ASP.NET Core는 `appsettings.json`, 환경별 파일, user-secrets, 환경 변수, 명령줄 인수를 차례로 읽어 합쳐요. 코드에서는 `builder.Configuration["Admin:Email"]`처럼 이름으로 꺼내요.

### appsettings.json
- 처음 등장: [P2 Day 24](#/day/p2-d24)

ASP.NET Core 앱의 기본 설정을 적는 JSON 파일이에요. 연결 문자열, 로그 수준, 요청 제한 값 등을 둬요. `appsettings.Development.json`처럼 환경 이름이 붙은 파일이 있으면 그 환경에서 값을 덮어써요.

### 실행 환경
- 처음 등장: [P2 Day 24](#/day/p2-d24)

앱이 지금 어떤 상황에서 실행되는지 나타내는 이름이에요. 개발 중에는 `Development`, 실제 서비스에서는 `Production`을 써요. `ASPNETCORE_ENVIRONMENT` 값으로 정하고, 환경에 따라 오류 화면·로그·설정이 달라져요.

### 로그 수준
- 처음 등장: [P2 Day 24](#/day/p2-d24)

로그 메시지의 중요도 단계예요. 낮은 것부터 Trace, Debug, Information, Warning, Error, Critical이 있어요. 설정에서 정한 수준보다 낮은 로그는 출력되지 않아요.

### ILogger
- 처음 등장: [P2 Day 24](#/day/p2-d24)

ASP.NET Core에서 로그를 남길 때 쓰는 인터페이스예요. `logger.LogInformation("관리자 계정 {Email}을(를) 만들었어요.", email)`처럼 수준별 메서드로 남겨요. `{Email}` 같은 자리표시자를 쓰면 값이 따로 기록되어 나중에 찾기 쉬워요.

## Day 25 · 회원가입·로그인

### 인증
- 처음 등장: [P2 Day 25](#/day/p2-d25)

요청을 보낸 사람이 "누구인지" 확인하는 일이에요. 이메일과 비밀번호로 로그인하면 서버가 확인한 뒤 쿠키를 줘서 다음 요청부터 누구인지 알 수 있어요. 영어로는 authentication이에요.

### 인가
- 처음 등장: [P2 Day 25](#/day/p2-d25)

확인된 사람이 "이 일을 해도 되는지" 정하는 일이에요. 로그인은 했지만 관리자가 아니면 스트리머를 등록할 수 없는 것이 인가예요. 영어로는 authorization이고, 인증 다음에 해요.

### 해싱
- 처음 등장: [P2 Day 25](#/day/p2-d25)

비밀번호 같은 값을 되돌릴 수 없는 긴 글자(해시)로 바꾸는 일이에요. 서버는 원래 비밀번호가 아니라 해시만 저장하고, 로그인할 때 입력값을 같은 방법으로 바꿔 비교해요. DB가 유출돼도 비밀번호 원문은 드러나지 않아요.

### 쿠키
- 처음 등장: [P2 Day 25](#/day/p2-d25)

서버가 `Set-Cookie` 헤더로 브라우저에 맡겨 두는 작은 값이에요. 브라우저는 같은 사이트로 요청할 때마다 쿠키를 자동으로 함께 보내요. 스트리머 허브는 로그인 상태를 쿠키로 기억해요.

### ASP.NET Core Identity
- 처음 등장: [P2 Day 25](#/day/p2-d25)

ASP.NET Core의 회원 관리 기능 묶음이에요. 가입, 비밀번호 해싱, 로그인, 역할을 제공하고 사용자 정보를 EF Core로 DB에 저장해요. `MapIdentityApi`로 가입·로그인 API 주소를 한 번에 만들 수 있어요.

## Day 26 · 권한

### 역할
- 처음 등장: [P2 Day 26](#/day/p2-d26)

사용자를 묶어 권한을 주는 이름표예요. 스트리머 허브에는 `Admin` 역할이 있고, 이 역할이 있는 사용자만 스트리머와 일정을 관리해요. 한 사용자가 여러 역할을 가질 수도 있어요.

### 권한 정책
- 처음 등장: [P2 Day 26](#/day/p2-d26)

"이 엔드포인트는 어떤 조건을 만족하는 사용자만 쓸 수 있다"는 규칙에 이름을 붙인 것이에요. `AddPolicy("Admin", policy => policy.RequireRole("Admin"))`로 만들고 `.RequireAuthorization("Admin")`으로 걸어요. 조건에 맞지 않으면 로그인 안 함은 401, 권한 없음은 403이에요.

### 클레임
- 처음 등장: [P2 Day 26](#/day/p2-d26)

로그인한 사용자에 대해 서버가 확인한 정보 한 조각이에요. 사용자 Id, 이메일, 역할 같은 것이 클레임으로 로그인 쿠키에 담겨요. 코드에서는 `ClaimsPrincipal user`에서 `user.FindFirstValue(ClaimTypes.NameIdentifier)`처럼 꺼내요.

### user-secrets
- 처음 등장: [P2 Day 26](#/day/p2-d26)

개발하는 PC에만 비밀 설정 값을 저장하는 .NET 기능이에요. `dotnet user-secrets set "Admin:Password" '…'`로 넣으면 프로젝트 폴더 밖(`%APPDATA%\Microsoft\UserSecrets`)에 저장되어 Git에 올라가지 않아요. 개발 환경에서만 읽히고, 배포할 때는 환경 변수를 써요.

## Day 27 · 프론트↔백 연결

### 출처
- 처음 등장: [P2 Day 27](#/day/p2-d27)

웹 주소의 스킴(`http`), 호스트(`localhost`), 포트(`5173`)를 합친 것이에요(origin). 셋 중 하나라도 다르면 다른 출처예요. 브라우저는 다른 출처로 보내는 요청을 보안 규칙으로 제한해요.

### CORS
- 처음 등장: [P2 Day 27](#/day/p2-d27)

다른 출처의 웹페이지가 내 서버의 응답을 읽어도 되는지 서버가 알려 주는 규칙이에요(Cross-Origin Resource Sharing). 서버가 허락한다는 헤더를 보내지 않으면 브라우저가 응답을 막아요. 스트리머 허브는 프록시와 단일 서버로 같은 출처를 유지해서 CORS 설정이 필요 없어요.

### 프록시
- 처음 등장: [P2 Day 27](#/day/p2-d27)

요청을 대신 받아 다른 서버로 넘겨 주고, 받은 응답을 다시 돌려주는 중간 서버예요. Vite 개발 서버는 `/api`로 시작하는 요청을 5250번 서버로 넘겨 줘요. 브라우저 입장에서는 같은 출처라서 CORS 문제가 없어요.

## Day 28 · 목록·상세 페이지

### SPA
- 처음 등장: [P2 Day 28](#/day/p2-d28)

Single Page Application의 줄임말로, HTML 페이지 하나를 불러온 뒤 화면 전환을 자바스크립트가 직접 그려서 처리하는 웹앱이에요. 다른 화면으로 가도 페이지 전체를 다시 불러오지 않아 빠르게 느껴져요. 스트리머 허브의 화면이 SPA예요.

### 해시 라우터
- 처음 등장: [P2 Day 28](#/day/p2-d28)

주소의 `#` 뒤(`#/streamers/3`)를 읽어 어떤 화면을 그릴지 정하는 라우터예요. `#` 뒤만 바뀌면 브라우저가 페이지를 새로 불러오지 않고 `hashchange` 이벤트만 알려 줘요. 그래서 서버에는 `index.html` 하나만 있으면 돼요.

## Day 29 · 방송 일정 페이지

### UTC
- 처음 등장: [P2 Day 29](#/day/p2-d29)

세계 시간의 기준이 되는 협정 세계시예요. 한국 시간(KST)은 언제나 UTC보다 9시간 빨라요. 서버와 DB는 UTC로 저장하고 주고받아서 어느 나라에서 봐도 같은 순간을 가리켜요.

### 시간대
- 처음 등장: [P2 Day 29](#/day/p2-d29)

지역마다 쓰는 시각의 규칙이에요(time zone). 이름은 `Asia/Seoul`처럼 쓰고, UTC와의 차이와 서머타임 여부가 들어 있어요. 화면에서 시간대를 지정하지 않으면 사용자의 컴퓨터 시간대를 따라요.

### ISO 8601
- 처음 등장: [P2 Day 29](#/day/p2-d29)

날짜와 시각을 글자로 적는 국제 표준 형식이에요. 예: `2026-11-02T11:00:00Z`에서 `T`는 날짜와 시각의 구분, 끝의 `Z`는 UTC라는 뜻이에요. 스트리머 허브의 API는 모든 시각을 이 형식으로 보내요.

### Intl.DateTimeFormat
- 처음 등장: [P2 Day 29](#/day/p2-d29)

날짜와 시각을 나라별 표기로 바꿔 주는 JavaScript 기본 기능이에요. `new Intl.DateTimeFormat('ko-KR', { timeZone: 'Asia/Seoul', hour: 'numeric', minute: '2-digit' })`처럼 언어와 시간대를 정해요. 시간대를 직접 정하면 사용자의 컴퓨터 시간대와 상관없이 한국 시간으로 보여요.

### 값 변환기
- 처음 등장: [P2 Day 29](#/day/p2-d29)

EF Core가 프로퍼티 값을 DB에 쓸 때와 읽을 때 바꿔 주는 규칙이에요(value converter). 스트리머 허브의 `UtcDateTimeConverter`는 SQLite에서 읽은 시각에 "UTC" 표시를 다시 붙여요. 그래야 JSON 시각 끝에 `Z`가 붙어요.

### Map
- 처음 등장: [P2 Day 29](#/day/p2-d29)

키와 값을 짝지어 담는 JavaScript의 자료 구조예요. `new Map<number, string>()`으로 만들고 `set`으로 넣으며, 같은 키는 한 번만 들어가요. 방송 일정 페이지에서 중복 없는 스트리머 목록을 만들 때 써요.

## Day 30 · 팬 게시판 API

### 페이지네이션
- 처음 등장: [P2 Day 30](#/day/p2-d30)

많은 데이터를 한 번에 보내지 않고 쪽(페이지) 단위로 나눠 보내는 방법이에요. 스트리머 허브는 `?page=2&pageSize=20`처럼 요청하고 `{ items, total, page, pageSize }` 모양으로 답해요. 서버에서는 `Skip`과 `Take`로 한 쪽만 읽어요.

### 프로젝션
- 처음 등장: [P2 Day 30](#/day/p2-d30)

DB에서 엔티티 전체가 아니라 필요한 칸만 골라 다른 모양으로 읽는 것이에요. EF Core에서는 `Select(p => new PostListItem(…))`처럼 쓰고, 고른 열만 SQL의 `SELECT`에 들어가요. 본문이나 비밀번호 해시처럼 필요 없는 데이터를 읽지 않아 가볍고 안전해요.

## Day 31 · 팬 게시판 화면

### 관찰자 패턴
- 처음 등장: [P2 Day 31](#/day/p2-d31)

어떤 값이 바뀌면 미리 등록해 둔 함수들을 차례로 불러 알려 주는 설계 방식이에요. 스트리머 허브의 `auth.ts`는 로그인 상태가 바뀔 때 `onAuthChange`로 등록된 함수를 불러 위쪽 메뉴를 다시 그려요. 주는 쪽과 받는 쪽이 서로를 자세히 몰라도 돼요.

## Day 32 · 관리자 화면

### 역할 기반 접근 제어
- 처음 등장: [P2 Day 32](#/day/p2-d32)

사용자의 역할에 따라 할 수 있는 일을 정하는 방식이에요(RBAC). 스트리머 허브는 서버가 `Admin` 정책으로 실제로 막고, 화면은 관리자에게만 메뉴를 보여 줘요. 화면에서 숨기는 것은 편의일 뿐이고 진짜 보호는 서버가 해요.

## Day 33 · 실시간 공지 오버레이

### 폴링
- 처음 등장: [P2 Day 33](#/day/p2-d33)

클라이언트가 정해진 간격마다 서버에 "새 소식 있어요?" 하고 다시 묻는 방식이에요. 만들기 쉽지만 소식이 없어도 요청이 계속 가고, 간격만큼 늦게 알게 돼요. 스트리머 허브의 오버레이는 처음에 3초 폴링으로 만들고 SSE로 바꿔요.

### SSE
- 처음 등장: [P2 Day 33](#/day/p2-d33)

Server-Sent Events의 줄임말로, 연결 하나를 열어 둔 채 서버가 새 소식을 생길 때마다 먼저 보내 주는 방식이에요. 응답의 `Content-Type`은 `text/event-stream`이고, 내용은 `event:`와 `data:` 줄로 이뤄져요. 서버에서 클라이언트 한 방향으로만 보내요.

### EventSource
- 처음 등장: [P2 Day 33](#/day/p2-d33)

브라우저에서 SSE 연결을 열고 이벤트를 받는 JavaScript 기본 객체예요. `new EventSource('/api/notices/stream')`으로 연결하고 `addEventListener('notice', …)`로 받아요. 연결이 끊기면 몇 초 뒤에 알아서 다시 연결해요.

### lock
- 처음 등장: [P2 Day 33](#/day/p2-d33)

여러 요청이 동시에 같은 데이터를 만지지 못하게 한 번에 하나씩만 들어가게 하는 C# 문법이에요. `lock (_mailboxes) { … }` 안의 코드는 한 요청이 끝나야 다음 요청이 실행해요. 앱 전체가 함께 쓰는 Singleton 객체의 목록을 지킬 때 써요.

### yield return
- 처음 등장: [P2 Day 33](#/day/p2-d33)

값을 한꺼번에 돌려주지 않고 하나씩 차례로 내놓는 C# 문법이에요. `IAsyncEnumerable<T>`를 돌려주는 메서드에서 쓰면 기다렸다가 값이 생길 때마다 내보낼 수 있어요. 스트리머 허브의 SSE는 새 공지가 올 때마다 `yield return`으로 하나씩 보내요.

## Day 34 · 보안 점검

### XSS
- 처음 등장: [P2 Day 34](#/day/p2-d34)

공격자가 게시글 같은 입력에 스크립트를 숨겨 다른 사람의 브라우저에서 실행시키는 공격이에요(Cross-Site Scripting). 사용자 데이터를 `innerHTML`에 넣으면 생길 수 있어요. `textContent`·`value`로 넣고, 링크 주소는 http·https인지 확인해서 막아요.

### CSRF
- 처음 등장: [P2 Day 34](#/day/p2-d34)

다른 사이트가 사용자 몰래 내 사이트로 요청을 보내게 해서, 로그인 쿠키를 이용해 원치 않는 일을 시키는 공격이에요(Cross-Site Request Forgery). 브라우저가 쿠키를 자동으로 붙이는 성질을 노려요. 스트리머 허브는 SameSite=Lax 쿠키, JSON만 받는 API, 같은 출처 구성으로 막아요.

### SameSite
- 처음 등장: [P2 Day 34](#/day/p2-d34)

다른 사이트에서 시작된 요청에 쿠키를 붙일지 정하는 쿠키 옵션이에요. `Lax`면 다른 사이트에서 보낸 POST 같은 요청에는 쿠키가 붙지 않아요. CSRF를 막는 첫 번째 벽이에요.

### HttpOnly
- 처음 등장: [P2 Day 34](#/day/p2-d34)

자바스크립트(`document.cookie`)가 쿠키를 읽지 못하게 하는 쿠키 옵션이에요. XSS가 생겨도 로그인 쿠키를 훔쳐 가기 어려워져요. 그래서 화면 코드는 쿠키 대신 `/api/me`로 로그인 상태를 물어요.

### SQL 인젝션
- 처음 등장: [P2 Day 34](#/day/p2-d34)

입력값에 SQL 조각을 섞어 DB가 원래와 다른 명령을 실행하게 만드는 공격이에요. SQL 문장을 문자열로 이어 붙이면 생겨요. EF Core의 LINQ는 입력값을 매개변수로 따로 보내서 이 공격을 막아요.

### 요청 제한
- 처음 등장: [P2 Day 34](#/day/p2-d34)

정해진 시간 동안 받을 수 있는 요청 수를 제한하는 기능이에요(rate limiting). 비밀번호를 마구 넣어 보는 공격이나 도배를 막고, 넘으면 429 Too Many Requests로 답해요. 스트리머 허브는 IP마다 1분에 30번까지 받아요.

### 개발 인증서
- 처음 등장: [P2 Day 34](#/day/p2-d34)

개발하는 PC에서 HTTPS를 시험하려고 .NET SDK가 만들어 주는 자체 서명 인증서예요. `dotnet dev-certs https --trust`로 내 PC가 믿게 하면 `https://localhost` 경고가 사라져요. 실제 서비스에서는 쓰지 않고 호스팅이나 프록시가 진짜 인증서를 써요.

## Day 35 · 단위 테스트

### 자동 테스트
- 처음 등장: [P2 Day 35](#/day/p2-d35)

코드가 기대대로 동작하는지 확인하는 일을 다른 코드가 대신 하게 만든 것이에요. 한 번 써 두면 명령 하나(`dotnet test`)로 언제든 다시 확인할 수 있어요. 코드를 고친 뒤 예전 기능이 망가졌는지 바로 알 수 있어요.

### 단위 테스트
- 처음 등장: [P2 Day 35](#/day/p2-d35)

메서드나 클래스 하나처럼 작은 부분만 떼어 확인하는 자동 테스트예요. HTTP나 진짜 서버 없이 빠르게 돌아가요. 스트리머 허브는 `PostService`의 권한 규칙, `ScheduleQuery`의 시간 범위, DTO 검증을 단위 테스트해요.

### xUnit
- 처음 등장: [P2 Day 35](#/day/p2-d35)

.NET에서 널리 쓰는 테스트 프레임워크예요. 테스트 메서드에 `[Fact]`나 `[Theory]` 특성을 붙이고 `Assert`로 결과를 확인해요. `dotnet new xunit`으로 테스트 프로젝트를 만들어요.

### Assert
- 처음 등장: [P2 Day 35](#/day/p2-d35)

테스트에서 "결과가 이래야 한다"를 확인하는 xUnit의 메서드 모음이에요. `Assert.Equal(기대값, 실제값)`이 다르면 테스트가 실패하고 두 값을 보여 줘요. `Assert.True`, `Assert.Null`, `Assert.Single` 등이 있어요.

### AAA 패턴
- 처음 등장: [P2 Day 35](#/day/p2-d35)

테스트를 준비(Arrange), 실행(Act), 확인(Assert) 세 부분으로 나눠 쓰는 방식이에요. 무엇을 준비했고 무엇을 했고 무엇을 기대하는지가 한눈에 보여요. 레퍼런스 테스트는 각 부분에 한국어 주석을 달아 두었어요.

### Theory
- 처음 등장: [P2 Day 35](#/day/p2-d35)

같은 테스트를 입력값만 바꿔 여러 번 실행하게 하는 xUnit 특성이에요. `[Theory]` 아래에 `[InlineData("ftp://example.com/channel")]`처럼 값을 여러 줄 붙이면 한 줄마다 테스트가 하나씩 돌아요. 값 하나만 확인할 때는 `[Fact]`를 써요.

## Day 36 · 통합 테스트

### 통합 테스트
- 처음 등장: [P2 Day 36](#/day/p2-d36)

여러 부분(라우팅, 인증, DB, 서비스)을 실제처럼 함께 돌려서 확인하는 자동 테스트예요. 진짜 HTTP 요청을 보내고 상태 코드와 응답을 확인해요. 단위 테스트보다 느리지만 부분끼리 잘 맞물리는지 알 수 있어요.

### WebApplicationFactory
- 처음 등장: [P2 Day 36](#/day/p2-d36)

ASP.NET Core 앱(`Program.cs`)을 메모리 안에서 실행해 통합 테스트를 하게 해 주는 클래스예요. `Microsoft.AspNetCore.Mvc.Testing` 패키지에 있어요. 테스트용 설정을 넣고 `CreateClient()`로 요청을 보낼 `HttpClient`를 만들어요.

## Day 37 · 코드 품질과 Git 흐름

### 코드 포매터
- 처음 등장: [P2 Day 37](#/day/p2-d37)

들여쓰기, 따옴표, 줄 길이 같은 코드 모양을 정해진 규칙대로 자동으로 맞춰 주는 도구예요. 사람마다 다른 모양 때문에 생기는 다툼과 실수가 줄어요. 검사만 하는 모드는 바꿀 곳이 있으면 실패로 알려 줘요.

### Prettier
- 처음 등장: [P2 Day 37](#/day/p2-d37)

JavaScript·TypeScript·CSS·HTML 등을 정리해 주는 코드 포매터예요. `npx prettier --check`로 검사하고 `--write`로 고쳐요. 스트리머 허브의 클라이언트는 `--single-quote --print-width 120` 옵션 기준이에요.

### dotnet format
- 처음 등장: [P2 Day 37](#/day/p2-d37)

.NET SDK에 들어 있는 C# 코드 포매터예요. `dotnet format StreamerHub.slnx --verify-no-changes`는 검사만, 옵션 없이 실행하면 고쳐요. 들여쓰기와 공백 같은 규칙을 맞춰 줘요.

### 풀 리퀘스트
- 처음 등장: [P2 Day 37](#/day/p2-d37)

내 브랜치의 변경을 `main`에 합쳐 달라고 GitHub에서 요청하는 기능이에요(PR). 바뀐 파일을 함께 보고 코멘트로 검토(리뷰)한 뒤 합쳐요. 혼자 하는 프로젝트에서도 변경을 정리하고 기록하는 데 좋아요.

### 머지
- 처음 등장: [P2 Day 37](#/day/p2-d37)

한 브랜치의 변경을 다른 브랜치에 합치는 일이에요. GitHub의 풀 리퀘스트에서는 Merge pull request 버튼으로 해요. 합친 뒤에는 내 PC에서 `git pull`로 최신 `main`을 받아요.

## Day 38 · 프로덕션 빌드

### 정적 파일
- 처음 등장: [P2 Day 38](#/day/p2-d38)

서버가 그대로 보내 주기만 하는 파일이에요. 빌드한 HTML·JS·CSS·그림 파일이 정적 파일이에요. ASP.NET Core에서는 `UseStaticFiles()`가 `wwwroot` 폴더의 정적 파일을 보내요.

### wwwroot
- 처음 등장: [P2 Day 38](#/day/p2-d38)

ASP.NET Core 프로젝트에서 정적 파일을 두는 기본 폴더 이름이에요. 스트리머 허브는 클라이언트를 빌드한 `dist` 안의 파일을 여기에 복사해서 서버 하나로 화면까지 보여 줘요. 빌드 결과라서 Git에는 올리지 않아요.

### 폴백 라우트
- 처음 등장: [P2 Day 38](#/day/p2-d38)

다른 어떤 라우트에도 맞지 않는 요청을 마지막에 받는 라우트예요. `MapFallbackToFile("index.html")`은 그런 주소에 `index.html`을 보내서 화면(SPA)이 주소를 처리하게 해요. 없는 API 주소까지 받지 않게 `/api/{**rest}`를 먼저 404로 막아요.

### dotnet publish
- 처음 등장: [P2 Day 38](#/day/p2-d38)

앱을 다른 곳에서 실행할 수 있게 필요한 파일을 모두 한 폴더로 모아 주는 명령이에요. `-c Release`로 최적화하고 `-o 폴더`로 결과 위치를 정해요. 결과 폴더에서 `dotnet StreamerHub.Api.dll`로 실행해요.

## Day 39 · 배포

### 리버스 프록시
- 처음 등장: [P2 Day 39](#/day/p2-d39)

인터넷에서 오는 요청을 앞에서 받아 뒤의 앱 서버로 넘겨 주는 서버예요. HTTPS 처리, 여러 서버로 나누기 같은 일을 맡아요. 앱 서버에는 모든 요청이 프록시에서 온 것처럼 보여서 진짜 접속 IP를 따로 전달받아야 해요.

### X-Forwarded-For
- 처음 등장: [P2 Day 39](#/day/p2-d39)

리버스 프록시가 원래 요청한 사용자의 IP를 앱 서버에 알려 주려고 붙이는 HTTP 헤더예요. ASP.NET Core는 `UseForwardedHeaders()`로 이 값을 읽고, 믿을 수 있는 프록시만 등록해 위조를 막아요. 요청 제한처럼 IP를 쓰는 미들웨어보다 앞에 둬야 해요.

### 백업
- 처음 등장: [P2 Day 39](#/day/p2-d39)

데이터를 잃어버릴 때를 대비해 다른 곳에 복사해 두는 일이에요. SQLite는 서버를 끈 뒤 DB 파일(과 `-wal`, `-shm` 파일)을 복사하면 돼요. 백업을 되돌려 놓는 복원도 미리 연습해 둬요.
