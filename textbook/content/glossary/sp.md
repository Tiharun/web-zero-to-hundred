# SP 용어

특별 프로젝트(이미지 도네이션 서비스)에서 처음 가르치는 용어예요. Docker·PostgreSQL·WebSocket처럼 다른 프로젝트 사전에 이미 있는 용어는 그 항목을 함께 써요.

### 이미지 후원
- 처음 등장: [SP Day 1](#/day/sp-d01)

시청자가 이미지와 짧은 메시지를 스트리머에게 보내고, 스트리머가 확인한 이미지만 방송 화면에 잠깐 나타나게 하는 기능이에요. 이 교재의 특별 프로젝트에서 만드는 서비스예요. 서비스 운영자는 결제를 전혀 다루지 않아요.

### 치지직
- 처음 등장: [SP Day 1](#/day/sp-d01)

네이버가 운영하는 인터넷 방송 플랫폼이에요. 스트리머가 방송하고 시청자는 채팅과 후원으로 참여해요. 개발자를 위한 Open API가 있어서 우리 서비스가 로그인 정보와 후원 이벤트를 받을 수 있어요.

### 치즈 후원
- 처음 등장: [SP Day 1](#/day/sp-d01)

치지직 시청자가 "치즈"라는 후원 수단으로 스트리머를 후원하는 치지직의 공식 기능이에요. 결제와 정산은 치지직이 처리하고, 돈은 치지직이 스트리머에게 직접 정산해요. 이 서비스는 후원 메시지 속 코드만 확인하고 돈에는 손대지 않아요.

### 검수
- 처음 등장: [SP Day 1](#/day/sp-d01)

시청자가 보낸 이미지를 방송에 내보내기 전에 스트리머가 직접 보고 승인하거나 거절하는 일이에요. 부적절한 이미지가 방송에 나가는 사고를 막는 가장 중요한 장치예요. 이 서비스는 기본으로 검수를 거치고, 자동 승인은 스트리머가 직접 켜야 해요.

### 결제 대행(PG)
- 처음 등장: [SP Day 1](#/day/sp-d01)

카드·계좌 결제를 대신 처리해 주는 회사나 서비스예요. PG는 Payment Gateway의 줄임말이에요. 결제를 받으려면 보통 PG와 계약하고 사업자·보안 의무를 져야 하는데, 이 서비스는 PG를 쓰지 않아요.

### 정산
- 처음 등장: [SP Day 1](#/day/sp-d01)

받은 돈을 계산해서 받을 사람에게 나눠 지급하는 일이에요. 치즈 후원의 정산은 치지직이 스트리머에게 직접 해요. 이 서비스의 운영자는 정산을 하지 않아요.

### 테스트 모드
- 처음 등장: [SP Day 1](#/day/sp-d01)

치지직 앱 승인 없이도 치즈 후원 흐름 전체를 연습할 수 있게, 서버가 치지직과 같은 모양의 가짜 후원 이벤트를 만들어 주는 기능이에요. 돈은 전혀 오가지 않아요. 대시보드의 "가짜 치즈 후원 보내기"가 이 기능을 써요.

### 아키텍처
- 처음 등장: [SP Day 2](#/day/sp-d02)

프로그램을 이루는 큰 조각들과 그 조각들이 서로 주고받는 방식을 정한 설계예요. 예를 들어 "화면은 React, 서버는 ASP.NET Core, 데이터는 PostgreSQL에 두고, 실시간 알림은 SignalR로 보낸다"가 이 서비스의 아키텍처예요. 코드를 쓰기 전에 정해 두면 무엇을 어디에 만들지 헷갈리지 않아요.

### 구성도
- 처음 등장: [SP Day 2](#/day/sp-d02)

아키텍처를 상자와 화살표로 그린 그림이에요. 상자는 프로그램 조각(화면, 서버, DB 등)이고, 화살표는 요청이나 데이터가 흐르는 방향이에요. 이 교재는 글자로 그린 구성도를 README에 넣어요.

### React
- 처음 등장: [SP Day 3](#/day/sp-d03)

화면을 작은 조각(컴포넌트)으로 나눠 만들고, 데이터가 바뀌면 화면을 알아서 다시 그려 주는 JavaScript 라이브러리예요. 웹 화면을 만들 때 널리 쓰여요. 이 교재는 React 19를 TypeScript와 함께 써요.

### 컴포넌트
- 처음 등장: [SP Day 3](#/day/sp-d03)

화면의 한 조각을 만드는 함수예요. React에서는 대문자로 시작하는 함수가 화면 조각을 돌려주면 컴포넌트가 되고, `<DonationCard />`처럼 태그로 써요. 같은 컴포넌트를 여러 번 써서 비슷한 화면을 반복해 만들 수 있어요.

### JSX
- 처음 등장: [SP Day 3](#/day/sp-d03)

JavaScript 코드 안에 HTML과 비슷한 태그를 바로 쓰는 문법이에요. 브라우저가 직접 읽지는 못하고, 빌드 도구가 일반 JavaScript로 바꿔 줘요. HTML과 달리 `class` 대신 `className`을 쓰고, 중괄호 `{}` 안에 값을 넣어요.

### TSX
- 처음 등장: [SP Day 3](#/day/sp-d03)

TypeScript 파일에서 JSX를 쓸 수 있게 한 형식이에요. 확장자는 `.tsx`이고, 태그에 넘기는 값의 타입까지 검사해 줘요.

### props
- 처음 등장: [SP Day 3](#/day/sp-d03)

부모 컴포넌트가 자식 컴포넌트에게 넘겨주는 값이에요. 함수의 매개변수와 같아서, `<DonationCard nickname="시청자" />`처럼 태그 속성으로 넘기고 자식은 받은 값으로 화면을 그려요. 자식은 받은 props를 직접 바꾸지 않아요.

### Oxlint
- 처음 등장: [SP Day 3](#/day/sp-d03)

JavaScript·TypeScript 코드에서 실수하기 쉬운 부분을 찾아 알려 주는 린터예요. Vite의 React 템플릿이 기본으로 넣어 주고 `npm run lint`로 실행해요. 예를 들어 훅을 잘못된 곳에서 부르면 오류로 알려 줘요.

### 훅
- 처음 등장: [SP Day 4](#/day/sp-d04)

React 컴포넌트 안에서 상태 같은 React 기능을 쓰게 해 주는 함수예요. 이름이 `use`로 시작하고(useState, useEffect 등), 컴포넌트 맨 위에서 항상 같은 순서로 불러야 해요. 조건문이나 반복문 안에서 부르면 안 돼요.

### useState
- 처음 등장: [SP Day 4](#/day/sp-d04)

컴포넌트가 기억할 값(상태)을 만드는 훅이에요. `const [count, setCount] = useState(0)`처럼 현재 값과 바꾸는 함수를 함께 돌려줘요. 바꾸는 함수를 부르면 React가 화면을 다시 그려요.

### 조건부 렌더링
- 처음 등장: [SP Day 4](#/day/sp-d04)

조건에 따라 화면에 보여 줄 것을 다르게 하는 방법이에요. React에서는 `{조건 && <태그 />}`나 `조건 ? A : B`를 TSX 안에 써요. 예를 들어 검수 대기 상태일 때만 승인 버튼을 보여 줘요.

### key (React)
- 처음 등장: [SP Day 4](#/day/sp-d04)

목록을 그릴 때 각 항목에 붙이는 고유한 이름표예요. React는 key로 어느 항목이 바뀌었는지 알아내서 필요한 부분만 다시 그려요. 순서가 바뀔 수 있는 목록에는 배열 번호 대신 후원 id 같은 고유 값을 써요.

### 불변 업데이트
- 처음 등장: [SP Day 4](#/day/sp-d04)

상태로 가진 배열이나 객체를 직접 고치지 않고, 바뀐 내용을 담은 새 배열·새 객체를 만들어 바꾸는 방식이에요. React는 새 값인지를 보고 다시 그릴지 판단하므로 `push`로 직접 고치면 화면이 바뀌지 않을 수 있어요. `map`, `filter`, 펼침 문법(`...`)을 써요.

### useEffect
- 처음 등장: [SP Day 5](#/day/sp-d05)

화면을 그린 뒤에 해야 하는 일(데이터 가져오기, 타이머, 실시간 연결 등)을 적는 훅이에요. 의존성 배열의 값이 바뀔 때마다 다시 실행돼요. 정리 함수를 돌려주면 다시 실행되기 전이나 화면에서 사라질 때 불려요.

### 의존성 배열
- 처음 등장: [SP Day 5](#/day/sp-d05)

useEffect 같은 훅의 두 번째 인자로 넘기는 배열이에요. 배열 안의 값이 바뀔 때만 효과를 다시 실행해요. 빈 배열 `[]`이면 처음 한 번만 실행하고, 아예 빼면 화면을 그릴 때마다 실행해요.

### 정리 함수
- 처음 등장: [SP Day 5](#/day/sp-d05)

useEffect가 돌려주는 함수로, 효과를 끝낼 때 뒷정리를 해요. 타이머 지우기, 연결 끊기, 늦게 온 응답 무시하기 같은 일을 여기서 해요. 빠뜨리면 화면을 떠난 뒤에도 타이머나 연결이 남아요.

### 커스텀 훅
- 처음 등장: [SP Day 5](#/day/sp-d05)

여러 훅을 묶어 이름을 붙인, 직접 만든 훅이에요. 이름은 `use`로 시작하고(예: `useImagePreview`), 여러 컴포넌트에서 같은 동작을 다시 쓸 수 있게 해 줘요.

### 제어 컴포넌트
- 처음 등장: [SP Day 5](#/day/sp-d05)

입력칸의 값을 React 상태가 쥐고 있는 입력 방식이에요. `value`와 `onChange`로 상태를 바꾸면 화면의 글자와 상태가 항상 같아요. 그래서 글자 수 세기나 검사를 쉽게 할 수 있어요.

### FileReader
- 처음 등장: [SP Day 5](#/day/sp-d05)

사용자가 고른 내 PC의 파일을 브라우저 안에서 읽는 브라우저 기능이에요. 서버로 보내지 않고도 이미지를 `data:` 주소로 읽어 미리보기를 보여 줄 수 있어요.

### React Router
- 처음 등장: [SP Day 6](#/day/sp-d06)

React 앱에서 주소(경로)에 따라 다른 화면을 보여 주는 라이브러리예요. 이 교재는 8.5.1 버전의 `react-router` 패키지를 Declarative 방식(`<BrowserRouter>`, `<Routes>`, `<Route>`)으로 써요.

### BrowserRouter
- 처음 등장: [SP Day 6](#/day/sp-d06)

주소창의 실제 경로(`/dashboard`처럼 #이 없는 주소)를 보고 화면을 고르는 React Router 구성 요소예요. 링크를 누르면 페이지를 새로 받지 않고 화면만 바꿔요. 새로고침하면 서버가 index.html을 돌려줘야 하므로 서버 설정이 함께 필요해요.

### Outlet
- 처음 등장: [SP Day 6](#/day/sp-d06)

레이아웃 라우트 안에서 자식 화면이 들어갈 자리를 표시하는 React Router 구성 요소예요. 위쪽 메뉴는 그대로 두고 Outlet 자리만 주소에 따라 바뀌어요.

### 레이아웃 라우트
- 처음 등장: [SP Day 6](#/day/sp-d06)

여러 화면이 함께 쓰는 틀(위쪽 메뉴, 로그인 확인 등)을 맡는 라우트예요. 자식 라우트들을 감싸고, 자식 화면은 레이아웃의 Outlet 자리에 그려져요.

### Npgsql
- 처음 등장: [SP Day 8](#/day/sp-d08)

.NET 프로그램이 PostgreSQL과 대화하게 해 주는 라이브러리예요. EF Core에서 PostgreSQL을 쓰려면 `Npgsql.EntityFrameworkCore.PostgreSQL` 패키지를 설치하고 `UseNpgsql(연결 문자열)`을 불러요. 연결 문자열은 `Host=…;Port=…;Database=…;Username=…;Password=…` 형식이에요.

### 빠른 실패
- 처음 등장: [SP Day 8](#/day/sp-d08)

꼭 필요한 설정이 없으면 프로그램을 억지로 계속 돌리지 않고, 시작할 때 바로 분명한 오류를 내고 멈추는 습관이에요. 나중에 엉뚱한 곳에서 이상하게 실패하는 것보다 원인을 찾기 쉬워요. 이 서비스는 연결 문자열이나 IP 해시 키가 없으면 시작하자마자 알려 줘요.

### 상태 전이
- 처음 등장: [SP Day 9](#/day/sp-d09)

어떤 대상의 상태가 정해진 규칙에 따라 다른 상태로 바뀌는 것이에요. 후원은 "검수 대기 → 승인됨 → 방송 완료"처럼 정해진 길로만 움직이고, 거절된 후원을 다시 승인하는 것처럼 규칙에 없는 이동은 막아요. 상태와 화살표를 그린 그림을 상태 전이도라고 해요.

### 배열 열
- 처음 등장: [SP Day 9](#/day/sp-d09)

한 칸에 값 여러 개를 목록으로 담는 PostgreSQL의 열 형식이에요(예: `text[]`). 이 서비스는 스트리머의 금지어 목록을 C#의 `string[]`로 두고, Npgsql이 이를 `text[]` 열로 저장해요.

### multipart/form-data
- 처음 등장: [SP Day 10](#/day/sp-d10)

글자 입력과 파일을 한 요청에 함께 담아 보내는 HTTP 본문 형식이에요. 본문을 경계 문자열(boundary)로 여러 부분으로 나누고, 부분마다 이름과 내용을 적어요. 파일 업로드 폼은 보통 이 형식을 써요.

### IFormFile
- 처음 등장: [SP Day 10](#/day/sp-d10)

ASP.NET Core에서 업로드된 파일 하나를 나타내는 형식이에요. 파일 크기(`Length`), 보낸 쪽이 붙인 이름과 형식, 내용을 읽는 메서드를 가지고 있어요. 이름과 형식은 보낸 사람이 마음대로 바꿀 수 있으니 믿지 않아요.

### GUID
- 처음 등장: [SP Day 10](#/day/sp-d10)

거의 겹치지 않는 128비트 무작위 식별자예요(Globally Unique Identifier). 32자리 16진수로 쓸 수 있어서, 업로드 파일 이름을 추측할 수 없고 겹치지 않게 만들 때 써요.

### 경로 조작
- 처음 등장: [SP Day 10](#/day/sp-d10)

파일 이름에 `..\`처럼 상위 폴더로 가는 글자를 넣어, 서버가 허용한 폴더 밖의 파일을 읽거나 덮어쓰게 만드는 공격이에요. 사용자가 준 파일 이름을 쓰지 않고 우리가 정한 형식의 이름만 허용하면 막을 수 있어요.

### 매직 넘버
- 처음 등장: [SP Day 11](#/day/sp-d11)

파일 맨 앞 몇 바이트에 들어 있는, 파일 형식을 알려 주는 고정된 값이에요. 예를 들어 JPEG는 `FF D8 FF`, PNG는 `89 50 4E 47`로 시작해요. 확장자는 이름만 바꾸면 속일 수 있지만 매직 넘버는 실제 내용이라 형식 확인에 써요.

### 디코딩
- 처음 등장: [SP Day 11](#/day/sp-d11)

압축되어 저장된 데이터(JPEG, PNG 파일 등)를 풀어서 실제로 쓸 수 있는 형태(픽셀 배열)로 바꾸는 일이에요. 이미지가 진짜인지는 끝까지 디코딩해 봐야 확실히 알 수 있어요.

### 재인코딩
- 처음 등장: [SP Day 11](#/day/sp-d11)

디코딩한 픽셀을 새 형식으로 다시 압축해 새 파일로 저장하는 일이에요. 원본 파일의 바이트를 가져가지 않으므로, 숨어 있던 메타데이터나 이상한 데이터가 함께 저장되지 않아요. 이 서비스는 모든 업로드를 WebP로 재인코딩해요.

### EXIF
- 처음 등장: [SP Day 11](#/day/sp-d11)

사진 파일 안에 들어 있는 촬영 정보예요. 찍은 기기, 시각, 사진 방향, 그리고 GPS 위치까지 들어 있을 수 있어요. 시청자의 위치가 새지 않도록 이 서비스는 EXIF를 남기지 않고, 방향 정보만 픽셀에 적용해요.

### WebP
- 처음 등장: [SP Day 11](#/day/sp-d11)

Google이 만든 이미지 형식이에요. 같은 품질에서 JPEG·PNG보다 파일이 작은 편이고, 주요 브라우저와 OBS 브라우저 소스가 표시할 수 있어요. 이 서비스는 처리한 이미지를 모두 WebP(품질 80)로 저장해요.

### SkiaSharp
- 처음 등장: [SP Day 11](#/day/sp-d11)

Google의 그래픽 엔진 Skia를 .NET에서 쓰게 해 주는 라이브러리예요. 이미지 형식 판별, 디코딩, 크기 조절, WebP 저장을 할 수 있어요. MIT 라이선스라 상업적으로 써도 라이선스 비용이 없어요(4.154.0 기준).

### 압축 폭탄
- 처음 등장: [SP Day 11](#/day/sp-d11)

파일 크기는 작지만 풀면 엄청나게 큰 데이터가 되도록 만든 파일이에요. 이미지라면 머리글에 아주 큰 가로·세로를 적어 서버 메모리를 바닥내려고 해요. 디코딩 전에 크기를 확인하고 상한을 두면 막을 수 있어요.

### 오픈소스 라이선스
- 처음 등장: [SP Day 11](#/day/sp-d11)

공개된 소스 코드를 누가, 어떤 조건으로 쓸 수 있는지 정한 약속이에요. MIT처럼 거의 조건 없이 상업적으로 쓸 수 있는 것도 있고, 매출 규모에 따라 유료 계약이 필요한 것도 있어요. 라이브러리를 고를 때 기능만큼 라이선스도 확인해요.

### BackgroundService
- 처음 등장: [SP Day 12](#/day/sp-d12)

ASP.NET Core 앱 안에서 요청과 상관없이 뒤에서 계속 도는 작업을 만드는 기본 클래스예요. `ExecuteAsync` 안에 반복할 일을 쓰면 앱이 켜질 때 시작하고 꺼질 때 멈춰요. 이 서비스의 정리 작업과 치지직 연결 점검이 이것을 써요.

### 보관 기간
- 처음 등장: [SP Day 12](#/day/sp-d12)

모은 데이터를 지우지 않고 두는 기간이에요. 기간이 지나면 지워야 개인정보를 필요 이상 오래 갖고 있지 않아요. 이 서비스는 후원 이미지와 기록을 7일 동안 보관하고 자동으로 지워요.

### Cache-Control
- 처음 등장: [SP Day 12](#/day/sp-d12)

브라우저와 중간 서버가 응답을 얼마나 오래, 어디에 저장해 둬도 되는지 알려 주는 HTTP 응답 헤더예요. 예를 들어 `private, max-age=3600`은 "이 사용자의 브라우저만 1시간 동안 저장해도 돼요"라는 뜻이에요.

### 온보딩
- 처음 등장: [SP Day 13](#/day/sp-d13)

새 사용자가 서비스를 처음 쓸 수 있게 준비를 마치는 과정이에요. 이 서비스에서는 가입한 스트리머가 후원 페이지 주소와 방송 이름을 정하면, 비밀 오버레이 주소와 기본 설정이 만들어져요.

### slug
- 처음 등장: [SP Day 13](#/day/sp-d13)

주소에 넣기 좋게 영문 소문자·숫자·하이픈으로만 만든 짧은 이름이에요. 후원 페이지 주소 `/d/my-stream`에서 `my-stream`이 slug예요. 사람이 읽기 쉽고 주소에 써도 깨지지 않아요.

### 암호학적 난수
- 처음 등장: [SP Day 13](#/day/sp-d13)

앞뒤 값을 보고도 다음 값을 추측할 수 없도록 만든 무작위 수예요. 비밀 토큰이나 코드처럼 남이 맞히면 안 되는 값에 써요. .NET에서는 `RandomNumberGenerator`가 만들어 줘요.

### Base64Url
- 처음 등장: [SP Day 13](#/day/sp-d13)

바이트 데이터를 영문자·숫자·`-`·`_`만으로 된 글자로 바꾸는 방식이에요. 일반 Base64의 `+`, `/`, `=`는 주소에서 특별한 뜻이 있어서, 주소에 넣어도 안전하도록 바꾼 형식이에요. 32바이트를 바꾸면 43글자가 돼요.

### HMAC
- 처음 등장: [SP Day 14](#/day/sp-d14)

비밀 키와 데이터를 함께 넣어 만드는 해시 값이에요(Hash-based Message Authentication Code). 키를 모르는 사람은 같은 결과를 만들 수 없어서, IP 주소처럼 경우의 수가 적은 값도 원문을 거꾸로 알아내기 어려워요. 이 서비스는 보낸 사람 IP를 HMAC-SHA256으로만 저장해요.

### 공개 API
- 처음 등장: [SP Day 14](#/day/sp-d14)

로그인 없이 누구나 부를 수 있는 API예요. 시청자용 후원 페이지가 쓰는 API가 여기에 해당해요. 누구나 부를 수 있으므로 입력 검사, 요청 제한, 비밀 값 숨기기를 더 꼼꼼히 해요.

### SignalR
- 처음 등장: [SP Day 15](#/day/sp-d15)

ASP.NET Core에서 서버와 브라우저가 실시간으로 메시지를 주고받게 해 주는 라이브러리예요. 가능하면 WebSocket을 쓰고, 안 되면 다른 방식으로 자동으로 바꿔요. 서버가 "이 그룹의 화면들에게 이 메시지를 보내"라고 쉽게 쓸 수 있어요.

### 허브
- 처음 등장: [SP Day 15](#/day/sp-d15)

SignalR에서 서버 쪽 연결 지점이 되는 클래스예요. 클라이언트가 `/hubs/overlay` 같은 주소로 허브에 연결하고, 허브는 연결된 클라이언트에게 메서드 이름으로 메시지를 보내거나 클라이언트가 부르는 메서드를 받아요.

### SignalR 그룹
- 처음 등장: [SP Day 15](#/day/sp-d15)

SignalR 연결 여러 개를 이름 하나로 묶은 것이에요. 그룹 이름으로 메시지를 보내면 그 그룹에 든 연결만 받아요. 이 서비스는 스트리머마다 그룹을 나눠, 내 후원이 다른 스트리머의 오버레이에 뜨지 않게 해요.

### 오버레이 토큰
- 처음 등장: [SP Day 16](#/day/sp-d16)

OBS 오버레이 주소에 들어 있는 비밀 값이에요(`overlay.html?token=…`). 오버레이는 로그인하지 않고 이 토큰만으로 연결하므로 비밀번호처럼 다뤄야 해요. 새어 나가면 설정에서 재발급해 옛 주소를 쓸 수 없게 해요.

### 보안 헤더
- 처음 등장: [SP Day 16](#/day/sp-d16)

브라우저가 더 안전하게 동작하도록 서버가 응답에 붙이는 HTTP 헤더예요. 예를 들어 `X-Frame-Options: DENY`는 다른 사이트가 우리 화면을 몰래 끼워 넣지 못하게 하고, `Referrer-Policy: no-referrer`는 주소에 든 토큰이 다른 사이트로 전달되지 않게 해요.

### 조건부 업데이트
- 처음 등장: [SP Day 17](#/day/sp-d17)

"지금 상태가 이것일 때만 바꿔라"처럼 조건을 붙여 행을 고치는 UPDATE예요. 조건이 맞지 않으면 0행이 바뀌므로, 이미 승인된 후원을 다시 승인하는 일을 데이터베이스가 막아 줘요. 바뀐 행 수를 보고 성공 여부를 판단해요.

### ExecuteUpdate
- 처음 등장: [SP Day 17](#/day/sp-d17)

EF Core에서 행을 메모리로 읽어 오지 않고 데이터베이스에 UPDATE 문 하나를 바로 보내는 메서드예요(`ExecuteUpdateAsync`). `Where`로 조건을 붙이고 `SetProperty`로 바꿀 열을 정하며, 바뀐 행 수를 돌려줘요.

### 경쟁 상태
- 처음 등장: [SP Day 17](#/day/sp-d17)

두 작업이 거의 동시에 같은 데이터를 다룰 때, 실행 순서에 따라 결과가 달라지는 문제예요. 예를 들어 "읽어서 대기 중인지 확인 → 승인으로 저장"을 두 요청이 동시에 하면 둘 다 승인할 수 있어요. 조건부 업데이트나 잠금으로 막아요.

### 큐
- 처음 등장: [SP Day 18](#/day/sp-d18)

먼저 들어온 것이 먼저 나가는 줄 서기 목록이에요(대기열). 오버레이는 받은 후원을 큐에 넣고 맨 앞의 것부터 한 장씩 보여 줘요.

### useRef
- 처음 등장: [SP Day 18](#/day/sp-d18)

화면을 다시 그려도 사라지지 않는 값을 담아 두는 React 훅이에요. 값을 바꿔도 화면을 다시 그리지 않아서, 실시간 연결 객체처럼 화면과 상관없이 계속 들고 있어야 하는 것을 담기 좋아요.

### useCallback
- 처음 등장: [SP Day 18](#/day/sp-d18)

함수를 한 번 만들어 두고, 의존성 배열의 값이 바뀔 때만 새로 만드는 React 훅이에요. 그 함수를 의존성으로 쓰는 useEffect가 쓸데없이 다시 실행되지 않게 할 때 써요.

### 자동 재연결
- 처음 등장: [SP Day 18](#/day/sp-d18)

네트워크나 서버 문제로 실시간 연결이 끊겼을 때 프로그램이 스스로 다시 연결을 시도하는 기능이에요. OBS 오버레이는 몇 시간씩 켜 두므로 서버가 잠깐 재시작해도 다시 붙어야 해요. SignalR 클라이언트의 `withAutomaticReconnect()`가 이 일을 해요.

### 보호된 라우트
- 처음 등장: [SP Day 19](#/day/sp-d19)

로그인한 사람만 볼 수 있게 막아 둔 화면 경로예요. 로그인하지 않았으면 로그인 화면으로 보내요. 화면에서 막는 것은 편의일 뿐이고, 진짜 보호는 서버 API의 인증 검사가 해요.

### 자동 승인
- 처음 등장: [SP Day 20](#/day/sp-d20)

스트리머가 검수하지 않아도 들어온 후원을 바로 방송에 내보내는 설정이에요. 편하지만 부적절한 이미지가 그대로 나갈 수 있어서 기본값은 꺼져 있어요.

### 금지어
- 처음 등장: [SP Day 20](#/day/sp-d20)

닉네임이나 메시지에 들어 있으면 후원을 받지 않도록 스트리머가 정한 단어 목록이에요. 이 서비스는 대소문자를 무시하고 단어가 포함되어 있는지 검사해요.

### useOutletContext
- 처음 등장: [SP Day 20](#/day/sp-d20)

레이아웃 라우트가 Outlet에 넘긴 값을 자식 화면에서 꺼내 쓰는 React Router 훅이에요. 이 서비스는 로그인한 스트리머 정보를 레이아웃에서 한 번 불러와 여러 화면이 함께 써요.

### Clipboard API
- 처음 등장: [SP Day 20](#/day/sp-d20)

웹페이지가 클립보드에 글자를 복사하거나 읽게 해 주는 브라우저 기능이에요(`navigator.clipboard.writeText`). 보안 때문에 https 주소나 localhost처럼 안전한 곳에서만 동작해요.

### OAuth 2.0
- 처음 등장: [SP Day 21](#/day/sp-d21)

사용자가 비밀번호를 우리 서비스에 알려 주지 않고도, 다른 서비스(예: 치지직)의 계정으로 로그인하거나 정해진 권한만 빌려줄 수 있게 하는 표준 방식이에요. 사용자는 치지직 화면에서 동의하고, 우리 서버는 그 결과로 토큰을 받아요.

### 인가 코드
- 처음 등장: [SP Day 21](#/day/sp-d21)

OAuth 2.0에서 사용자가 동의한 뒤 우리 리디렉션 주소로 전달되는 1회용 짧은 코드예요. 이 코드만으로는 아무것도 할 수 없고, 서버가 Client Secret과 함께 보내야 토큰으로 바꿀 수 있어요.

### 액세스 토큰
- 처음 등장: [SP Day 21](#/day/sp-d21)

API를 부를 때 "이 사용자가 허락했어요"를 증명하려고 요청 헤더에 넣는 값이에요(`Authorization: Bearer 토큰`). 유효 기간이 짧아서 치지직은 1일이에요(작성 기준일 2026-11, 공식 문서 기준).

### 리프레시 토큰
- 처음 등장: [SP Day 21](#/day/sp-d21)

액세스 토큰이 만료됐을 때 사용자에게 다시 묻지 않고 새 액세스 토큰을 받는 데 쓰는 값이에요. 치지직의 리프레시 토큰은 30일 동안 유효하고 한 번만 쓸 수 있어서, 갱신할 때마다 새 값으로 바꿔 저장해야 해요.

### state 값
- 처음 등장: [SP Day 21](#/day/sp-d21)

OAuth 로그인을 시작할 때 우리가 만든 1회용 무작위 값이에요. 로그인 화면으로 보낼 때 함께 보내고, 돌아왔을 때 같은 값인지 확인해서 남이 위조한 로그인 결과를 걸러 내요.

### OAuth 스코프
- 처음 등장: [SP Day 21](#/day/sp-d21)

OAuth로 사용자가 허락하는 권한의 범위예요. 예를 들어 "후원 조회", "유저 정보 조회", "채팅 메시지 쓰기"처럼 나뉘어요. 치지직은 스코프를 로그인 주소에 적지 않고 개발자 센터의 앱 설정에서 정해요.

### 리디렉션 URI
- 처음 등장: [SP Day 21](#/day/sp-d21)

OAuth 로그인이 끝난 뒤 인가 코드를 들고 돌아올 우리 서비스의 주소예요. 개발자 센터에 등록한 값과 로그인 요청에 넣은 값이 글자 하나까지 같아야 해요.

### 치지직 개발자 센터
- 처음 등장: [SP Day 22](#/day/sp-d22)

치지직 Open API를 쓰려는 개발자가 애플리케이션을 등록하고 Client ID와 Client Secret을 받는 웹사이트예요(`developers.chzzk.naver.com`). 리디렉션 주소와 필요한 스코프도 여기서 설정해요.

### Client ID
- 처음 등장: [SP Day 22](#/day/sp-d22)

개발자 센터에 등록한 우리 애플리케이션을 구별하는 공개 식별자예요. 로그인 주소에 그대로 들어가므로 남이 봐도 괜찮아요.

### Client Secret
- 처음 등장: [SP Day 22](#/day/sp-d22)

우리 애플리케이션만 아는 비밀 값이에요. 인가 코드를 토큰으로 바꿀 때 서버가 함께 보내요. 코드·커밋·화면·방송에 절대 노출하지 않고 user-secrets나 환경 변수에만 둬요.

### 치지직 Open API
- 처음 등장: [SP Day 22](#/day/sp-d22)

치지직이 외부 개발자에게 공개한 API 모음이에요(`https://openapi.chzzk.naver.com`). 사용자 정보 조회, 채팅 보내기, 세션 소켓으로 채팅·후원 이벤트 받기 등을 제공해요. 문서는 바뀔 수 있으니 쓰기 전에 공식 문서를 다시 확인해요.

### 토큰 교환
- 처음 등장: [SP Day 23](#/day/sp-d23)

OAuth 2.0에서 서버가 인가 코드를 Client ID·Client Secret과 함께 보내고, 대신 액세스 토큰과 리프레시 토큰을 받는 단계예요. 브라우저가 아니라 서버끼리 주고받아서 Secret이 밖으로 나가지 않아요.

### 계정 연결
- 처음 등장: [SP Day 23](#/day/sp-d23)

다른 서비스의 계정(치지직 채널)을 우리 서비스의 계정 하나에 이어 붙이는 일이에요. 한 번 연결하면 다음부터 치지직으로 로그인해도 같은 계정으로 들어와요.

### 타이밍 공격
- 처음 등장: [SP Day 23](#/day/sp-d23)

비교에 걸리는 시간 차이를 재서 비밀 값을 한 글자씩 알아내려는 공격이에요. 일반 문자열 비교는 다른 글자를 만나면 바로 멈추기 때문에 걸리는 시간이 조금씩 달라요. 비밀 값은 항상 같은 시간이 걸리는 비교 함수(`FixedTimeEquals`)로 비교해요.

### Data Protection
- 처음 등장: [SP Day 24](#/day/sp-d24)

ASP.NET Core가 제공하는 암호화 기능이에요. 앱이 관리하는 키로 값을 암호화(`Protect`)하고 다시 풀어요(`Unprotect`). 로그인 쿠키도 이것으로 보호되고, 이 서비스는 치지직 토큰을 DB에 저장하기 전에 이것으로 암호화해요.

### 토큰 회전
- 처음 등장: [SP Day 24](#/day/sp-d24)

토큰을 갱신할 때마다 새 토큰을 받고 옛 토큰은 못 쓰게 되는 방식이에요. 치지직의 리프레시 토큰이 이렇게 동작하므로, 갱신 응답에 든 새 리프레시 토큰을 바로 저장해야 해요.

### SemaphoreSlim
- 처음 등장: [SP Day 24](#/day/sp-d24)

.NET에서 동시에 들어올 수 있는 작업 수를 제한하는 잠금 도구예요. 개수를 1로 만들면 한 번에 하나만 통과해요. 이 서비스는 1회용 리프레시 토큰을 두 요청이 동시에 쓰지 않도록 이것으로 줄을 세워요.

### Socket.IO
- 처음 등장: [SP Day 25](#/day/sp-d25)

### Engine.IO
- 처음 등장: [SP Day 25](#/day/sp-d25)

Socket.IO 아래에서 실제 연결(폴링, WebSocket)을 맡는 통신 규칙이에요. 버전을 EIO 번호로 부르고, Socket.IO 2.x 서버는 EIO=3을 써요. 치지직 세션 소켓은 Socket.IO 2.x이므로 .NET 클라이언트에 `EIO = V3`를 지정해요.

### 세션 소켓
- 처음 등장: [SP Day 25](#/day/sp-d25)

치지직이 채팅·후원 같은 이벤트를 실시간으로 보내 주는 Socket.IO 연결이에요. 세션 주소를 API로 받아 연결하고, 연결 메시지로 받은 세션 키로 원하는 이벤트를 구독해요. 세션 주소는 1회용이에요.

### 에뮬레이터
- 처음 등장: [SP Day 25](#/day/sp-d25)

진짜 시스템을 흉내 내는 프로그램이에요. 이 프로젝트의 치지직 에뮬레이터는 내 PC에서 Socket.IO 2.5.0 서버로 치지직 세션 소켓과 비슷한 메시지를 보내 줘요. 실제 치지직이 아니므로, 여기서 된다고 실서버에서도 된다는 보장은 없어요.

### 페이로드

메시지나 요청에 담긴 실제 내용 부분이에요. 예를 들어 치지직 DONATION 이벤트의 페이로드에는 후원 금액, 후원 메시지, 후원자 닉네임이 들어 있어요.

### C# 이벤트
- 처음 등장: [SP Day 26](#/day/sp-d26)

### 브라우저 중계
- 처음 등장: [SP Day 26](#/day/sp-d26)

서버가 외부 실시간 연결에 직접 붙을 수 없을 때, 브라우저(대시보드 화면)가 대신 연결해서 받은 이벤트를 우리 서버로 넘겨주는 방식이에요. 이 교재의 기본 구현은 서버가 직접 연결하고, 이것은 안 될 때의 대안으로 소개만 해요.

### 후원 코드
- 처음 등장: [SP Day 27](#/day/sp-d27)

치즈 모드에서 이미지 후원 1건마다 발급하는 `#AB12` 같은 짧은 코드예요. 시청자가 치지직 치즈 후원 메시지에 이 코드를 넣으면, 서버가 이벤트 속 코드를 찾아 어느 이미지 후원의 치즈인지 맞춰요. 30분 안에 써야 해요.

### 멱등성
- 처음 등장: [SP Day 27](#/day/sp-d27)

같은 요청이나 이벤트를 여러 번 처리해도 결과가 한 번 처리한 것과 같은 성질이에요. 같은 후원 이벤트가 두 번 와도 이미지 후원이 한 번만 확인되도록 조건부 업데이트로 지켜요.

### 할당량
- 처음 등장: [SP Day 28](#/day/sp-d28)

외부 API를 일정 시간 동안 부를 수 있는 횟수 한도예요(Quota). 넘으면 보통 429(Too Many Requests) 응답을 받아요. 치지직 할당량의 정확한 수치는 이 교재 작성 시점에 확인하지 못했어요.

### XMLHttpRequest
- 처음 등장: [SP Day 29](#/day/sp-d29)

### FormData
- 처음 등장: [SP Day 29](#/day/sp-d29)

폼의 입력값과 파일을 multipart/form-data로 보내기 좋게 담는 브라우저 객체예요. `append('image', file)`처럼 이름과 값을 넣고 요청 본문으로 넘기면, 브라우저가 경계 문자열과 Content-Type을 알아서 정해요.

### 업로드 진행률
- 처음 등장: [SP Day 29](#/day/sp-d29)

파일을 서버로 보내는 동안 전체 중 얼마나 보냈는지를 퍼센트로 나타낸 값이에요. 휴대폰처럼 느린 네트워크에서 "멈췄나?" 하는 걱정을 줄여 줘요.

### 신고

스트리머가 부적절한 후원을 서비스 운영자에게 알리는 기능이에요. 신고하면 그 후원은 거절되고 보낸 사람은 차단되며, 이미지는 운영자가 확인할 증거로 격리해 두었다가 보관 기간이 지나면 지워져요.

### 차단

### 긴급 정지

방송 화면에 문제가 생겼을 때 오버레이에 보이는 이미지와 대기 중인 이미지를 한 번에 모두 내리는 기능이에요. 화면 비우기를 가장 먼저 하고, 아직 나가지 않은 승인 후원은 "긴급 정지됨"으로 바꿔 다시 나오지 않게 해요.
