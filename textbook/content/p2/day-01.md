## 📖 개념 이해

### 웹사이트는 세 부분으로 이루어져 있어요

**비유부터 볼게요.** 식당을 떠올려 보세요. 손님이 앉아서 메뉴판을 보고 음식을 받는 **홀**, 주문을 받아 요리하는 **주방**, 재료를 정리해 보관하는 **창고**가 있어요. 손님은 주방에 들어가지 않고, 홀에서 주문서를 내고 음식을 받아요.

웹사이트도 똑같이 세 부분이에요.

```text
브라우저 (홀)
  │ 요청      ▲ 응답
  ▼           │
C# 서버 (주방)
  │ 읽기·쓰기 ▲ 결과
  ▼           │
데이터베이스 (창고)
```

**정확한 정의는 이래요.**

- **[[프론트엔드]]**(front-end)는 사용자가 직접 보고 누르는 화면 쪽 프로그램이에요. 브라우저 안에서 HTML, CSS, JavaScript(앞으로는 TypeScript)로 만들어요. P1에서 만든 사이트가 프론트엔드예요.
- **[[백엔드]]**(back-end)는 화면 뒤에서 데이터를 저장하고, 규칙을 검사하고, 요청에 답하는 서버 쪽 프로그램이에요. 사용자 눈에는 보이지 않아요. 스트리머 허브에서는 C#으로 만들어요.
- **[[데이터베이스]]**(database)는 데이터를 정해진 모양으로 오래 보관하고, 빠르게 찾고 고칠 수 있게 해 주는 저장소예요. 프로그램을 껐다 켜도 데이터가 남아요. 줄여서 DB라고 해요. 스트리머 허브에서는 SQLite라는 DB를 써요.
- **[[풀스택]]**(full-stack)은 프론트엔드, 백엔드, 데이터베이스까지 한 서비스의 모든 층을 함께 다루는 것을 말해요. P2에서는 이 세 층을 모두 직접 만들어요.

P1에서는 글과 영상 목록을 화면 파일 안에 직접 적어 두었어요. 그래서 "로그인", "게시판 글 저장", "다른 사람이 쓴 글 보기"를 만들 수 없었어요. 사람이 많아도 같은 글을 보려면 **모두가 함께 쓰는 보관 장소**가 필요하고, 그 장소를 지키는 프로그램이 백엔드예요.

### 클라이언트, 요청, 응답, API

**비유:** 식당에서 손님이 주문서를 내면(요청), 주방이 요리를 만들어 내보내요(응답). 주문서에 적을 수 있는 메뉴 이름이 정해져 있어야 주방이 알아듣겠죠? 그 메뉴판이 API예요.

**정확한 정의:**

- **[[클라이언트]]**(client)는 서버에 무언가를 요청하는 쪽 프로그램이에요. 웹에서는 보통 브라우저와 그 안에서 도는 화면 코드가 클라이언트예요. 서버가 "주는 쪽"이라면 클라이언트는 "받아서 보여 주는 쪽"이에요.
- **[[요청]]**(request)은 클라이언트가 서버에게 "이것을 주세요" 또는 "이것을 해 주세요"라고 보내는 메시지예요. 주소, 방법, 필요하면 보낼 데이터가 들어 있어요.
- **[[응답]]**(response)은 서버가 요청을 받고 돌려보내는 메시지예요. 결과를 나타내는 번호와 내용(HTML 파일, JSON 데이터 등)이 들어 있어요.
- **[[API]]**(에이피아이)는 프로그램끼리 정해진 방법으로 기능이나 데이터를 주고받게 해 주는 약속이에요. 웹에서는 보통 "이 주소로 이렇게 요청하면 이런 [[JSON]]을 돌려준다"는 규칙 모음을 말해요. 스트리머 허브에서는 이런 주소들이 API예요.

```text
GET /api/streamers
→ 스트리머 목록을 줘요

GET /api/schedules
→ 방송 일정을 줘요

POST /api/posts
→ 게시판에 새 글을 저장해요
```

앞에 붙은 `GET`, `POST`는 요청의 **방법**이에요. `GET`은 "가져오기", `POST`는 "새로 만들기"라고 먼저 기억해 두세요. 자세한 내용은 [[HTTP 메서드]]를 Day 16에서 배워요.

응답에는 결과를 나타내는 번호가 붙어요. 이 번호를 [[상태 코드]]라고 하고, 오늘은 두 개만 알면 돼요.

- `200`: 잘 됐어요. 요청한 것을 드릴게요.
- `404`: 없어요. 그 주소에는 아무것도 없어요.

### P1과 P2는 어디가 달라요?

[P1 Day 25](#/day/p1-d25)에서 `fetch`로 `data/videos.json` 파일을 읽어 왔죠? 그때도 이미 요청과 응답이 있었어요. 다른 점은 **응답을 만드는 쪽**이에요.

```text
P1: 브라우저
      │ 요청
      ▼
    파일 서버 ─▶ .json 파일
    (파일을 그대로 전달)

P2: 브라우저
      │ 요청
      ▼
    C# 서버 ─▶ SQLite DB
    (규칙에 따라 계산해서 답)
```

P1의 서버는 파일을 그대로 건네주기만 했어요. P2의 서버는 요청을 받으면 DB에서 읽고, 로그인한 사람인지 확인하고, 규칙에 맞는지 검사한 뒤 답을 만들어요.

:::info 실무에서는
회사에서도 대부분의 웹 서비스가 이 세 부분 구조예요. 프론트엔드 개발자와 백엔드 개발자가 나뉘어 일하는 곳이 많고, 둘이 주고받는 약속이 API예요. 풀스택이 되면 혼자서 서비스 하나를 처음부터 끝까지 만들 수 있어요. 그래서 이 책의 40일은 화면 → 서버 → DB → 연결 → 배포 순서로 가요.
:::

### 40일 동안 만들 스트리머 허브

완성본에는 화면이 7종류 있어요. 그림은 아주 단순하게 줄인 모양이에요.

**1. 홈**

```text
+-----------------------------+
| 스트리머 허브  홈 스트리머  |
+-----------------------------+
| 스트리머 허브               |
| [이번 주 방송 일정]         |
| 다가오는 방송               |
|  달빛곰 · 저녁 게임 방송    |
| 팬 게시판 새 글             |
+-----------------------------+
```

**2. 스트리머 목록·상세**

```text
+-----------------------------+
| [검색: 이름        ]        |
| +--------+ +--------+       |
| | 달빛곰 | | 픽셀   |       |
| | 치지직 | | 토끼   |       |
| +--------+ +--------+       |
| 달빛곰을 누르면 상세 화면   |
+-----------------------------+
```

**3. 주간 방송 일정**

```text
+-----------------------------+
| < 이전 주   이번 주  다음 >|
| 월 20:00 달빛곰 게임 방송   |
| 화 13:00 픽셀토끼 그림      |
| 금 21:00 노을고양이 노래    |
+-----------------------------+
```

**4. 팬 게시판**

```text
+-----------------------------+
| 팬 게시판       [글쓰기]    |
| 첫 글이에요   팬1  11/02    |
| 응원해요      팬2  11/03    |
| < 1 2 3 >                   |
+-----------------------------+
```

**5. 로그인·가입**

```text
+-----------------------------+
| 이메일    [              ]  |
| 비밀번호  [              ]  |
| [로그인]                    |
+-----------------------------+
```

**6. 관리자 화면** (관리자 계정만 볼 수 있어요)

```text
+-----------------------------+
| 관리자                      |
| 스트리머 등록 / 수정 / 삭제 |
| 방송 일정 등록              |
| 공지 보내기 [          ]    |
+-----------------------------+
```

**7. OBS 공지 오버레이** (P1 Day 27의 오버레이와 같은 종류예요. 방송 화면 위에 띄워요)

```text
+-----------------------------+
|        (방송 화면)          |
|                             |
|  [공지] 오늘 8시에 시작!    |
+-----------------------------+
```

화면 주소와 화면의 대응은 이렇게 돼요. `#` 뒤의 글자로 화면을 바꾸는 방법은 Day 28에서 만들어요.

## 🛠️ 따라하기

모두 7단계예요. 한 단계를 끝낼 때마다 성공 상자와 내 화면을 비교해요.

### 1단계 · P1 사이트를 브라우저로 열기 (5분)

요청과 응답을 눈으로 보려면 진짜 요청이 오가는 페이지가 필요해요. P1에서 만든 사이트의 **콘텐츠 페이지**(`contents.html`)가 딱 좋아요. 이 페이지는 `fetch`로 `data/videos.json`을 읽어 오거든요.

**어디서:** VS Code (폴더 `C:\dev\my-creator-site`가 열려 있는 창)

**무엇을:**

1. VS Code 왼쪽 탐색기에서 `contents.html`을 오른쪽 클릭하고 Live Preview 확장 프로그램의 **Show Preview**(영어) 항목을 클릭해요. 한국어 화면에서는 이름이 조금 다를 수 있어요. [P1 Day 2](#/day/p1-d02)에서 Live Preview를 켠 방법 그대로 하면 돼요.
2. VS Code 안에 미리 보기 창이 열리면 창 위쪽의 주소 칸에서 주소를 확인해요. `http://127.0.0.1:3000/contents.html`처럼 생겼어요. 숫자 `3000`은 달라도 돼요.
3. 이 주소를 통째로 복사해요. 주소 칸을 클릭한 뒤 `Ctrl + A`, `Ctrl + C`를 눌러요.
4. Chrome 또는 Edge를 열고 주소 표시줄에 붙여 넣은 뒤 `Enter`를 눌러요.

:::success
브라우저에 P1에서 만든 콘텐츠 페이지가 보이고, 영상 카드가 나열되어 있어요. 주소 표시줄이 `http://127.0.0.1:…/contents.html`로 시작해요.
:::

:::tip 다른 길
- GitHub Pages에 올려 둔 사이트가 있으면 `https://<내 아이디>.github.io/my-creator-site/contents.html`을 열어도 같아요. 아이디를 잊었다면 GitHub 저장소 페이지의 **Settings → Pages**에서 주소를 볼 수 있어요.
- P1 사이트가 아예 없으면 `https://example.com/`을 열어 보세요. 요청이 한 개뿐인 단순한 페이지라서 3단계까지는 그대로 따라 할 수 있어요. 과제의 표는 보이는 줄만 적으면 돼요.
:::

### 2단계 · 개발자 도구 Network 탭 열기 (4분)

[P1 Day 6](#/day/p1-d06)에서 개발자 도구를 열어 봤죠? 오늘은 **Network** 탭을 써요. 이 탭은 **열어 둔 뒤에 일어난 요청**만 보여 줘요. 그래서 먼저 탭을 열고, 그다음에 페이지를 새로 고쳐야 해요.

**어디서:** Chrome 또는 Edge (1단계의 콘텐츠 페이지가 열린 탭)

**무엇을:**

1. `F12`를 눌러요. 노트북이면 `Fn + F12`일 수 있어요. 안 열리면 페이지의 빈 곳을 오른쪽 클릭하고 **검사**(영어: **Inspect**)를 클릭해요.
2. 개발자 도구 위쪽 탭 줄에서 **Network**를 클릭해요. 한국어 화면에서는 **네트워크**라고 보일 수 있어요. 안 보이면 탭 줄 오른쪽의 `»`를 눌러 목록에서 골라요.
3. 페이지로 마우스를 옮기고 `F5`를 눌러 새로 고침해요.

:::success
Network 탭에 표가 나타나요. 왼쪽부터 **Name**, **Status**, **Type**, **Size**, **Time** 같은 열이 있고, 줄이 여러 개 쌓여요. 맨 위 줄은 `contents.html`이에요. 줄 개수는 달라도 돼요. 탭이 비어 있다면 3단계로 가지 말고 아래 🧯 자주 막히는 곳의 첫 번째 항목을 보세요.
:::

### 3단계 · 요청 세 개 읽기: HTML, CSS, JSON (9분)

브라우저는 주소 하나를 열 때 요청을 한 번이 아니라 여러 번 보내요. 먼저 HTML 파일을 받고, 그 안에 적힌 CSS 파일, JavaScript 파일, 이미지를 하나씩 더 요청해요. 오늘은 이 중 세 줄만 자세히 읽어요.

**어디서:** 개발자 도구 → **Network** 탭 → 목록

**무엇을:**

1. 목록에서 **Name** 열이 `contents.html`인 줄을 찾아 **Status**와 **Type**을 읽어요.
2. `style.css` 줄을 찾아 읽어요.
3. `videos.json` 줄을 찾아 읽어요.
4. `videos.json` 줄을 클릭해요. 오른쪽(또는 아래쪽)에 자세한 창이 열려요.
5. 자세한 창 위쪽에서 **Headers** 탭을 클릭하고 **General** 부분의 **Request URL**, **Request Method**, **Status Code**를 읽어요.
6. **Response** 탭을 클릭해요.

예상되는 값은 이래요. 내 화면의 **Type** 글자는 브라우저 버전에 따라 조금 다를 수 있어요.

| Name | Status | Type |
|---|---|---|
| `contents.html` | `200` | `document` |
| `style.css` | `200` | `stylesheet` |
| `videos.json` | `200` | `fetch` |

:::success
- **Status**가 세 줄 모두 `200`이에요.
- `videos.json`의 **Request Method**가 `GET`이에요. 주소창에 주소를 쳐서 페이지를 여는 일도 `GET` 요청이에요.
- **Response** 탭에 `[`와 `{`, `"title"` 같은 글자가 줄줄이 보여요. P1 Day 25에서 만든 JSON 글자 그대로예요.
:::

이것이 **응답 하나**예요. 번호(`200`), 종류(`fetch`), 내용(JSON 글자)이 들어 있죠. 지금은 서버가 파일을 그대로 건네줬고, 스트리머 허브에서는 이 JSON을 C# 서버가 만들어 줄 거예요.

## 🧯 자주 막히는 곳

여기에 없는 증상은 [문제 해결 모음](#/page/troubleshooting)에서 찾아보세요.

### Network 탭이 비어 있어요

**원인:** Network 탭은 탭을 연 뒤에 일어난 요청만 기록해요. 페이지를 먼저 열고 개발자 도구를 나중에 열면 그 전의 요청은 목록에 없어요.

**해결:** 개발자 도구에서 **Network** 탭이 선택된 상태로 페이지로 마우스를 옮기고 `F5`를 눌러요. 줄이 나타나면 해결이에요.

### `videos.json` 줄이 빨간색이거나 `Failed to fetch` 오류 상자가 나와요

**원인:** 파일을 더블클릭해서(`file:///C:/…`로 시작하는 주소로) 열었어요. 브라우저의 보안 규칙 때문에 이 방식에서는 `fetch`로 다른 파일을 읽을 수 없어요. P1 Day 25에서 배운 규칙이에요. 브라우저 콘솔(Console 탭)에는 이런 오류가 보여요(문구는 브라우저와 버전에 따라 조금 달라요).

```text
Fetch API cannot load file:///.../data/videos.json. URL scheme "file" is not supported.
```

**해결:** VS Code Live Preview의 주소(`http://127.0.0.1:…`)나 GitHub Pages 주소로 열어요. 1단계를 처음부터 다시 따라 하면 돼요. 주소가 `http`로 시작하면 해결이에요.

### P1 배포 주소가 기억나지 않아요

**원인:** 주소를 따로 적어 두지 않았어요. 주소는 GitHub에 있어요.

**해결:**

1. 브라우저에서 `https://github.com/`에 로그인하고 `my-creator-site` 저장소를 열어요.
2. 위쪽 탭 줄에서 **Settings**를 클릭하고 왼쪽 메뉴에서 **Pages**를 클릭해요.
3. 화면 위쪽에 `Your site is live at …` 같은 주소 안내가 보여요(문구는 바뀔 수 있어요). 그 주소 뒤에 `contents.html`을 붙여서 열어요.

### 폴더를 바탕 화면이나 OneDrive 안에 만들었어요

**원인:** 파일 탐색기의 새 폴더가 지금 보고 있는 위치에 만들어져요. `C:\dev`로 이동하지 않고 만들면 엉뚱한 곳에 생겨요.

**해결:**

1. 파일 탐색기 주소 표시줄의 빈 곳을 클릭하고 경로를 읽어요. `C:\dev\streamer-hub`가 아니면 잘못 만든 거예요.
2. 잘못 만든 `streamer-hub` 폴더는 그 안이 비어 있을 때 클릭하고 `Delete` 키로 지워요.
3. 5단계를 처음부터 다시 따라 해요.

### 파일 이름이 `README.md.txt`가 되었어요

**원인:** 메모장처럼 확장자를 몰래 붙이는 프로그램으로 만들었거나, 이름을 `README`만 입력했을 때 생겨요. VS Code 탐색기에서 `README.md`라고 정확히 입력하면 생기지 않아요.

**해결:**

1. 파일 탐색기에서 **보기 → 표시 → 파일 확장명**이 켜져 있는지 확인해요.
2. VS Code에서 그 파일이 열려 있으면 탭을 닫아요.
3. 파일 탐색기에서 `README.md.txt`를 한 번 클릭하고 `F2`를 눌러요. `End` 키로 끝으로 간 뒤 `Backspace`를 4번 눌러 `.txt`를 지우고 `Enter`를 눌러요. 확장자를 바꾸겠느냐는 경고가 나오면 **예**를 클릭해요.
4. VS Code 탐색기에서 `README.md`가 보이면 해결이에요.

### `F12`를 눌러도 개발자 도구가 안 열려요

**원인:** 노트북에서는 기능 키가 `Fn`과 함께 눌려야 할 수 있어요.

**해결:** `Fn + F12`를 눌러요. 그래도 안 되면 페이지의 빈 곳을 오른쪽 클릭하고 **검사**를 클릭해요. 또는 `Ctrl + Shift + I`를 눌러요.
